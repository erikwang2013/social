## 1. लक्ष्य और दायरा

छवि+पाठ शॉर्ट-कंटेंट और IM को जोड़ने वाला एक सोशल प्लेटफ़ॉर्म बनाना, जिसमें लाइव स्ट्रीमिंग (वीडियो + दानमाकु + माइक-लिंक), वॉइस (संदेश / 1v1 कॉल / वॉइस चैट रूम) और गिफ्ट-टिपिंग वर्चुअल अर्थव्यवस्था शामिल हो। UI बहुभाषीकरण, कंटेंट अनुवाद और बहु-क्षेत्रीय अनुपालन का समर्थन, वैश्विक बहु-क्षेत्रीय तैनाती के साथ। तीन प्लेटफ़ॉर्म पर समानांतर नेटिव डेवलपमेंट: iOS / Android / HarmonyOS।

## 2. सिस्टम अवलोकन

```
                    ┌─────────────────────────────────────────────┐
                    │   iOS (SwiftUI) │ Android (Kotlin+Compose)  │
                    │            HarmonyOS (ArkTS)                │

              │   service (webman v2)     │──gRPC──▶ infrastructure
              │  业务单体：认证/资料/动态/ │          (bee-rust)
              │  点赞/评论/关注/IM 网关/   │  gRPC      搜索/推荐/图/
              │  翻译调度/审核/直播/语音/  │  ▲        时序/热数据

  media/（自建媒体层，信令走 service WS 网关）

```

## 3. सबसिस्टम की ज़िम्मेदारियाँ

### 3.1 contracts (gRPC अनुबंध, नया शीर्ष-स्तरीय निर्देशिका)

```
contracts/
├── buf.yaml                      # buf 配置（唯一生成入口）
├── common/types.proto            # 分页、错误、时间戳、区域枚举等公共类型
├── infra/infra_service.proto     # infrastructure 对外服务
├── user/user_service.proto       # service 对外服务（admin 调用用）
└── admin/admin_service.proto     # admin 对外服务（service/infra 调用用）
```

- जनरेशन पाइपलाइन: CI buf का उपयोग करके तीन प्रकार के स्टब जनरेट करता है और उन्हें संबंधित सब-रिपो में कमिट करता है (बिल्ड नेटवर्क पर निर्भर नहीं करते)
  - service/, admin/ → PHP स्टब (grpc/grpc + google/protobuf)
  - infrastructure/ → Rust स्टब (tonic)
- वर्जनिंग नियम: केवल फ़ील्ड जोड़ें, कभी संशोधित या हटाएँ नहीं; पैकेज नाम मेजर वर्जन रखते हैं (`social.user.v1`)

### 3.2 service (webman v2) — उपयोगकर्ता-पक्ष व्यवसाय मोनोलिथ

- **API डोमेन**: auth (JWT दोहरे टोकन + ब्लैकलिस्ट), profile, posts, likes, comments, follows, IM (कन्वर्सेशन/मैसेज/WS गेटवे), notifications, अनुवाद शेड्यूलिंग, लाइव रूम/दानमाकु/माइक-लिंक सिग्नलिंग, वॉइस कॉल/वॉइस चैट रूम सिग्नलिंग, वर्चुअल अर्थव्यवस्था (वॉलेट/गिफ्ट/IAP सत्यापन/रेवेन्यू शेयर), GDPR निर्यात/हटाना
- **बहुभाषी त्रुटि प्रणाली**: त्रुटियाँ `{code, lang_key, params}` लौटाती हैं; टेक्स्ट क्लाइंट द्वारा locale के अनुसार रेंडर किया जाता है
- **क्यू** (redis-queue): मॉडरेशन ट्रिगर, अनुवाद शेड्यूलिंग, पुश डिलीवरी, एसिंक्रोनस सांख्यिकी, गिफ्ट-इफ़ेक्ट ब्रॉडकास्ट
- **निर्धारित कार्य** (webman-crontab): अनुवाद प्री-वार्मिंग, समाप्त टोकन/मैसेज सफाई, ऑडिट संग्रहण, रेवेन्यू-शेयर निपटान
- **ID**: `erikwang2013/snowflake-php` (admin के अनुरूप)
- **अनुबंध**: OpenAPI 3.0 स्वचालित निर्यात → तीनों प्लेटफ़ॉर्म के लिए टाइप किए गए क्लाइंट जनरेट

### 3.3 infrastructure (bee-rust) — उच्च-थ्रूपुट कंप्यूट लेयर

व्यवसाय का प्राथमिक डेटा संग्रहीत नहीं करता (MySQL एकमात्र सत्य का स्रोत है); कंप्यूट-भारी / क्वेरी-भारी क्षमताएँ संभालता है:

- `bee_search`: पोस्ट/उपयोगकर्ताओं पर फुल-टेक्स्ट खोज (चीनी शब्द विभाजन, बहुभाषी अनुक्रमण)
- `bee_graph`: सोशल ग्राफ़ → अनुशंसा फ़ीड
- `bee_tsdb`: DAU, पोस्टिंग, इंटरैक्शन, लाइव व्यू, वॉइस कॉल अवधि आदि की टाइम-सीरीज़ सांख्यिकी
- `bee_cache/bee_kv`: टाइमलाइन कैश, काउंटर (लाइक संख्या, व्यू संख्या, ऑनलाइन उपयोगकर्ता)
- क्षेत्रवार तैनाती; पढ़ने-भारी, लिखने-हल्की; डेटा केंद्रीय स्थल से प्रतिकृति

### 3.4 admin (open-admin परिवर्तन)

**पुनः उपयोग**: JWT/RBAC/ऑडिट/फ़ाइल प्रबंधन/हेल्थ चेक/zh-en i18n इन्फ्रास्ट्रक्चर

**नया**:
- कंटेंट मॉडरेशन वर्कबेंच: पोस्ट/कमेंट/इमेज की द्विभाषी साथ-साथ समीक्षा, बहुभाषी अस्वीकृति-कारण टेम्पलेट, उपयोगकर्ता दंड
- रिपोर्ट प्रबंधन क्यू
- GDPR अनुरोध डेस्क (निर्यात/हटाने के टिकट)
- bee_tsdb द्वारा समर्थित डेटा डैशबोर्ड
- i18n शब्द प्रबंधन (चारों क्लाइंट के साझा शब्दों का CRUD)
- गिफ्ट कैटलॉग प्रबंधन (SKU, कीमत, इफ़ेक्ट, बहुभाषी नाम)
- लाइव provider कॉन्फ़िगरेशन (रूटिंग रणनीति, स्विच क्रम)
- निकासी अनुरोध समीक्षा

### 3.5 media (स्व-होस्टेड मीडिया लेयर, Node.js + सिस्टम सेवाएँ)

- `sfu/`: mediasoup; 1v1 कॉल और वॉइस चैट रूम का मीडिया प्लेन संभालता है; केवल मीडिया फ़ॉरवर्डिंग, कोई व्यवसाय तर्क नहीं
- `srs/`: स्व-होस्टेड SRS लाइव स्ट्रीमिंग; RTMP इनजेस्ट → FFmpeg ट्रांसकोडिंग → HTTP-FLV/HLS वितरण
- `coturn/`: TURN रिले, NAT ट्रैवर्सल के लिए फ़ॉलबैक
- सभी सिग्नलिंग फ़ॉरवर्डिंग के लिए service के WS गेटवे का पुनः उपयोग करती है

### 3.6 apps — तीन प्लेटफ़ॉर्म पर समानांतर नेटिव डेवलपमेंट

- साझा OpenAPI अनुबंध; प्रत्येक प्लेटफ़ॉर्म अपना टाइप किया हुआ क्लाइंट जनरेट करता है
- एकीकृत इन्फ्रास्ट्रक्चर मॉड्यूल: नेटवर्किंग लेयर (रिट्राई/ऑथ रिफ्रेश), WS क्लाइंट (IM/दानमाकु/कॉल सिग्नलिंग), i18n (स्थानीय संसाधन + रिमोट इंक्रीमेंटल शब्द), पुश पंजीकरण, थीम
- HarmonyOS नोट्स: Huawei Push Kit, ArkTS कंकरेंसी मॉडल अनुकूलन

## 4. बैकएंड संचार (gRPC)

```
 service (webman/PHP) ──gRPC──▶ infrastructure (bee-rust/tonic)
      │                            ▲
      │ gRPC                        │ gRPC
      ▼                            │
 admin (webman/PHP) ──────gRPC─────┘
   （admin→service：封号/删内容/审核结果回调）
```

| कॉलर → कैली | सामग्री |
|------|------|
| service → infra | फुल-टेक्स्ट खोज, अनुशंसा फ़ीड, टाइमलाइन हॉट कैश, काउंटर रीड/राइट, टाइम-सीरीज़ सांख्यिकी लेखन |
| admin → infra | डैशबोर्ड सांख्यिकी क्वेरी, बैकएंड खोज |
| admin → service | उपयोगकर्ता दंड, कंटेंट हटाना, मॉडरेशन परिणाम वितरण |
| service → admin | रिपोर्ट घटनाएँ, मॉडरेशन कार्य क्यूइंग (एसिंक्रोनस) |

सीमा: तीनों प्लेटफ़ॉर्म ऐप और प्रशासनिक फ्रंटएंड (Flutter) HTTPS REST + WS का उपयोग करते हैं, gRPC को सीधे नहीं छूते।

**संचालन पूर्वापेक्षा**: PHP पक्ष में gRPC के लिए आधिकारिक `grpc` एक्सटेंशन (C एक्सटेंशन) + `grpc/grpc` composer पैकेज आवश्यक है; सर्वर मोड workerman के आधिकारिक walkor/grpc दृष्टिकोण का अनुसरण करता है; तैनाती दस्तावेज़ में इसे स्पष्ट करना होगा।

## 5. बहुभाषी आर्किटेक्चर (तीन परतें)

| परत | दृष्टिकोण |
|----|------|
| **UI परत** | प्रति प्लेटफ़ॉर्म locale संसाधन (zh/en से शुरुआत; प्रणाली किसी भी भाषा का समर्थन करती है); सर्वर केवल त्रुटि कोड + टेम्पलेट key भेजता है |
| **कंटेंट परत** | प्रकाशन पर मूल पाठ संग्रहीत करें + स्वचालित भाषा पहचान `lang` फ़ील्ड में लिखी जाए; पढ़ने पर reader.lang ≠ author.lang → अनुवाद सेवा (LLM/MT provider एब्स्ट्रैक्शन), परिणाम Redis में कैश (bee_cache, TTL), `is_translated` फ़्लैग से मूल पर वापसी; लोकप्रिय कंटेंट निर्धारित रूप से प्री-वार्म |
| **अनुपालन परत** | मॉडरेशन नियम क्षेत्रवार लागू (EU GDPR नियम vs अन्य क्षेत्र); द्विभाषी रिपोर्ट/मॉडरेशन UI |

दानमाकु रियल-टाइम छोटा पाठ है: कोई कंटेंट अनुवाद नहीं, केवल UI i18n + बहुभाषी संवेदनशील-शब्द फ़िल्टरिंग।

## 6. IM आर्किटेक्चर

- **गेटवे**: webman WS गेटवे, बहु-इंस्टेंस + Redis pub/sub क्रॉस-नोड फ़ॉरवर्डिंग, `client_msg_id` आइडेम्पोटेंट डीडुप्लीकेशन
- **डेटा**: conversations / conversation_members / messages / message_reads; 1v1 + ग्रुप चैट (ग्रुप सीमा 500)
- **डिलीवरी**: ऑनलाइन → WS सीधा पुश; ऑफ़लाइन → APNs/FCM/हुआवेई पुश
- **क्षमताएँ**: रीड रसीद, टाइपिंग इंडिकेटर, समय-सीमित रिकॉल, इमेज/वॉइस मैसेज (S3 अपलोड + ट्रांसकोडिंग)
- फ़ीड के साथ उपयोगकर्ता प्रणाली और अधिसूचना प्रणाली साझा करता है

## 7. लाइव स्ट्रीमिंग आर्किटेक्चर (वीडियो + दानमाकु + माइक-लिंक, दोहरा ट्रैक)

### 7.1 Provider एब्स्ट्रैक्शन (service के भीतर)

```
LiveProvider 接口（admin 可配置）
├── provider_3rd   → 第三方直播云（默认主力）：推流/转码/CDN 分发/实时审核
└── provider_self  → 自建 SRS：推流/FFmpeg 转码/自有分发（审核调第三方审核 API）
```

| तंत्र | डिज़ाइन |
|------|------|
| रूटिंग रणनीति | रूम निर्माण पर क्षेत्रवार डिफ़ॉल्ट provider चुना जाता है (admin कॉन्फ़िगरेबल ओवरराइड); बिना तीसरे-पक्ष कवरेज या लागत-संवेदनशील क्षेत्र → स्व-होस्टेड |
| विफलता फ़ेलओवर | प्रसारक SDK दोहरा इनजेस्ट (प्राथमिक = तीसरा पक्ष, बैकअप = स्व-होस्टेड SRS); प्लेयर provider के अनुसार URL हल करते हैं, तीसरे पक्ष की विफलता पर स्वतः स्व-होस्टेड स्ट्रीम पर स्विच |
| दानमाकु/माइक-लिंक | वीडियो पाइपलाइन से डिकपल्ड: दानमाकु service WS से, माइक-लिंक तीसरे-पक्ष RTC से |
| अनुपालन | स्व-होस्टेड पाइपलाइन का रियल-टाइम ऑडियो/वीडियो मॉडरेशन तीसरे-पक्ष मॉडरेशन API पुनः उपयोग करता है (केवल मॉडरेशन खरीदें, परिवहन नहीं) |

### 7.2 लाइव रूम

रूम CRUD, प्रसारण प्रारंभ/समाप्ति स्टेट मशीन, कवर, घोषणाएँ (बहुभाषी), व्यू काउंट (bee_tsdb), दानमाकु रूम चैनल (Redis pub/sub), माइक-लिंक भूमिका प्रबंधन (होस्ट/माइक-लिंक सीटें, service तीसरे-पक्ष RTC टोकन जारी करता है), ऑनलाइन/पीक/अवधि सांख्यिकी → admin डैशबोर्ड।

## 8. वॉइस आर्किटेक्चर (तीन-में-एक)

| रूप | कार्यान्वयन |
|------|------|
| वॉइस मैसेज | IM मैसेज प्रकार विस्तार: S3 संग्रहण + ट्रांसकोडिंग (m4a) + अवधि |
| 1v1 कॉल | WS गेटवे पर सिग्नलिंग (offer/answer/ICE), रिंग/उत्तर/डिस्कनेक्ट स्टेट मशीन (Redis), मीडिया प्लेन mediasoup से, कॉल रिकॉर्ड संग्रहीत |

## 9. वर्चुअल अर्थव्यवस्था (टॉप-अप + गिफ्ट-टिपिंग + निकासी)

```
移动端 IAP（App Store/Google Play/华为）──┐
国内：微信支付 / 支付宝（APP/H5）          ├─▶ PaymentProvider ─▶ 钱包
国外：微信国际 / 支付宝国际 / Stripe / PayPal│    （按 region 选路）
                                          └─▶ payments 支付单（幂等+验签+对账）
   礼物库(admin 上架) ──▶ 打赏：校验余额→扣款→礼物记录→
                         直播间特效事件广播(WS)→主播收入入账(分成)
主播钱包 ──▶ payouts 提现单 ──▶ 国内：商家转账 │ 国外：Stripe Connect/PayPal
```

### 9.1 भुगतान चैनल (घरेलू vs अंतर्राष्ट्रीय)

```
PaymentProvider 接口（admin 配置）
├── 国内（CNY）
│   ├── wechat_cn    微信支付（APP/H5）
│   ├── alipay_cn    支付宝（APP/WAP）
│   └── 提现：商家转账（零钱/银行卡）
├── 国外（USD/EUR/...）
│   ├── wechat_global  微信国际支付（境外商户）
│   ├── alipay_global  支付宝国际（Alipay+）
│   ├── stripe         卡 / Apple Pay / Google Pay / SEPA
│   ├── paypal
│   └── 提现：Stripe Connect / PayPal 批量打款
└── 移动端虚拟币充值：App Store / Google Play / 华为 IAP（商店政策强制，服务端凭证校验）
```

| तंत्र | डिज़ाइन |
|------|------|
| चैनल रूटिंग | उपयोगकर्ता क्षेत्र + मुद्रा + admin व्यापारी नियमों द्वारा चैनल चयन, कॉन्फ़िगरेबल फ़ॉलबैक क्रम (घरेलू/अंतर्राष्ट्रीय स्वाभाविक रूप से विभाजित) |

अनुपालन: मोबाइल वर्चुअल-मुद्रा टॉप-अप स्टोर IAP से होकर जाना चाहिए (Apple/Google/हुआवेई कटौती); WeChat/Alipay का उपयोग H5/Web और विशिष्ट क्षेत्रीय परिदृश्यों के लिए; निकासी में निधि निपटान शामिल है, इसलिए प्लेटफ़ॉर्म उन्हें लाइसेंस प्राप्त चैनलों के स्प्लिट/पेआउट इंटरफ़ेस से संभालता है; चैनल अनुबंध योग्यता M6b से पहले पुष्टि की जाए; नाबालिगों की सीमाएँ अनुपालन चरण में जाती हैं।

## 12. तैनाती और संचालन (वैश्विक बहु-क्षेत्रीय)

- **प्रारंभिक आर्किटेक्चर**: दो प्रमुख क्षेत्र — चीन + विदेश; प्रत्येक क्षेत्र में webman क्लस्टर + bee-rust क्लस्टर + स्थानीय Redis + media (SFU/SRS/TURN); MySQL केंद्रीय प्राथमिक + प्रति-क्षेत्र रीड-ओनली प्रतिकृति; CDN क्षेत्रवार
- **WS निकटतम-क्षेत्र कनेक्शन**, क्रॉस-क्षेत्र संदेश केंद्रीय रूप से समन्वित; पुश क्षेत्रवार संबंधित विक्रेता से
- **विकास पथ**: ट्रैफ़िक वृद्धि के बाद उपयोगकर्ता हैश द्वारा डेटाबेस शार्डिंग
- **निगरानी**: Prometheus मेट्रिक्स (open-admin पैटर्न का अनुसरण), केंद्रीकृत लॉग, अलर्ट (त्रुटि दर/विलंबता/क्यू बैकलॉग/मीडिया सेवा स्वास्थ्य)

## 13. सुरक्षा और अनुपालन

- service open-admin की 18-परत सुरक्षा प्रणाली की प्रतिकृति बनाता है (XSS/SQLi/CSRF/रेट लिमिटिंग/CSP)
- मॉडरेशन पाइपलाइन: प्रकाशन पर बहुभाषी संवेदनशील-शब्द → इमेज/ऑडियो-वीडियो मॉडरेशन (तीसरे-पक्ष API) → मानव मॉडरेशन वर्कबेंच
- GDPR: डेटा निर्यात, समाप्ति/हटाने का अधिकार, लॉग धारण नीति, नाबालिगों के लिए आयु सीमा, क्षेत्रीय नियम अंतर

### 16.4 भर्ती प्राथमिकताएँ

1. बैकएंड PHP ×2 + टेक लीड (नींव अवधि का मूल; बैकएंड सबसे बड़ा कार्यभार क्षेत्र)
2. मोबाइल ×3 (तीन प्लेटफ़ॉर्म समानांतरता कुल समयसीमा की कठिन बाधा है — जितना जल्दी, उतना बेहतर)
3. UI/UX, QA
4. Rust, DevOps (M1–M2 से पहले प्रवेश)
5. ऑडियो/वीडियो (M3 के अंत)
6. भुगतान/अनुपालन सलाहकार, स्थानीयकरण (M6/M7 में आवश्यकतानुसार)

### 16.5 जोखिम और फ़ॉलबैक

- ऑडियो/वीडियो और भुगतान चैनल दो सबसे कठिन-भर्ती भूमिकाएँ हैं (विशेषज्ञ दुर्लभ); आउटसोर्सिंग/सलाहकार फ़ॉलबैक योजनाएँ रखें
- यदि HarmonyOS इंजीनियर मिलना कठिन है, तो Android इंजीनियर पहले संभाल सकता है (ArkTS TS के साथ समान जड़ें साझा करता है और जल्दी सीखा जा सकता है); तीन प्लेटफ़ॉर्म समानांतर गति प्रभावित नहीं होती
