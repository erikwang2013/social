# Общий дизайн социальной платформы (Social Platform Design)

## 1. Цели и охват

Построить социальную платформу, сочетающую короткий контент (изображения+текст) и IM, с трансляциями (видео + данмаку + совместный эфир), голосом (сообщения / звонки 1v1 / голосовые комнаты) и виртуальной экономикой с донатами-подарками. Поддержка мультиязычного UI, перевода контента и регионального комплаенса, развёртывание в нескольких регионах мира. Параллельная нативная разработка на трёх платформах: iOS / Android / HarmonyOS.

## 3. Обязанности подсистем

### 3.1 contracts (gRPC-контракты, новый корневой каталог)

```
contracts/
├── buf.yaml                      # buf 配置（唯一生成入口）
├── common/types.proto            # 分页、错误、时间戳、区域枚举等公共类型
├── infra/infra_service.proto     # infrastructure 对外服务
├── user/user_service.proto       # service 对外服务（admin 调用用）
└── admin/admin_service.proto     # admin 对外服务（service/infra 调用用）
```

- Конвейер генерации: CI генерирует buf'ом три вида стабов и коммитит их в соответствующие подрепозитории (сборка не зависит от сети)
  - service/, admin/ → стабы PHP (grpc/grpc + google/protobuf)
  - infrastructure/ → стабы Rust (tonic)
- Правило версионирования: только добавление полей, без изменения и удаления; имя пакета несёт major-версию (`social.user.v1`)

### 3.2 service (webman v2) — пользовательский бизнес-монолит

- **API-домены**: auth (JWT двойные токены + блэклист), profile, posts, likes, comments, follows, IM (диалоги/сообщения/WS-шлюз), notifications, планирование перевода, сигнализация комнат/данмаку/совместного эфира, сигнализация звонков/голосовых комнат, виртуальная экономика (кошелёк/подарки/проверка IAP/разделение дохода), GDPR-экспорт/удаление
- **Мультиязычная система ошибок**: ошибки возвращают `{code, lang_key, params}`, тексты рендерит клиент по locale
- **Очереди** (redis-queue): триггеры модерации, планирование перевода, доставка пушей, асинхронная статистика, рассылка эффектов подарков
- **Планировщик** (webman-crontab): предпрогрев переводов, очистка просроченных токенов/сообщений, архивирование аудита, расчёты по разделению дохода
- **ID**: `erikwang2013/snowflake-php` (как в admin)
- **Контракты**: автоэкспорт OpenAPI 3.0 → генерация типизированных клиентов для трёх платформ

### 3.3 infrastructure (bee-rust) — вычислительный слой высокой пропускной способности

Не хранит бизнес-основные данные (MySQL — единственный источник истины), берёт на себя вычислительно/запросно-тяжёлые функции:

- `bee_search`: полнотекстовый поиск по постам/пользователям (китайская сегментация слов, мультиязычная индексация)
- `bee_graph`: социальный граф → рекомендательная лента
- `bee_tsdb`: временные ряды: DAU, посты, взаимодействия, просмотры трансляций, длительность звонков и т.д.
- `bee_cache/bee_kv`: кэш таймлайнов, счётчики (лайки, просмотры, онлайн-пользователи)
- Развёртывается по регионам, чтения много/записи мало, данные реплицируются из центра

### 3.4 admin (доработка open-admin)

**Переиспользуется**: JWT/RBAC/аудит/управление файлами/health check/инфраструктура i18n (кит./англ.)

**Новое**:
- Рабочее место модерации контента: двуязычная построчная проверка постов/комментариев/изображений, мультиязычные шаблоны причин отклонения, наказания пользователей
- Очередь обработки жалоб
- Стол запросов GDPR (тикеты на экспорт/удаление)
- Дашборды данных на базе bee_tsdb
- Управление терминами i18n (CRUD терминов, общих для четырёх клиентов)
- Управление каталогом подарков (SKU, цены, эффекты, мультиязычные названия)
- Конфигурация провайдеров трансляций (стратегия маршрутизации, порядок переключения)
- Проверка заявок на вывод средств

### 3.5 media (собственный медиаслой, Node.js + системные сервисы)

- `sfu/`: mediasoup, несёт медиаплоскость звонков 1v1 и голосовых комнат; только медиа-ретрансляция, без бизнес-логики
- `srs/`: собственный SRS для трансляций: RTMP-вход → транскодинг FFmpeg → доставка HTTP-FLV/HLS
- `coturn/`: TURN-ретранслятор, фолбэк для прохождения NAT
- Вся сигнализация переиспользует WS-шлюз service для пересылки

### 3.6 apps — параллельная нативная разработка на трёх платформах

- Общий OpenAPI-контракт, каждая платформа генерирует собственный типизированный клиент
- Унифицированные инфраструктурные модули: сетевой слой (ретраи/обновление авторизации), WS-клиент (сигнализация IM/данмаку/звонков), i18n (локальные ресурсы + удалённые инкрементальные термины), регистрация пушей, темы
- Заметки по HarmonyOS: Huawei Push Kit, адаптация модели конкурентности ArkTS

## 4. Взаимодействие бэкендов (gRPC)

```
 service (webman/PHP) ──gRPC──▶ infrastructure (bee-rust/tonic)
      │                            ▲
      │ gRPC                        │ gRPC
      ▼                            │
 admin (webman/PHP) ──────gRPC─────┘
   （admin→service：封号/删内容/审核结果回调）
```

| Вызывающий → Вызываемый | Содержимое |
|------|------|
| service → infra | полнотекстовый поиск, рекомендательная лента, горячий кэш таймлайна, чтение/запись счётчиков, запись временных рядов |
| admin → infra | запросы статистики для дашбордов, поиск по бэкенду |
| admin → service | наказания пользователей, удаление контента, выдача результатов модерации |
| service → admin | события жалоб, постановка задач модерации в очередь (асинхронно) |

Граница: приложения трёх платформ и фронтенд админки (Flutter) работают по HTTPS REST + WS и не касаются gRPC напрямую.

**Операционная предпосылка**: gRPC на стороне PHP требует официального расширения `grpc` (C-расширение) + composer-пакета `grpc/grpc`; серверный режим — по официальной схеме workerman walkor/grpc; это нужно чётко описать в документации по развёртыванию.

## 5. Мультиязычная архитектура (три слоя)

| Слой | Подход |
|----|------|
| **UI-слой** | locale-ресурсы на каждой платформе (старт с zh/en, система поддерживает любые языки); сервер шлёт только коды ошибок + ключи шаблонов |
| **Слой контента** | при публикации хранится оригинал + автодетект языка в поле `lang`; при чтении reader.lang ≠ author.lang → сервис перевода (абстракция LLM/MT-провайдера), результат кэшируется в Redis (bee_cache, TTL), флаг `is_translated` позволяет вернуть оригинал; популярный контент предпрогревается по расписанию |
| **Слой комплаенса** | правила модерации действуют по регионам (правила GDPR ЕС vs другие регионы); двуязычный UI жалоб/модерации |

Данмаку — это реальновременный короткий текст: перевод контента не делается, только i18n UI + мультиязычная фильтрация чувствительных слов.

## 6. Архитектура IM

- **Шлюз**: webman WS-шлюз, несколько инстансов + межнодовая пересылка через Redis pub/sub, идемпотентная дедупликация по `client_msg_id`
- **Данные**: conversations / conversation_members / messages / message_reads; личные + групповые чаты (лимит группы 500)
- **Доставка**: онлайн → прямой пуш по WS; офлайн → APNs/FCM/Huawei-пуши
- **Возможности**: подтверждение прочтения, индикатор набора, отзыв сообщения с ограничением по времени, изображения/голосовые сообщения (загрузка в S3 + транскодинг)
- Общая с лентой система пользователей и уведомлений

## 7. Архитектура трансляций (видео + данмаку + совместный эфир, два трека)

### 7.1 Абстракция провайдера (внутри service)

```
LiveProvider 接口（admin 可配置）
├── provider_3rd   → 第三方直播云（默认主力）：推流/转码/CDN 分发/实时审核
└── provider_self  → 自建 SRS：推流/FFmpeg 转码/自有分发（审核调第三方审核 API）
```

| Механизм | Дизайн |
|------|------|
| Стратегия маршрутизации | при создании комнаты выбирается провайдер по умолчанию для региона (admin может переопределить); регионы без стороннего покрытия или чувствительные к стоимости → свой SRS |
| Отказоустойчивость | двойная отдача с SDK стримера (основная = сторонняя, резервная = свой SRS); плеер резолвит URL по провайдеру, при сбое стороннего автоматически переключается на свой поток |
| Данмаку/совместный эфир | развязаны с видеотрактой: данмаку идёт через WS service, совместный эфир — через сторонний RTC |
| Комплаенс | реальновременная аудио/видео-модерация собственного тракта переиспользует сторонние API модерации (покупаем только модерацию, не хостинг) |

### 7.2 Комнаты трансляций

CRUD комнат, state machine начала/конца эфира, обложка, объявления (мультиязычные), счётчики просмотров (bee_tsdb), каналы данмаку комнат (Redis pub/sub), управление ролями совместного эфира (ведущий/слоты, service выдаёт сторонние RTC-токены), статистика онлайн/пик/длительность → дашборды admin.

## 8. Архитектура голоса (комплект из трёх)

| Форма | Реализация |
|------|------|
| Голосовые сообщения | расширение типа IM-сообщения: хранение в S3 + транскодинг (m4a) + длительность |
| Звонки 1v1 | сигнализация через WS-шлюз (offer/answer/ICE), state machine звонок/приём/завершение (Redis), медиаплоскость через mediasoup, записи звонков в БД |
| Голосовые комнаты | управление комнатами переиспользует паттерн комнат трансляций, состояния микрофона/слушателей ведёт service, медиаплоскость через mediasoup |

## 9. Виртуальная экономика (пополнение + подарки + вывод средств)

```
移动端 IAP（App Store/Google Play/华为）──┐
国内：微信支付 / 支付宝（APP/H5）          ├─▶ PaymentProvider ─▶ 钱包
国外：微信国际 / 支付宝国际 / Stripe / PayPal│    （按 region 选路）
                                          └─▶ payments 支付单（幂等+验签+对账）
   礼物库(admin 上架) ──▶ 打赏：校验余额→扣款→礼物记录→
                         直播间特效事件广播(WS)→主播收入入账(分成)
主播钱包 ──▶ payouts 提现单 ──▶ 国内：商家转账 │ 国外：Stripe Connect/PayPal
```

### 9.1 Платёжные каналы (внутренние и зарубежные)

```
PaymentProvider 接口（admin 配置）
├── 国内（CNY）
│   ├── wechat_cn    微信支付（APP/H5）
│   ├── alipay_cn    支付宝（APP/WAP）
│   └── 提现：商家转账（零钱/银行卡）
├── 国外（USD/EUR/...）
│   ├── wechat_global  微信国际支付（境外商户）
│   ├── alipay_global  支付宝国际（Alipay+）
│   ├── stripe         卡 / Apple Pay / Google Pay / SEPA
│   ├── paypal
│   └── 提现：Stripe Connect / PayPal 批量打款
└── 移动端虚拟币充值：App Store / Google Play / 华为 IAP（商店政策强制，服务端凭证校验）
```

| Механизм | Дизайн |
|------|------|
| Маршрутизация каналов | выбор канала по региону пользователя + валюте + правилам мерчантов admin, настраиваемый порядок фолбэка (естественное разделение внутренних/зарубежных) |
| Платёжный ордер | унифицированная модель payments: пользователь/канал/сумма/валюта/state machine, идемпотентность по всем каналам |
| Колбэки | единая обёртка проверки подписи (RSA/HMAC), идемпотентные колбэки, ежедневная сверка (по выпискам каналов) |
| Вывод средств | ордера payouts: внутренние — перевод мерчанта, зарубежные — Stripe Connect/PayPal; режим расщепления/агентской выплаты по возможностям канала |
| Ценообразование | региональные ценовые таблицы (admin): виртуальная валюта × цены в валютах, централизованное управление курсами |
| Риск-контроль | лимиты/частотные ограничения/алерты по аномальным ордерам, полный аудит операций (переиспользует систему аудита) |
| SKU подарков | каталог подарков (цены, идентификаторы эффектов, мультиязычные названия) ведёт admin |

Комплаенс: пополнение виртуальной валюты на мобильных обязательно через IAP магазинов (комиссия Apple/Google/Huawei); WeChat/Alipay — для H5/Web и региональных сценариев; вывод средств связан с расчётами по средствам, поэтому платформа реализует его через интерфейсы расщепления/агентской выплаты лицензированных каналов; квалификация для договоров с каналами подтверждается до M6b; лимиты для несовершеннолетних — на этапе комплаенса.

## 10. Ключевые модели данных

- Пользователи: users, user_profiles (мультиязычные поля)
- Соцчасть: follows, posts, post_translations, comments, comment_translations, likes, reports
- IM: conversations, conversation_members, messages, message_reads
- Трансляции: live_rooms, live_streams (с провайдером), danmaku_archive
- Голос: call_records, voice_rooms, voice_room_members
- Виртуальная экономика: wallets, currency_transactions, gift_catalog, gifts_given, streamer_earnings, withdrawals, payments, payouts, price_plans (региональные цены/курсы), merchant_configs (конфигурации мерчантов каналов), products (SKU IAP)
- Платформа: i18n_terms (термины для четырёх клиентов), moderation_queue, provider_configs, audit_logs

## 11. Выбор баз данных и хранилищ

| Назначение | Хранилище | Компонент |
|------|------|----------|
| Бизнес-основные данные (пользователи/посты/IM/кошелёк/модерация/жалобы) | MySQL 8 (центральный мастер + региональные read-only реплики) | общая для service и admin, единственный источник истины |
| Горячие данные/сессии/онлайн-статусы/счётчики/каналы данмаку/state machine звонков | Redis 7 | bee_kv / bee_cache (фича redis) |
| Полнотекстовый поиск (посты/пользователи, поиск по админке) | OpenSearch (старт на одном узле) | bee_search (фича opensearch) |
| Временные ряды (DAU/тренды/просмотры трансляций/длительность звонков/дашборды) | QuestDB (старт с одного бинарника) | bee_tsdb (фича questdb, заменяемо на influxdb) |
| Социальный граф → рекомендательная лента | Neo4j Community (старт на одном узле) | bee_graph (фича neo4j, заменяемо на nebulagraph) |
| Объектные файлы (изображения/видео/голос/экспорт-пакеты) | S3 (MinIO или облако) | прямое подключение service + доставка через CDN |
| Журналы аудита | MySQL audit_logs, по истечении архивация в объектное хранилище | переиспользует систему аудита admin |

Принципы выбора: компоненты bee-rust — абстракции с фича-флагами: старт на одном узле, с ростом масштабов замена на распределённые бэкенды, без привязки; MySQL всегда единственный источник истины; вычислительный слой (индексы/статистика/граф/кэш) хранит только восстанавливаемые производные данные. Фронтенд админки (Flutter) не касается БД напрямую — всё через бэкенд admin.

## 12. Развёртывание и эксплуатация (глобальная многозональность)

- **Стартовая архитектура**: два крупных региона — Китай + зарубежье; в каждом регионе кластер webman + кластер bee-rust + локальный Redis + media (SFU/SRS/TURN); центральный мастер MySQL + read-only реплики в каждом регионе; CDN по регионам
- **Ближайшая точка входа WS**, межрегиональные сообщения координируются централизованно; пуши идут через соответствующего провайдера по регионам
- **Путь эволюции**: после роста трафика шардирование БД по хешу пользователя
- **Мониторинг**: Prometheus metrics (по паттерну open-admin), централизованные логи, алерты (ошибки/задержки/переполнение очередей/здоровье медиасервисов)

## 13. Безопасность и комплаенс

- service воспроизводит 18-уровневую модель защиты open-admin (XSS/SQLi/CSRF/лимитирование/CSP)
- Конвейер модерации: мультиязычный фильтр чувствительных слов при публикации → модерация изображений/аудио-видео (сторонние API) → ручная модерация
- GDPR: экспорт данных, право на удаление/стирание, политика хранения логов, возрастной порог для несовершеннолетних, дифференциация правил по регионам

### 16.4 Приоритеты найма

1. Бэкенд PHP ×2 + техлид (ядро периода фундамента; бэкенд — самый большой объём работ)
2. Мобильные ×3 (параллельность трёх платформ — жёсткое ограничение общего срока, чем раньше, тем лучше)
3. UI/UX, QA
4. Rust, DevOps (до M1–M2)
5. Аудио/видео (конец M3)
6. Платёжный/комплаенс-консультанты, локализация (по потребности на M6/M7)

### 16.5 Риски и подстраховка

- Аудио/видео и платёжные каналы — две самые труднонанимаемые роли (дефицит экспертов); заложить фолбэк через аутсорс/консультантов
- Если HarmonyOS-инженера трудно нанять, сначала его может закрыть Android-инженер (ArkTS одного корня с TS, осваивается быстро); ритм параллельной разработки трёх платформ не страдает
