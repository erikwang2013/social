# التصميم الشامل للمنصة الاجتماعية (Social Platform Design)

**语言 / Languages:** [中文](2026-08-16-social-platform-design.md) · [English](2026-08-16-social-platform-design.en.md) · [한국어](2026-08-16-social-platform-design.ko.md) · [Русский](2026-08-16-social-platform-design.ru.md) · [Deutsch](2026-08-16-social-platform-design.de.md) · [Français](2026-08-16-social-platform-design.fr.md) · [Español](2026-08-16-social-platform-design.es.md) · [Português](2026-08-16-social-platform-design.pt.md) · [हिन्दी](2026-08-16-social-platform-design.hi.md) · [العربية](2026-08-16-social-platform-design.ar.md) · [বাংলা](2026-08-16-social-platform-design.bn.md) · [Bahasa Indonesia](2026-08-16-social-platform-design.id.md) · [日本語](2026-08-16-social-platform-design.ja.md)

- الحالة: مؤكَّد، بانتظار التنفيذ
- النطاق: مجتمع محتوى قصير (صورة+نص) + مراسلة فورية + بث مباشر/صوت + اقتصاد افتراضي، متعدد اللغات، متعدد المناطق عالميًا

## 1. الأهداف والنطاق

بناء منصة اجتماعية تجمع بين المحتوى القصير (صورة+نص) والمراسلة الفورية، مع بث مباشر (فيديو + دانماكو + مشاركة الميكروفون)، وصوت (رسائل / مكالمات 1v1 / غرف دردشة صوتية)، واقتصاد افتراضي للإكراميات والهدايا. دعم تعدد لغات الواجهة، وترجمة المحتوى، والامتثال متعدد المناطق، مع نشر في مناطق متعددة حول العالم. تطوير أصلي متوازٍ على ثلاث منصات: iOS / Android / HarmonyOS.

## 2. نظرة عامة على النظام

```
                    ┌─────────────────────────────────────────────┐
                    │   iOS (SwiftUI) │ Android (Kotlin+Compose)  │
                    │            HarmonyOS (ArkTS)                │
                    └───────┬─────────────────────────┬───────────┘
                            │  HTTPS / WSS（多区域就近接入）
                  ┌─────────▼──────────┐   ┌──────────────────────┐
                  │  CDN + 区域接入层   │   │ 厂商推送 APNs/FCM/华为 │
                  └─────────┬──────────┘   └──────────────────────┘
              ┌─────────────▼─────────────┐
              │   service (webman v2)     │──gRPC──▶ infrastructure
              │  业务单体：认证/资料/动态/ │          (bee-rust)
              │  点赞/评论/关注/IM 网关/   │  gRPC      搜索/推荐/图/
              │  翻译调度/审核/直播/语音/  │  ▲        时序/热数据
              │  虚拟经济                 │  │ gRPC
              └─────────────┬─────────────┘  │
                  ┌─────────▼─────────┐      │
                  │ MySQL + Redis     │      │
                  │ S3 对象存储       │      │
                  └───────────────────┘      │
              ┌──────────────────────────────┴──┐
              │   admin (open-admin 改造, webman) │
              │  审核台/举报/GDPR/看板/词条/礼物库/ │
              │  直播配置/提现审核                 │
              └──────────────────────────────────┘

  media/（自建媒体层，信令走 service WS 网关）
  ├── sfu/    mediasoup：1v1 通话、语聊房
  ├── srs/    SRS：自建直播（RTMP → FFmpeg 转码 → FLV/HLS）
  └── coturn/ TURN 中继

  外部：第三方直播云（推流/转码/CDN/实时审核）、第三方 RTC（连麦）、
        第三方审核 API、商店 IAP（App Store / Google Play / 华为）
```

## 3. مسؤوليات الأنظمة الفرعية

### 3.1 contracts (عقود gRPC، دليل جذر جديد)

```
contracts/
├── buf.yaml                      # buf 配置（唯一生成入口）
├── common/types.proto            # 分页、错误、时间戳、区域枚举等公共类型
├── infra/infra_service.proto     # infrastructure 对外服务
├── user/user_service.proto       # service 对外服务（admin 调用用）
└── admin/admin_service.proto     # admin 对外服务（service/infra 调用用）
```

- خط الإنتاج: تولّد CI ثلاثة أنواع من الكعوب (stubs) عبر buf وتُرسل إلى المستودعات الفرعية المعنية (البناء لا يعتمد على الشبكة)
  - service/, admin/ → كعوب PHP (grpc/grpc + google/protobuf)
  - infrastructure/ → كعوب Rust (tonic)
- قاعدة الإصدارات: إضافة الحقول فقط، لا تعديل ولا حذف؛ اسم الحزمة يحمل الإصدار الرئيسي (`social.user.v1`)

### 3.2 service (webman v2) — كتلة الأعمال أحادية الجانب الخاصة بالمستخدم

- **مجالات API**: auth (JWT رمزان + قائمة سوداء)، profile، posts، likes، comments، follows، IM (المحادثات/الرسائل/بوابة WS)، notifications، جدولة الترجمة، إشارات غرف البث/الدانماكو/مشاركة الميكروفون، إشارات المكالمات الصوتية/غرف الدردشة الصوتية، الاقتصاد الافتراضي (المحفظة/الهدايا/التحقق من IAP/تقاسم الإيرادات)، تصدير/حذف GDPR
- **نظام أخطاء متعدد اللغات**: تُرجع الأخطاء `{code, lang_key, params}`؛ تُعرض النصوص من جهة العميل حسب الإعداد المحلي
- **الطوابير** (redis-queue): محفزات المراجعة، جدولة الترجمة، تسليم الإشعارات، إحصاءات غير متزامنة، بث تأثيرات الهدايا
- **المهام المجدولة** (webman-crontab): التسخين المسبق للترجمات، تنظيف الرموز/الرسائل منتهية الصلاحية، أرشفة التدقيق، تسوية تقاسم الإيرادات
- **المعرّفات**: `erikwang2013/snowflake-php` (مطابق لـ admin)
- **العقود**: تصدير تلقائي لـ OpenAPI 3.0 → توليد عملاء مكتوبين بالأنواع للمنصات الثلاث

### 3.3 infrastructure (bee-rust) — طبقة الحوسبة عالية الإنتاجية

لا تخزن بيانات الأعمال الأساسية (MySQL هو مصدر الحقيقة الوحيد)؛ تتولى القدرات الثقيلة حسابًا/استعلامًا:

- `bee_search`: بحث نص كامل في المنشورات/المستخدمين (تقسيم الكلمات الصينية، فهرسة متعددة اللغات)
- `bee_graph`: الرسم البياني الاجتماعي → خلاصة التوصيات
- `bee_tsdb`: إحصاءات السلاسل الزمنية: DAU، النشر، التفاعلات، مشاهدات البث، مدة المكالمات الصوتية، إلخ
- `bee_cache/bee_kv`: ذاكرة تخزين مؤقت للخط الزمني، عدادات (الإعجابات، المشاهدات، المستخدمون المتصلون)
- يُنشر حسب المنطقة؛ قراءات كثيرة وكتابات قليلة، تُنسخ البيانات من المركز

### 3.4 admin (إعادة بناء open-admin)

**يُعاد استخدامه**: البنية التحتية JWT/RBAC/التدقيق/إدارة الملفات/فحوصات الصحة/i18n (صيني/إنجليزي)

**جديد**:
- منصة مراجعة المحتوى: مراجعة ثنائية اللغة جنبًا إلى جنب للمنشورات/التعليقات/الصور، قوالب متعددة اللغات لأسباب الرفض، عقوبات للمستخدمين
- طابور معالجة البلاغات
- مكتب طلبات GDPR (تذاكر تصدير/حذف)
- لوحات بيانات تعتمد على bee_tsdb
- إدارة المصطلحات i18n (CRUD للمصطلحات المشتركة بين العملاء الأربعة)
- إدارة كتالوج الهدايا (SKU، الأسعار، التأثيرات، الأسماء متعددة اللغات)
- إعداد مزودي البث (استراتيجية التوجيه، ترتيب التبديل)
- مراجعة طلبات السحب

### 3.5 media (طبقة الوسائط ذاتية الاستضافة، Node.js + خدمات نظام)

- `sfu/`: mediasoup؛ يحمل مستوى الوسائط لمكالمات 1v1 وغرف الدردشة الصوتية؛ إعادة توجيه وسائط فقط، بلا منطق أعمال
- `srs/`: SRS ذاتي الاستضافة للبث؛ إدخال RTMP → ترميز FFmpeg → توزيع HTTP-FLV/HLS
- `coturn/`: مرحّل TURN، احتياط لاختراق NAT
- كل الإشارات تمر عبر بوابة WS الخاصة بـ service

### 3.6 apps — تطوير أصلي متوازٍ على ثلاث منصات

- عقد OpenAPI مشترك؛ كل منصة تولّد عميلها المكتوب بالأنواع
- وحدات بنية موحدة: طبقة الشبكات (إعادة المحاولة/تحديث المصادقة)، عميل WS (إشارات IM/الدانماكو/المكالمات)، i18n (موارد محلية + مصطلحات بعيدة تدريجية)، تسجيل الإشعارات، السمات
- ملاحظات HarmonyOS: Huawei Push Kit، التكيف مع نموذج التزامن في ArkTS

## 4. اتصال الخوادم الخلفية (gRPC)

```
 service (webman/PHP) ──gRPC──▶ infrastructure (bee-rust/tonic)
      │                            ▲
      │ gRPC                        │ gRPC
      ▼                            │
 admin (webman/PHP) ──────gRPC─────┘
   （admin→service：封号/删内容/审核结果回调）
```

| المتصل ← المُتصل به | المحتوى |
|------|------|
| service ← infra | بحث نص كامل، خلاصة توصيات، ذاكرة تخزين مؤقت ساخنة للخط الزمني، قراءة/كتابة عدادات، كتابة إحصاءات السلاسل الزمنية |
| admin ← infra | استعلامات إحصاءات اللوحات، بحث خلفي |
| admin ← service | عقوبات المستخدمين، حذف المحتوى، تسليم نتائج المراجعة |
| service ← admin | أحداث البلاغات، إدراج مهام المراجعة في الطابور (غير متزامن) |

الحدود: تطبيقات المنصات الثلاث وواجهة الإدارة الأمامية (Flutter) تستخدم HTTPS REST + WS ولا تلمس gRPC مباشرة.

**متطلب تشغيلي**: يتطلب gRPC في جانب PHP الامتداد الرسمي `grpc` (امتداد C) + حزمة composer `grpc/grpc`؛ وضع الخادم يتبع نهج walkor/grpc الرسمي من workerman؛ يجب توضيح ذلك في وثائق النشر.

## 5. البنية متعددة اللغات (ثلاث طبقات)

| الطبقة | النهج |
|----|------|
| **طبقة الواجهة** | موارد إعدادات محلية لكل منصة (البداية zh/en؛ النظام يدعم أي لغة)؛ يرسل الخادم رموز الأخطاء + مفاتيح القوالب فقط |
| **طبقة المحتوى** | عند النشر، تخزين النص الأصلي + كشف اللغة تلقائيًا في الحقل `lang`؛ عند القراءة، reader.lang ≠ author.lang ← خدمة الترجمة (تجريد مزود LLM/MT)، تُخزن النتائج مؤقتًا في Redis (bee_cache، TTL)، مع علامة `is_translated` للعودة إلى الأصل؛ تسخين مسبق مجدول للمحتوى الشائع |
| **طبقة الامتثال** | تطبق قواعد المراجعة حسب المنطقة (قواعد GDPR الأوروبية مقابل المناطق الأخرى)؛ واجهة بلاغات/مراجعة ثنائية اللغة |

الدانماكو نص قصير فوري: لا ترجمة للمحتوى، فقط i18n للواجهة + تصفية متعددة اللغات للكلمات الحساسة.

## 6. بنية IM

- **البوابة**: بوابة WS من webman، متعددة المثيلات مع إعادة توجيه بين العقد عبر Redis pub/sub، إزالة تكرارات حتمية (idempotent) عبر `client_msg_id`
- **البيانات**: conversations / conversation_members / messages / message_reads؛ محادثات خاصة + جماعية (حد المجموعة 500)
- **التسليم**: متصل ← دفع مباشر عبر WS؛ غير متصل ← دفع APNs/FCM/Huawei
- **القدرات**: إيصالات القراءة، مؤشر الكتابة، سحب محدود زمنيًا، رسائل الصور/الصوت (رفع S3 + ترميز)
- يتشارك نظام المستخدمين ونظام الإشعارات مع الخلاصة

## 7. بنية البث المباشر (فيديو + دانماكو + مشاركة الميكروفون، مسار مزدوج)

### 7.1 تجريد المزود (داخل service)

```
LiveProvider 接口（admin 可配置）
├── provider_3rd   → 第三方直播云（默认主力）：推流/转码/CDN 分发/实时审核
└── provider_self  → 自建 SRS：推流/FFmpeg 转码/自有分发（审核调第三方审核 API）
```

| الآلية | التصميم |
|------|------|
| استراتيجية التوجيه | مزود افتراضي حسب المنطقة عند إنشاء الغرفة (يمكن لـ admin تجاوزه)؛ المناطق بلا تغطية طرف ثالث أو الحساسة للتكلفة ← ذاتي الاستضافة |
| تحمّل الأعطال | إدخال مزدوج عبر SDK المذيع (أساسي = طرف ثالث، احتياطي = SRS ذاتي)؛ يحل اللاعبون عنوان URL حسب المزود وينتقلون تلقائيًا إلى البث الذاتي عند تعطل الطرف الثالث |
| الدانماكو/مشاركة الميكروفون | منفصلان عن خط الفيديو: الدانماكو عبر WS الخاص بـ service، ومشاركة الميكروفون عبر RTC الطرف الثالث |
| الامتثال | مراجعة الصوت/الفيديو الفورية في الخط الذاتي تستخدم واجهات مراجعة الطرف الثالث (نشتري المراجعة فقط، لا الاستضافة) |

### 7.2 غرف البث

CRUD للغرف، آلة حالات بدء/إيقاف البث، الغلاف، الإعلانات (متعددة اللغات)، عدادات المشاهدة (bee_tsdb)، قنوات الدانماكو للغرف (Redis pub/sub)، إدارة أدوار مشاركة الميكروفون (المضيف/المقاعد، يصدر service رموز RTC الطرف الثالث)، إحصاءات الاتصال/الذروة/المدة ← لوحات admin.

## 8. بنية الصوت (ثلاثية)

| الشكل | التنفيذ |
|------|------|
| الرسائل الصوتية | توسيع نوع رسالة IM: تخزين S3 + ترميز (m4a) + المدة |
| مكالمات 1v1 | الإشارات عبر بوابة WS (offer/answer/ICE)، آلة حالات الرنين/الرد/الإنهاء (Redis)، مستوى الوسائط عبر mediasoup، سجلات المكالمات في قاعدة البيانات |
| غرف الدردشة الصوتية | إدارة الغرف تعيد استخدام نمط غرف البث؛ حالات الميكروفون/المستمعين يديرها service؛ مستوى الوسائط عبر mediasoup |

## 9. الاقتصاد الافتراضي (شحن + إكراميات هدايا + سحب)

```
移动端 IAP（App Store/Google Play/华为）──┐
国内：微信支付 / 支付宝（APP/H5）          ├─▶ PaymentProvider ─▶ 钱包
国外：微信国际 / 支付宝国际 / Stripe / PayPal│    （按 region 选路）
                                          └─▶ payments 支付单（幂等+验签+对账）
   礼物库(admin 上架) ──▶ 打赏：校验余额→扣款→礼物记录→
                         直播间特效事件广播(WS)→主播收入入账(分成)
主播钱包 ──▶ payouts 提现单 ──▶ 国内：商家转账 │ 国外：Stripe Connect/PayPal
```

### 9.1 قنوات الدفع (محلية مقابل دولية)

```
PaymentProvider 接口（admin 配置）
├── 国内（CNY）
│   ├── wechat_cn    微信支付（APP/H5）
│   ├── alipay_cn    支付宝（APP/WAP）
│   └── 提现：商家转账（零钱/银行卡）
├── 国外（USD/EUR/...）
│   ├── wechat_global  微信国际支付（境外商户）
│   ├── alipay_global  支付宝国际（Alipay+）
│   ├── stripe         卡 / Apple Pay / Google Pay / SEPA
│   ├── paypal
│   └── 提现：Stripe Connect / PayPal 批量打款
└── 移动端虚拟币充值：App Store / Google Play / 华为 IAP（商店政策强制，服务端凭证校验）
```

| الآلية | التصميم |
|------|------|
| توجيه القنوات | اختيار القناة حسب منطقة المستخدم + العملة + قواعد التاجر في admin، مع ترتيب احتياطي قابل للضبط (فصل طبيعي محلي/دولي) |
| أمر الدفع | نموذج payments موحد: المستخدم/القناة/المبلغ/العملة/آلة الحالات، حتمي عبر جميع القنوات |
| عمليات الاستدعاء | غلاف موحد للتحقق من التوقيع (RSA/HMAC)، عمليات استدعاء حتمية، مهمة مطابقة يومية (التحقق من كشوفات القنوات) |
| السحب | أوامر payouts: تحويل تاجر محلي، دفع دولي Stripe Connect/PayPal؛ وضع التقسيم/الدفع حسب قدرة القناة |
| التسعير | جداول أسعار إقليمية (admin): العملة الافتراضية × أسعار العملات، إدارة مركزية لأسعار الصرف |
| التحكم بالمخاطر | حدود/تقييدات تردد/تنبيهات للأوامر الشاذة، تدقيق كامل للتدفقات (يعيد استخدام نظام التدقيق) |
| SKU الهدايا | كتالوج الهدايا (الأسعار، معرّفات التأثيرات، الأسماء متعددة اللغات) يديره admin |

الامتثال: يجب أن يمر شحن العملة الافتراضية على الجوال عبر IAP المتاجر (عمولة Apple/Google/Huawei)؛ يُستخدم WeChat/Alipay لـ H5/Web وسيناريوهات إقليمية محددة؛ السحب يتعلق بتسوية الأموال، لذا تنفذه المنصة عبر واجهات التقسيم/الدفع لقنوات مرخصة؛ تُثبت أهلية العقود مع القنوات قبل M6b؛ حدود القاصرين تدخل مرحلة الامتثال.

## 10. نماذج البيانات الأساسية

- المستخدمون: users, user_profiles (حقول متعددة اللغات)
- الاجتماعي: follows, posts, post_translations, comments, comment_translations, likes, reports
- IM: conversations, conversation_members, messages, message_reads
- البث: live_rooms, live_streams (مع المزود), danmaku_archive
- الصوت: call_records, voice_rooms, voice_room_members
- الاقتصاد الافتراضي: wallets, currency_transactions, gift_catalog, gifts_given, streamer_earnings, withdrawals, payments, payouts, price_plans (أسعار إقليمية/أسعار صرف), merchant_configs (إعدادات تاجر القنوات), products (SKU IAP)
- المنصة: i18n_terms (مصطلحات مشتركة بين العملاء الأربعة), moderation_queue, provider_configs, audit_logs

## 11. اختيار قواعد البيانات والتخزين

| الغرض | التخزين | المكوّن |
|------|------|----------|
| بيانات الأعمال الأساسية (المستخدمون/المنشورات/IM/المحفظة/المراجعة/البلاغات) | MySQL 8 (أساسي مركزي + نسخ للقراءة فقط إقليمية) | مشترك بين service وadmin؛ مصدر الحقيقة الوحيد |
| البيانات الساخنة/الجلسات/حالات الاتصال/العدادات/قنوات الدانماكو/آلات حالات المكالمات | Redis 7 | bee_kv / bee_cache (خاصية redis) |
| البحث النص الكامل (المنشورات/المستخدمون، البحث الخلفي لـ admin) | OpenSearch (بداية بعقدة واحدة) | bee_search (خاصية opensearch) |
| إحصاءات السلاسل الزمنية (DAU/الاتجاهات/مشاهدات البث/مدة المكالمات/اللوحات) | QuestDB (بداية بملف واحد) | bee_tsdb (خاصية questdb، قابلة للاستبدال بـ influxdb) |
| الرسم البياني الاجتماعي ← خلاصة التوصيات | Neo4j Community (بداية بعقدة واحدة) | bee_graph (خاصية neo4j، قابلة للاستبدال بـ nebulagraph) |
| ملفات الكائنات (صور/فيديوهات/صوت/حزم تصدير) | S3 (MinIO أو مزود سحابي) | وصول مباشر من service + توزيع عبر CDN |
| سجلات التدقيق | MySQL audit_logs، أرشفة في تخزين الكائنات عند انتهاء الصلاحية | يعيد استخدام نظام تدقيق admin |

مبادئ الاختيار: مكونات bee-rust تجريدات بمفاتيح ميزات — بداية بعقدة واحدة، واستبدال بخوادم موزعة مع النمو، دون تقييد؛ MySQL دائمًا مصدر الحقيقة الوحيد؛ طبقة الحوسبة (الفهارس/الإحصاءات/الرسم البياني/الذاكرة المؤقتة) تخزن بيانات مشتقة قابلة لإعادة البناء فقط. الواجهة الأمامية للإدارة (Flutter) لا تلمس قاعدة البيانات مباشرة؛ كل شيء يمر عبر خادم admin.

## 12. النشر والتشغيل (متعدد المناطق عالميًا)

- **البنية الأولية**: منطقتان كبيرتان — الصين + الخارج؛ كل منطقة تضم مجموعة webman + مجموعة bee-rust + Redis محلي + media (SFU/SRS/TURN)؛ أساسي مركزي MySQL + نسخ للقراءة فقط لكل منطقة؛ CDN حسب المنطقة
- **اتصال WS بالأقرب**، رسائل بين المناطق تُنسق مركزيًا؛ الإشعارات عبر المزود المناسب لكل منطقة
- **مسار التطور**: بعد نمو الحركة، تقسيم قواعد البيانات حسب تجزئة المستخدم
- **المراقبة**: مقاييس Prometheus (باتباع نمط open-admin)، سجلات مركزية، تنبيهات (معدل الأخطاء/الكمون/تراكم الطوابير/صحة خدمات الوسائط)

## 13. الأمان والامتثال

- يعيد service إنتاج نموذج الدفاع ذي الـ 18 طبقة من open-admin (XSS/SQLi/CSRF/تحديد المعدل/CSP)
- خط المراجعة: تصفية كلمات حساسة متعددة اللغات عند النشر ← مراجعة الصور/الصوت والفيديو (واجهات طرف ثالث) ← مراجعة بشرية
- GDPR: تصدير البيانات، حق الإلغاء/الحذف، سياسة الاحتفاظ بالسجلات، حد عمر القاصرين، تمايز القواعد الإقليمية

### 16.4 أولويات التوظيف

1. خلفي PHP ×2 + قائد تقني (جوهر مرحلة الأساس؛ الخلفية أكبر مجال عمل)

### 16.5 المخاطر والاحتياطات

- الصوت/الفيديو وقنوات الدفع هما الدوران الأصعب في التوظيف (خبراء نادرون)؛ خصص خطط احتياط عبر الاستعانة الخارجية/المستشارين
