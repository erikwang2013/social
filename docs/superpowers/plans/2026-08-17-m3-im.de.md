# M3-IM-Meilenstein-Implementierungsplan (P1: Geschlossener Kreislauf für Text- und Bildnachrichten)

**语言 / Languages:** [中文](2026-08-17-m3-im.md) · [English](2026-08-17-m3-im.en.md) · [한국어](2026-08-17-m3-im.ko.md) · [Русский](2026-08-17-m3-im.ru.md) · [Deutsch](2026-08-17-m3-im.de.md) · [Français](2026-08-17-m3-im.fr.md) · [Español](2026-08-17-m3-im.es.md) · [Português](2026-08-17-m3-im.pt.md) · [हिन्दी](2026-08-17-m3-im.hi.md) · [العربية](2026-08-17-m3-im.ar.md) · [বাংলা](2026-08-17-m3-im.bn.md) · [Bahasa Indonesia](2026-08-17-m3-im.id.md) · [日本語](2026-08-17-m3-im.ja.md)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Ziel:** M3 P1 liefern: geschlossener Kreislauf für Text-/Bildnachrichten in Privat- und Gruppenchat — WS-Gateway (webman ws worker + Redis pub/sub über Knoten hinweg), Datenmodell mit vier Tabellen, Schreiben über WS / Lesen über REST, Online-Direkt-Push + Offline-Warteschlange + Polling-Degradierung, WS-Client-Anbindung auf drei Plattformen.

**Architektur:** service (webman) erhält einen zusätzlichen ws worker (8789), Verbindungsregistrierung schreibt doppelt nach Redis (`ws:conn:{fd}` TTL 60s + Knotenindex `ws:user:{uid}`) + in-memory Map des Workers; Kanäle sind per-User `im:user:{uid}` pub/sub über Knoten hinweg. Alle Schreibpfade laufen über WS (send/read/typing/recall), Lesepfade über REST (Unterhaltungen/Historie-Paginierung). Zustellung: Online-Direkt-Push + Offline-Warteschlange `im:offline:{uid}` (cap 200) + `PushProvider`-Interface (in M3 NullProvider, Polling-Degradierung). Nachrichten-Idempotenz: SETNX `im:dedup:{uid}:{client_msg_id}` TTL 24h + eindeutiger DB-Index. **Kein im proto nötig** (keine serviceübergreifenden Aufrufe, gRPC ist nur ein M2-Artefakt).

**Tech-Stack:** PHP 8.3 / webman 2.x / workerman ws / Redis (webman/redis-Plugin) / Eloquent / sqlite :memory: Tests; Android OkHttp WebSocket + kotlinx.serialization; iOS URLSessionWebSocketTask; HarmonyOS @ohos.net.webSocket.

**Bestätigte Entscheidungen:** Push-Strategie = NullProvider + In-App-Benachrichtigungen + Polling-Degradierung (vom Nutzer abgesegnet); Sprach-/Anrufe-/Mehrgeräte-Mehrfachverbindungen auf M4 verschoben.

- [ ] **Schritt 2: ConnectionRegistry (lokale Verbindungstabelle + Redis-Registrierung)**

Statische Klasse. `Map<int fd, int uid>` (Speicher) + `Map<int uid, int fd>` Einzelverbindungs-Policy. Methoden:
- `attach(int $fd, int $uid)`: Hat die uid bereits einen alten fd → alten fd zum Rauswurf zurückgeben (Frame `kicked` pushen + close), dann den neuen fd registrieren; nach Redis `ws:conn:{fd}` = uid (EXPIRE 60) und `ws:user:{uid}` = Kennung dieses Knotens schreiben (node id über `gethostname().':'.posix_getpid()` oder `im.node_id` aus der Config, beim Schreiben EXPIRE 60).

- `localFd(int $uid): ?int`: Speicher-Nachschlag.
- `heartbeat(int $fd, int $uid)`: EXPIRE von `ws:conn:{fd}` und `ws:user:{uid}` verlängern.
- Redis über `support\Redis` (webman-redis-Plugin, siehe bestehende Nutzung von `app/queue/redis`).
- Die Knotenkennung stammt aus `ws.constructor.node_id` in `config/process.php` (Standard `gethostname()`, änderbar).

- [ ] **Schritt 1: PushProvider-Interface + NullPushProvider**

```php
interface PushProvider { public function send(int $uid, array $payload): void; }
class NullPushProvider implements PushProvider { public function send(int $uid, array $payload): void {} }
```

Factory in Deliverer: `push()` holt die Implementierung aus der Config oder einer statischen Map (in M3 fix NullPushProvider; `ponytail: für die Anbieter-Integration genügt eine Implementierungsklasse + Factory-Zweig`).

- [ ] **Schritt 2: Deliverer (Kern der knotenübergreifenden Zustellung)**

Statische Methoden:
- `deliver(Message $msg, int $senderId): void`: `ConversationMember::where('conversation_id',$msg->conversation_id)->where('status',1)->pluck('user_id')` holen; für jedes Mitglied:
  - `ConnectionRegistry::localFd($uid)` Treffer → in diesem Worker per `sendToFd` `{type:'message', data:{...msg-Felder..., sender_id}}` pushen;
  - kein Treffer → `Redis::publish('im:user:'.$uid, json_encode([...]))` (andere Knoten pushen nach dem Abo direkt, sobald die lokale Map prüft); niemand abonniert den Kanal → `Redis::rpush('im:offline:'.$uid, $payload)` + `LTRIM` cap 200.
  - Nach dem Offline-Enqueue `PushProvider::send($uid, payload)` aufrufen (in M3 Null no-op).
  - Knoten-Abo-Verwaltung: `bootstrap(int $workerFd)` nutzt `\Workerman\Timer` alle 5s für differenzielles Abo der Kanäle lokal onlineer Nutzer auf `im:user:*` (den `Redis::subscribe`-Callback zum Pushen auf den lokalen fd verwenden — siehe workerman-Redis-Abo-Beispiel). Der Abo-Callback empfängt die `im:user:{uid}`-Nachricht → bei `localFd($uid)`-Treffer direkt pushen, sonst ignorieren (der Absender hat die Offline-Warteschlange bereits geschrieben).
- `notifyRead(int $cid, int $uid, int $lastReadId): void`: an die Kanäle jedes Mitglieds publishen `{type:'read', data:{conversation_id,user_id,last_read_id}}` (Online-Push, keine Offline-Persistenz — die Gelesen-Semantik liegt in der DB, bei Reconnect neu geholt).
- `relayTyping(int $cid, int $uid): void`: an jedes Mitglied `{type:'typing', data:{conversation_id,user_id}}` publishen, nur an Mitglieder `!= $uid` pushen.
- `notifyRecall(int $cid, int $mid, int $uid): void`: `{type:'recall', data:{conversation_id,message_id,user_id}}` publishen, Offline-Mitglieder ebenfalls in `im:offline:{uid}` einreihen (Rückruf-Benachrichtigungen brauchen Offline-Zustellung).
