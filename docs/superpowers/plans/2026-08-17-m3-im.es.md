# Plan de implementación del hito M3 IM (P1: bucle cerrado de mensajes de texto e imagen)

**语言 / Languages:** [中文](2026-08-17-m3-im.md) · [English](2026-08-17-m3-im.en.md) · [한국어](2026-08-17-m3-im.ko.md) · [Русский](2026-08-17-m3-im.ru.md) · [Deutsch](2026-08-17-m3-im.de.md) · [Français](2026-08-17-m3-im.fr.md) · [Español](2026-08-17-m3-im.es.md) · [Português](2026-08-17-m3-im.pt.md) · [हिन्दी](2026-08-17-m3-im.hi.md) · [العربية](2026-08-17-m3-im.ar.md) · [বাংলা](2026-08-17-m3-im.bn.md) · [Bahasa Indonesia](2026-08-17-m3-im.id.md) · [日本語](2026-08-17-m3-im.ja.md)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Objetivo:** Entregar M3 P1: bucle cerrado de mensajes de texto/imagen en chat privado y de grupo — puerta de enlace WS (webman ws worker + Redis pub/sub entre nodos), modelo de datos de cuatro tablas, escritura por WS / lectura por REST, push directo en línea + cola fuera de línea + degradación por polling, integración de clientes WS en las tres plataformas.

**Arquitectura:** service (webman) añade un ws worker (8789), el registro de conexiones escribe doble en Redis (`ws:conn:{fd}` TTL 60s + índice de nodo `ws:user:{uid}`) + Map en memoria del worker; los canales son por usuario `im:user:{uid}` pub/sub entre nodos. Todos los caminos de escritura van por WS (send/read/typing/recall), los de lectura por REST (conversaciones/paginación de historial). Entrega: push directo en línea + cola fuera de línea `im:offline:{uid}` (cap 200) + interfaz `PushProvider` (en M3, NullProvider, degradación por polling). Idempotencia de mensajes: SETNX `im:dedup:{uid}:{client_msg_id}` TTL 24h + índice único en BD. **No se necesita im proto** (sin llamadas entre servicios, gRPC es solo un activo de M2).

**Stack tecnológico:** PHP 8.3 / webman 2.x / workerman ws / Redis (plugin webman/redis) / Eloquent / pruebas sqlite :memory:; Android OkHttp WebSocket + kotlinx.serialization; iOS URLSessionWebSocketTask; HarmonyOS @ohos.net.webSocket.

**Decisiones confirmadas:** Estrategia de push = NullProvider + notificaciones in-app + degradación por polling (aprobado por el usuario); voz/llamadas/multidispositivo multiconnection diferidos a M4.

- [ ] **Paso 1: Envelope (análisis/serialización del sobre)**

Frame entrante JSON `{type, seq, data}`; frame saliente `{type, seq?, data}`. `Envelope::decode(string $raw): ?array` (fallo json/type ausente devuelve null); `Envelope::encode(string $type, array $data, ?int $seq=null): string`. - [ ] **Paso 2: ActionHandler::handle(int $fd, int $uid, array $env): void**

Dispatch por `$env['type']`, los tipos desconocidos devuelven `{type:'error', data:{msg:'unknown type'}}`:
- `ping` → devolver `pong` (eco de seq); `ConnectionRegistry::heartbeat($fd,$uid)`.
- `send` → validar `data.{conversation_id, client_msg_id}` y al menos uno de `content|image_url` (ausente → error); idempotencia: `Redis::set('im:dedup:'.$uid.':'.$cmid, '1', 'EX', 86400, 'NX')`, si false → consultar la BD y devolver `{type:'ack', data:{client_msg_id, message_id}}` y return; persistir (`Message::create`, índice único de BD como respaldo — en conflicto devolver el ack con el id existente) → `Deliverer::deliver($msg, $uid)` (Tarea 5) → devolver `{type:'ack', data:{client_msg_id, message_id}}`.
- `read` → validar conversation_id; `MessageRead::advance($cid,$uid,$data.last_read_id)`; `Deliverer::notifyRead($cid,$uid,$lastReadId)`.
- `typing` → `Deliverer::relayTyping($cid,$uid)` (solo reenvío, sin persistencia).
- `recall` → validar message_id y que el remitente es uno mismo; `Message::where('id',..)->where('sender_id',$uid)->first()`, rechazar si `created_at` tiene más de >120s (error); `update(['recall_status'=>1,'recall_at'=>now])`; `Deliverer::notifyRecall($cid,$mid,$uid)`.

- [ ] **Paso 1: Interfaz PushProvider + NullPushProvider**

```php
interface PushProvider { public function send(int $uid, array $payload): void; }
class NullPushProvider implements PushProvider { public function send(int $uid, array $payload): void {} }
```

Factory en Deliverer: `push()` toma la implementación de la config o de un map estático (en M3 fijo NullPushProvider; `ponytail: la integración de un proveedor solo necesita una clase de implementación + rama de factory`).

- [ ] **Paso 2: Deliverer (núcleo de entrega entre nodos)**

Métodos estáticos:
- `deliver(Message $msg, int $senderId): void`: obtener `ConversationMember::where('conversation_id',$msg->conversation_id)->where('status',1)->pluck('user_id')`; por cada miembro:
  - `ConnectionRegistry::localFd($uid)` acierto → en ese worker enviar por `sendToFd` `{type:'message', data:{...campos msg..., sender_id}}`;
  - sin acierto → `Redis::publish('im:user:'.$uid, json_encode([...]))` (otros nodos tras suscribirse consultan la Map local y envían directo); nadie suscrito al canal → `Redis::rpush('im:offline:'.$uid, $payload)` + `LTRIM` cap 200.
  - Tras la cola fuera de línea, llamar a `PushProvider::send($uid, payload)` (en M3, Null no-op).
  - Gestión de suscripciones del nodo: `bootstrap(int $workerFd)` usa `\Workerman\Timer` cada 5s para suscribir diferencialmente los canales de los usuarios locales en línea en `im:user:*` (usar el callback `Redis::subscribe` que envía al fd local — ver el ejemplo de suscripción Redis de workerman). El callback de suscripción recibe el mensaje `im:user:{uid}` → si `localFd($uid)` acierta enviar directo, si no ignorar (el remitente ya escribió la cola fuera de línea).
- `notifyRead(int $cid, int $uid, int $lastReadId): void`: publicar en los canales de cada miembro `{type:'read', data:{conversation_id,user_id,last_read_id}}` (push en línea, sin persistencia fuera de línea — la semántica de lectura está en la BD, se recarga al reconectar).
- `relayTyping(int $cid, int $uid): void`: publicar a cada miembro `{type:'typing', data:{conversation_id,user_id}}`, enviar solo a miembros `!= $uid`.
- `notifyRecall(int $cid, int $mid, int $uid): void`: publicar `{type:'recall', data:{conversation_id,message_id,user_id}}`, los miembros fuera de línea también entran en `im:offline:{uid}` (las notificaciones de recall requieren entrega fuera de línea).
