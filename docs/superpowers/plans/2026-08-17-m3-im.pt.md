# Plano de implementação do marco M3 IM (P1: ciclo fechado de mensagens de texto e imagem)

**语言 / Languages:** [中文](2026-08-17-m3-im.md) · [English](2026-08-17-m3-im.en.md) · [한국어](2026-08-17-m3-im.ko.md) · [Русский](2026-08-17-m3-im.ru.md) · [Deutsch](2026-08-17-m3-im.de.md) · [Français](2026-08-17-m3-im.fr.md) · [Español](2026-08-17-m3-im.es.md) · [Português](2026-08-17-m3-im.pt.md) · [हिन्दी](2026-08-17-m3-im.hi.md) · [العربية](2026-08-17-m3-im.ar.md) · [বাংলা](2026-08-17-m3-im.bn.md) · [Bahasa Indonesia](2026-08-17-m3-im.id.md) · [日本語](2026-08-17-m3-im.ja.md)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Objetivo:** Entregar o M3 P1: ciclo fechado de mensagens de texto/imagem em chat privado e em grupo — gateway WS (webman ws worker + Redis pub/sub entre nós), modelo de dados de quatro tabelas, escrita via WS / leitura via REST, push direto online + fila offline + degradação por polling, integração dos clientes WS nas três plataformas.

**Arquitetura:** service (webman) adiciona um ws worker (8789), o registro de conexões grava em duplicidade no Redis (`ws:conn:{fd}` TTL 60s + índice de nó `ws:user:{uid}`) + Map em memória do worker; os canais são por usuário `im:user:{uid}` pub/sub entre nós. Todos os caminhos de escrita passam por WS (send/read/typing/recall), os de leitura por REST (conversas/paginação de histórico). Entrega: push direto online + fila offline `im:offline:{uid}` (cap 200) + interface `PushProvider` (no M3, NullProvider, degradação por polling). Idempotência de mensagens: SETNX `im:dedup:{uid}:{client_msg_id}` TTL 24h + índice único no BD. **Não precisa de im proto** (sem chamadas entre serviços, gRPC é apenas um ativo do M2).

**Stack de tecnologia:** PHP 8.3 / webman 2.x / workerman ws / Redis (plugin webman/redis) / Eloquent / testes sqlite :memory:; Android OkHttp WebSocket + kotlinx.serialization; iOS URLSessionWebSocketTask; HarmonyOS @ohos.net.webSocket.

**Decisões confirmadas:** Estratégia de push = NullProvider + notificações in-app + degradação por polling (aprovada pelo usuário); voz/chamadas/multidispositivo multi-conexão adiados para M4.

- [ ] **Passo 2: ConnectionRegistry (tabela de conexões locais + registro no Redis)**

Classe estática. `Map<int fd, int uid>` (memória) + `Map<int uid, int fd>` política de conexão única. Métodos:
- `attach(int $fd, int $uid)`: se o uid já tem um fd antigo → retornar o fd antigo para expulsão (enviar frame `kicked` + close), depois registrar o novo fd; escrever no Redis `ws:conn:{fd}` = uid (EXPIRE 60) e `ws:user:{uid}` = identificador deste nó (node id via `gethostname().':'.posix_getpid()` ou `im.node_id` da config, EXPIRE 60 na escrita).

- `localFd(int $uid): ?int`: busca em memória.
- `heartbeat(int $fd, int $uid)`: renovar o EXPIRE de `ws:conn:{fd}` e `ws:user:{uid}`.
- Redis via `support\Redis` (plugin webman redis, ver o uso existente de `app/queue/redis`).
- O identificador de nó vem de `ws.constructor.node_id` em `config/process.php` (padrão `gethostname()`, alterável).

- [ ] **Passo 1: Envelope (parse/serialização do envelope)**

Frame de entrada JSON `{type, seq, data}`; frame de saída `{type, seq?, data}`. `Envelope::decode(string $raw): ?array` (falha de json/type ausente retorna null); `Envelope::encode(string $type, array $data, ?int $seq=null): string`. Constantes: `T_SEND='send' T_ACK='ack' T_READ='read' T_TYPING='typing' T_RECALL='recall' T_PING='ping'`; `T_MESSAGE='message' T_KICKED='kicked' T_PONG='pong' T_ERROR='error'`.

- [ ] **Passo 2: ActionHandler::handle(int $fd, int $uid, array $env): void**

Dispatch por `$env['type']`, tipos desconhecidos retornam `{type:'error', data:{msg:'unknown type'}}`:
- `ping` → retornar `pong` (eco de seq); `ConnectionRegistry::heartbeat($fd,$uid)`.
- `send` → validar `data.{conversation_id, client_msg_id}` e pelo menos um de `content|image_url` (ausente → error); idempotência: `Redis::set('im:dedup:'.$uid.':'.$cmid, '1', 'EX', 86400, 'NX')`, se false → consultar o BD e retornar `{type:'ack', data:{client_msg_id, message_id}}` e return; persistir (`Message::create`, índice único do BD como salvaguarda — em conflito retornar o ack com o id existente) → `Deliverer::deliver($msg, $uid)` (Tarefa 5) → retornar `{type:'ack', data:{client_msg_id, message_id}}`.
- `read` → validar conversation_id; `MessageRead::advance($cid,$uid,$data.last_read_id)`; `Deliverer::notifyRead($cid,$uid,$lastReadId)`.
- `typing` → `Deliverer::relayTyping($cid,$uid)` (apenas retransmissão, sem persistência).
- `recall` → validar message_id e que o remetente é o próprio usuário; `Message::where('id',..)->where('sender_id',$uid)->first()`, rejeitar se `created_at` tiver mais de >120s (error); `update(['recall_status'=>1,'recall_at'=>now])`; `Deliverer::notifyRecall($cid,$mid,$uid)`.

- [ ] **Passo 1: Interface PushProvider + NullPushProvider**

```php
interface PushProvider { public function send(int $uid, array $payload): void; }
class NullPushProvider implements PushProvider { public function send(int $uid, array $payload): void {} }
```

Factory no Deliverer: `push()` pega a implementação da config ou de um map estático (no M3 fixo NullPushProvider; `ponytail: a integração de um fornecedor só precisa de uma classe de implementação + ramo de factory`).

- [ ] **Passo 2: Deliverer (núcleo de entrega entre nós)**

Métodos estáticos:
- `deliver(Message $msg, int $senderId): void`: obter `ConversationMember::where('conversation_id',$msg->conversation_id)->where('status',1)->pluck('user_id')`; para cada membro:
  - `ConnectionRegistry::localFd($uid)` acerto → naquele worker enviar via `sendToFd` `{type:'message', data:{...campos msg..., sender_id}}`;
  - sem acerto → `Redis::publish('im:user:'.$uid, json_encode([...]))` (outros nós, após assinar, consultam o Map local e enviam direto); ninguém assinado ao canal → `Redis::rpush('im:offline:'.$uid, $payload)` + `LTRIM` cap 200.
  - Após a fila offline, chamar `PushProvider::send($uid, payload)` (no M3, Null no-op).
  - Gestão de assinaturas do nó: `bootstrap(int $workerFd)` usa `\Workerman\Timer` a cada 5s para assinar diferencialmente os canais dos usuários locais online em `im:user:*` (usar o callback `Redis::subscribe` que envia para o fd local — ver o exemplo de assinatura Redis do workerman). O callback de assinatura recebe a mensagem `im:user:{uid}` → se `localFd($uid)` acertar enviar direto, senão ignorar (o remetente já escreveu a fila offline).
- `notifyRead(int $cid, int $uid, int $lastReadId): void`: publicar nos canais de cada membro `{type:'read', data:{conversation_id,user_id,last_read_id}}` (push online, sem persistência offline — a semântica de leitura está no BD, recarregada ao reconectar).
- `relayTyping(int $cid, int $uid): void`: publicar a cada membro `{type:'typing', data:{conversation_id,user_id}}`, enviar apenas a membros `!= $uid`.
- `notifyRecall(int $cid, int $mid, int $uid): void`: publicar `{type:'recall', data:{conversation_id,message_id,user_id}}`, membros offline também entram em `im:offline:{uid}` (notificações de recall precisam de entrega offline).
