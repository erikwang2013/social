# M3 IM マイルストーン実装計画（P1: テキスト＋画像メッセージのクローズドループ）

**语言 / Languages:** [中文](2026-08-17-m3-im.md) · [English](2026-08-17-m3-im.en.md) · [한국어](2026-08-17-m3-im.ko.md) · [Русский](2026-08-17-m3-im.ru.md) · [Deutsch](2026-08-17-m3-im.de.md) · [Français](2026-08-17-m3-im.fr.md) · [Español](2026-08-17-m3-im.es.md) · [Português](2026-08-17-m3-im.pt.md) · [हिन्दी](2026-08-17-m3-im.hi.md) · [العربية](2026-08-17-m3-im.ar.md) · [বাংলা](2026-08-17-m3-im.bn.md) · [Bahasa Indonesia](2026-08-17-m3-im.id.md) · [日本語](2026-08-17-m3-im.ja.md)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**目標:** M3 P1 を納品する：プライベートチャット＋グループチャットのテキスト/画像メッセージのクローズドループ — WS ゲートウェイ（webman ws worker + ノード間 Redis pub/sub）、4テーブルのデータモデル、書き込みは WS / 読み取りは REST、オンライン直接プッシュ + オフラインキュー + ポーリング降格、3端末 WS クライアント接続。

**アーキテクチャ:** service（webman）に ws worker（8789）を追加。接続登録は Redis に二重書き込み（`ws:conn:{fd}` TTL 60s + ノード索引 `ws:user:{uid}`）+ worker のメモリ Map。チャネルはユーザー単位 `im:user:{uid}` のノード間 pub/sub。書き込みパスはすべて WS（send/read/typing/recall）、読み取りパスは REST（会話/履歴ページング）。配信：オンライン直接プッシュ + オフラインキュー `im:offline:{uid}`（cap 200）+ `PushProvider` インターフェース（M3 は NullProvider、ポーリング降格でカバー）。メッセージ冪等性：SETNX `im:dedup:{uid}:{client_msg_id}` TTL 24h + DB 一意索引。**im proto は不要**（サービス間呼び出しなし、gRPC は M2 の資産のみ）。

**技術スタック:** PHP 8.3 / webman 2.x / workerman ws / Redis（webman/redis プラグイン）/ Eloquent / sqlite :memory: テスト。Android は OkHttp WebSocket + kotlinx.serialization。iOS は URLSessionWebSocketTask。HarmonyOS は @ohos.net.webSocket。

**確定済みの決定:** プッシュ戦略 = NullProvider + アプリ内通知 + ポーリング降格（ユーザー決定済み）。音声/通話/複数端末・複数接続は M4 へ後置。

- [ ] **Step 2: ConnectionRegistry（自ノード接続表 + Redis 登録）**

静的クラス。`Map<int fd, int uid>`（メモリ）+ `Map<int uid, int fd>` の単一接続ポリシー。メソッド：
- `attach(int $fd, int $uid)`：その uid に既存の旧 fd があれば → 旧 fd を返してキックアウト用に（`kicked` フレームをプッシュ + close）、その後新しい fd を登録。Redis に `ws:conn:{fd}` = uid（EXPIRE 60）と `ws:user:{uid}` = 自ノード識別子を書く（node id は `gethostname().':'.posix_getpid()` か config の `im.node_id` を使い、書き込み時に EXPIRE 60）。
- `detach(int $fd)`：メモリから削除 + Redis DEL `ws:conn:{fd}`。`ws:user:{uid}` が自ノードを指していれば DEL。
- `localFd(int $uid): ?int`：メモリ検索。
- `heartbeat(int $fd, int $uid)`：`ws:conn:{fd}` と `ws:user:{uid}` の EXPIRE を更新。
- Redis は `support\Redis` を使う（webman redis プラグイン。既存の `app/queue/redis` の使い方を参照）。
- ノード識別子は `config/process.php` の `ws.constructor.node_id` から取得（デフォルト `gethostname()`、変更可）。

- [ ] **Step 3: WsServer（Worker handler）**

`Workerman\Worker` を継承（webman プラグイン/公式 ws サンプル参照）。`onConnect` は空実装。`onWebSocketConnect`（worker 構築後に静的メソッドとして登録）で `$_GET['token']` を解析 → `JwtHelper::decode`（`app/middleware/AuthMiddleware.php` の使い方を参照、失敗時 close(4001)）。成功時 `ConnectionRegistry::attach` して `{type:'ready'}` フレームを返す。`onMessage` は ActionHandler に委譲（タスク4）。`onClose` は `detach` を呼ぶ。`onWorkerStart` は Redis 購読コールバックを登録（`im:user:{uid}` の動的購読はタスク5の Deliverer の責務）——タスク3は接続ライフサイクルのみ実装し、メッセージ処理はタスク4に残す。

- [ ] **Step 1: Envelope（エンベロープの解析/シリアライズ）**

入フレーム JSON `{type, seq, data}`。出フレーム `{type, seq?, data}`。`Envelope::decode(string $raw): ?array`（json 失敗/type 欠如は null を返す）。`Envelope::encode(string $type, array $data, ?int $seq=null): string`。定数：`T_SEND='send' T_ACK='ack' T_READ='read' T_TYPING='typing' T_RECALL='recall' T_PING='ping'`。`T_MESSAGE='message' T_KICKED='kicked' T_PONG='pong' T_ERROR='error'`。

- [ ] **Step 2: ActionHandler::handle(int $fd, int $uid, array $env): void**

`$env['type']` で分岐し、未知のタイプは `{type:'error', data:{msg:'unknown type'}}` を返す：
- `ping` → `pong` を返す（seq エコー）。`ConnectionRegistry::heartbeat($fd,$uid)`。
- `send` → `data.{conversation_id, client_msg_id}` と `content|image_url` の少なくとも一方を検証（欠如 → error）。冪等性：`Redis::set('im:dedup:'.$uid.':'.$cmid, '1', 'EX', 86400, 'NX')`。false なら DB を照会して `{type:'ack', data:{client_msg_id, message_id}}` を返して return。落庫（`Message::create`、DB 一意索引が保険——衝突時は既存 id で ack を返す）→ `Deliverer::deliver($msg, $uid)`（タスク5）→ `{type:'ack', data:{client_msg_id, message_id}}` を返す。
- `read` → conversation_id を検証。`MessageRead::advance($cid,$uid,$data.last_read_id)`。`Deliverer::notifyRead($cid,$uid,$lastReadId)`。
- `typing` → `Deliverer::relayTyping($cid,$uid)`（純転送、落庫なし）。
- `recall` → message_id と送信者が自分自身であることを検証。`Message::where('id',..)->where('sender_id',$uid)->first()`。`created_at` が 120秒より前なら拒否（error）。`update(['recall_status'=>1,'recall_at'=>now])`。`Deliverer::notifyRecall($cid,$mid,$uid)`。

- [ ] **Step 1: PushProvider インターフェース + NullPushProvider**

```php
interface PushProvider { public function send(int $uid, array $payload): void; }
class NullPushProvider implements PushProvider { public function send(int $uid, array $payload): void {} }
```

ファクトリは Deliverer に置く：`push()` は config か静的 map から実装を取得（M3 は NullPushProvider 固定。`ponytail: ベンダー接続は実装クラス + ファクトリ分岐を足すだけ`）。

- [ ] **Step 2: Deliverer（ノード間配信の核心）**

静的メソッド：
- `deliver(Message $msg, int $senderId): void`：`ConversationMember::where('conversation_id',$msg->conversation_id)->where('status',1)->pluck('user_id')` を取得。メンバーごとに：
  - `ConnectionRegistry::localFd($uid)` にヒット → その worker 内で `sendToFd` により `{type:'message', data:{...msg フィールド..., sender_id}}` をプッシュ。
  - ヒットしない → `Redis::publish('im:user:'.$uid, json_encode([...]))`（他ノードが購読後ローカル Map を確認して直接プッシュ）。チャンネルに購読者がいなければ → `Redis::rpush('im:offline:'.$uid, $payload)` + `LTRIM` cap 200。
  - オフライン入隊後に `PushProvider::send($uid, payload)` を呼ぶ（M3 は Null で無操作）。
  - ノード購読管理：`bootstrap(int $workerFd)` は `\Workerman\Timer` で5秒ごとに `im:user:*` の自ノードオンラインユーザーチャンネルへ差分購読（`Redis::subscribe` のコールバックで自ノード fd にプッシュ——workerman の Redis 購読サンプル参照）。購読コールバックが `im:user:{uid}` メッセージを受信 → `localFd($uid)` ヒットなら直接プッシュ、それ以外は無視（送信側がオフラインキューを書いている）。
- `notifyRead(int $cid, int $uid, int $lastReadId): void`：各メンバーのチャンネルに `{type:'read', data:{conversation_id,user_id,last_read_id}}` を publish（オンラインプッシュのみ、オフラインは落庫しない——既読の意味論は DB 基準で、再接続時に取得）。
- `relayTyping(int $cid, int $uid): void`：各メンバーに `{type:'typing', data:{conversation_id,user_id}}` を publish。`!= $uid` のメンバーにのみプッシュ。
- `notifyRecall(int $cid, int $mid, int $uid): void`：`{type:'recall', data:{conversation_id,message_id,user_id}}` を publish。オフラインメンバーにも `im:offline:{uid}` へ入隊（撤回通知はオフライン配信が必要）。
