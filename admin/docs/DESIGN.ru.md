## 2. Архитектура бэкенда

### 2.1 Многослойное проектирование

| Слой | Каталог | Обязанность |
|---|------|------|
| Маршрутизация | `config/route.php` | Сопоставление URL с контроллерами, привязка промежуточного ПО, версионированные маршруты |
| Промежуточное ПО | `app/middleware/` | Перехват атак (SecurityFilter), ограничение частоты (RateLimit), аутентификация (JWT), авторизация (RBAC), версия API (ApiVersion) |
| Контроллеры | 14: Dashboard/User/Role/Permission/Config/Log/Profile/Export/Import/Upload/Health/Docs (админ) + Captcha/Auth (API v1) | Проверка параметров запроса, вызов бизнес-логики, форматирование ответов |
| Бизнес-сервисы | `app/service/` | Переиспользуемая бизнес-логика (зарезервировано) |
| Модели данных | `app/model/` | ORM-маппинг, связи, шифрование/дешифрование полей |
| Общие утилиты | `app/common/` | Сервисы Hashids, Snowflake, Encryption |

### 2.2 Жизненный цикл запроса

```
客户端请求
  │
  ▼
webman HTTP Server (workerman)
  │
  ▼
Route 匹配
  │
  ▼
中间件链:
  Locale ──────────────► Accept-Language / ?lang= 语言检测
  │
  ▼
  SecurityFilter ──────► HTTP方法检查 → 405 (仅允许 GET/POST/PUT/DELETE/OPTIONS/HEAD)
  │                     XSS/SQL注入/路径遍历/命令注入/CSRF 攻击拦截 (403)
  ▼
  RateLimit ───────────► Redis 滑动窗口限流
  │ (失败返回 429 + Retry-After 头)
  ▼
  ApiVersion ─────────► API-Version 头校验，注入 $request->apiVersion
  │ (失败返回 400)
  ▼
  AdminAuth ──────────► JWT 验证，注入 $request->adminId
  │ (失败返回 401)
  ▼
  AdminPermission ────► RBAC 权限校验（Redis 60s 缓存）
  │ (失败返回 403)
  ▼
  OperationLog ───────► 操作日志记录 (POST/PUT/DELETE)，自动检测来源端
  │
  ▼
Controller::method()
  │
  ├─► 参数验证 (validator)
  ├─► 敏感操作确认 (confirmPassword)
  ├─► decodeId() — hashid → BIGINT
  ├─► Model 操作 (自动 encryptable 加解密)
  ├─► encodeId() — BIGINT → hashid
  └─► Response JSON
```

### 2.3 Жизненный цикл ID

```
生成 (Snowflake) → 存储 (MySQL BIGINT) → 传输 (Hashids 编码) → 外部 (hash 字符串)
                                                                    │
                            HashidsService::decode() ←──────────────┘
```

### 2.4 Система шифрования данных

```
传输层 (encryption)     — AES-256-CBC，独立密钥
存储层 (encryptable)    — AES-128-ECB，独立密钥，Model $casts 自动处理
展示层 (mask)           — 手机号: 138****1234，邮箱: a***@example.com
```


### 4.2 Стратегия версионирования API

Версия API управляется через заголовок запроса и **не отражается в пути URL**:

```http
API-Version: v1
```

| Механизм | Описание |
|------|------|
| Версия по умолчанию | При отсутствии заголовка `API-Version` по умолчанию `v1` |
| Проверка | Проверяет промежуточное ПО `ApiVersion`; неподдерживаемая версия возвращает 400 |
| Маршрутизация | Вспомогательная функция `v()` динамически резолвит класс контроллера по версии |
| Каталог | Контроллеры организованы по версиям: `app/api/{version}/controller/` |

Пример расширения — добавление API v2:
1. Создать `app/api/v2/controller/AuthController.php`
2. Добавить `'v2'` в константу `SUPPORTED` промежуточного ПО `ApiVersion`
3. Определения маршрутов менять не нужно

```bash
# 使用 v1
curl -H "API-Version: v1" /api/auth/login

# 使用 v2
curl -H "API-Version: v2" /api/auth/login

# 不传，默认 v1
curl /api/auth/login
```

### 4.3 Стратегия ограничения частоты

Основана на алгоритме скользящего окна Redis Sorted Set, выполняется атомарным Lua-скриптом:

| Интерфейс | Ограничение |
|------|------|
| По умолчанию | 60 раз/мин/IP/маршрут |
| POST /api/auth/login | 10 раз/мин |
| POST /api/auth/register | 5 раз/мин |

При превышении возвращается 429, заголовки ответа включают X-RateLimit-Limit / Remaining / Reset / Retry-After.

### 4.4 Единый ответ

```json
{
  "code": 0,
  "message": "success",
  "data": { ... }
}
```

| code | Смысл | Сценарий срабатывания |
|------|------|---------|
| 0 | Успех | Обычный ответ |
| 400 | Ошибка параметров | Неверный формат запроса |
| 401 | Не аутентифицирован | Token отсутствует/истёк/недействителен |
| 403 | Нет прав | Роль пользователя не содержит требуемого права |
| 404 | Не найдено | Ресурс не найден |
| 422 | Ошибка проверки | Параметры формы не соответствуют правилам / не удалось подтвердить пароль |
| 500 | Ошибка сервера | Непредвиденное исключение |

### 4.5 Процесс аутентификации (с кликабельной капчей)

```
客户端                               服务端
  │                                    │
  │  ① POST /api/captcha/generate     │ captcha_create('click')
  │◄── {key, image(base64), targets}  │
  │                                    │
  │  ② 用户点击图中文字位置              │
  │                                    │
  │  ③ POST /api/auth/login           │
  │     {username, password,          │
  │      captcha_key, clicks}         │
  │────────────────────────────────►  │
  │                                    │ ① captcha_verify()
  │                                    │ ② password_verify()
  │                                    │ ③ jwt()->create()
  │◄── {access_token, refresh_token}  │
  │                                    │
  │  ④ GET /admin/dashboard           │
  │     Authorization: Bearer xxx     │
  │────────────────────────────────►  │ AdminAuth → AdminPermission
  │◄── 200 {dashboard data}           │
```

### 4.6 Модель прав (RBAC)

```
  用户 ──┬── 角色 ──┬── 权限
  User     Role      Permission
                 │
                 ├── type=1: 菜单 (控制侧边栏可见)
                 ├── type=2: 按钮 (控制页面内操作)
                 └── type=3: API  (控制接口访问)

  权限标识格式: {method}.{path}
  例: get.admin/user  post.admin/user  delete.admin/user
  超级管理员标识: * (跳过所有权限检查)
```

### 4.7 Второе подтверждение чувствительных операций

Чувствительные операции, такие как удаление пользователей, ролей и прав, требуют передачи текущего пароля пользователя в теле запроса для повторной проверки личности:

```
客户端                           服务端
  │                                │
  │  DELETE /admin/user/{hashid}  │
  │  { password: "******" }       │
  │────────────────────────────►  │
  │                                │ confirmPassword(adminId, password)
  │                                │ → 密码错误返回 422
  │                                │ → 密码正确继续执行
  │◄── 200 { code: 0 }           │
```

Фронтенд перед запуском операции удаления показывает диалог подтверждения, собирает пароль пользователя и затем отправляет запрос.

## 6. Проектирование безопасности

### 6.1 Многоуровневая защита

| Уровень | Мера |
|------|------|
| Ограничение методов | Белый список HTTP-методов SecurityFilter, разрешены только GET/POST/PUT/DELETE/OPTIONS/HEAD, нестандартные методы возвращают 405 |
| Перехват атак | Промежуточное ПО SecurityFilter, обнаружение и перехват XSS/SQL-инъекции/обхода пути/инъекции команд/CSRF |
| Проверка человека | Кликабельная капча, обязательна при входе/регистрации |
| Блокировка учётной записи | 5 последовательных неудачных входов блокируют учётную запись на 15 минут, в период блокировки возвращается 429 |
| Ограничение сессий | Не более 3 одновременных токенов на пользователя, при превышении старейший токен автоматически в чёрный список |
| Ограничение частоты | Промежуточное ПО RateLimit, скользящее окно Redis, атомарный Lua |
| CSP | Заголовок Content-Security-Policy ограничивает источники ресурсов, защищает от XSS и внедрения данных |
| Подтверждение операций | Чувствительные операции (например, удаление) требуют повторного ввода текущего пароля пользователя |
| Передача | HTTPS + JWT Bearer Token |
| ID интерфейсов | Шифрование Hashids, внешние стороны не могут обратно вычислить реальный ID |
| Тело запроса | Шифрование чувствительных полей AES-256-CBC |
| База данных | BIGINT-первичные ключи (автоинкремент не раскрывается) |
| База данных | Шифрованное хранение чувствительных полей AES-128-ECB |
| Аутентификация | JWT HS256, истечение 2ч + refresh token |
| Авторизация | RBAC, контроль прав с гранулярностью method.path |
| Аудит | OperationLog записывает все операции (включая автоматическое определение источника source) |

### 6.2 Управление ключами

```
JWT_SECRET          → 环境变量注入，64位随机字符串
HASHIDS_SALT        → 唯一盐值，泄漏后需全局更换
ENCRYPTION_KEY      → API 传输加密密钥，32字节
ENCRYPTABLE_KEY     → DB 存储加密密钥，与传输密钥独立
SCOUT_HOSTS         → ES 地址，内网部署
```

## 8. Архитектура развёртывания

### 8.1 Рекомендуемая топология


### 8.2 Docker Compose (рекомендуется для продакшена)

`docker-compose.yml` в корне проекта оркеструет все сервисы указанной топологии:

| Сервис | Образ/сборка | Порты | Описание |
|------|----------|------|------|
| `nginx` | nginx:alpine | 80, 443 | Обратный прокси + статические файлы + Gzip |
| `app` | сборка из локального `Dockerfile` | 8787 | PHP 8.3 + OPcache + webman |
| `mysql` | mysql:8.0 | 3306 | Основная БД, персистентность через том данных |
| `redis` | redis:7-alpine | 6379 | Кэш / ограничение частоты / капча |
| `elasticsearch` | elasticsearch:8.x | 9200 | Полнотекстовый поиск |

Перед запуском замените в `docker-compose.yml` ключи `JWT_SECRET`, `HASHIDS_SALT`, `ENCRYPTION_KEY` и другие на случайные строки.

```bash
cp .env.docker .env
docker-compose up -d
```

### 8.3 CI/CD

Непрерывная интеграция GitHub Actions определена в `.github/workflows/ci.yml`:
- Проверка синтаксиса PHP (`php -l`)
- Модульные тесты PHPUnit
- Статический анализ Flutter (`flutter analyze`)

### 8.4 Резервное копирование БД

`database/backup/backup.sh` — резервное копирование mysqldump + gzip, автоматическая очистка старых копий старше 30 дней.
`database/backup/restore.sh` — интерактивный выбор и восстановление резервной копии.

### 8.5 Мониторинг

Конечная точка `GET /metrics` (`MetricsController`) раскрывает 5 gauge-метрик в текстовом формате Prometheus: общее число HTTP-запросов, число активных пользователей, состояние соединения с БД/Redis, объём используемой памяти.
