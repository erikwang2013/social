## 1. ডিফেন্স ইন ডেপথের সামগ্রিক দৃশ্য

সিস্টেমটি ৭-স্তরের ডিফেন্স ইন ডেপথ মডেল ব্যবহার করে, যা বাইরে থেকে ভেতরে স্তরে স্তরে দূষিত অনুরোধগুলো ছেঁকে নেয়, নিশ্চিত করে যে কোনো একক স্তর ব্যর্থ হলেও পরবর্তী প্রতিরক্ষা লাইনগুলো কার্যকর থাকে।

সম্পূর্ণ মিডলওয়্যার চেইনটি নিম্নলিখিত ক্রমে কার্যকর হয় (`config/middleware.php` দেখুন):

```
请求 → Cors → Locale(Accept-Language) → SecurityMiddleware (erikwang2013/security-php, 31种检测器) → RateLimit → [路由组中间件: AdminAuth → AdminPermission → OperationLog] → Controller
```

| স্তর | মিডলওয়্যার/প্রক্রিয়া | প্রতিরক্ষার লক্ষ্য |
|----|--------|---------|
| ১ | SecurityMiddleware (erikwang2013/security-php) | ৩১ ধরনের আক্রমণ শনাক্তকরণ + HTTP মেথড যাচাই + অনুরোধ বডির আকার সীমা + Content-Type যাচাই + CSRF + IP আক্রমণ এসকেলেশন ব্ল্যাকলিস্ট |
| ২ | Cors | ক্রস-অরিজিন নিরাপত্তা + নিরাপত্তা রেসপন্স হেডার ইনজেকশন |
| ৩ | RateLimit | Redis স্লাইডিং উইন্ডো রেট লিমিটিং, ব্রুট-ফোর্স প্রতিরোধ |
| ৪ | AdminAuth | JWT প্রমাণীকরণ + ব্ল্যাকলিস্ট লগআউট |
| ৫ | AdminPermission | RBAC method.path গ্র্যানুলারিটি অনুমোদন |
| ৬ | OperationLog | অপারেশন অডিট + উৎস প্রান্ত ট্র্যাকিং |
| ৭ | ডেটা এনক্রিপশন | Hashids ID অস্পষ্টকরণ + Encryptable DB এনক্রিপশন + EncryptionService ট্রান্সমিশন এনক্রিপশন |

ফ্রন্টএন্ডের তিন স্তর (Flutter) আলাদা ইনপুট যাচাই করে; ব্যাকএন্ড কোনো কিছুর উপর বিশ্বাস করে না, প্রতিটি স্তর স্বাধীনভাবে প্রতিরক্ষা করে।

## 2. আক্রমণ শনাক্তকরণ ইঞ্জিন

## 2. 攻击检测引擎 (erikwang2013/security-php)

আক্রমণ শনাক্তকরণ নিজস্ব SecurityMiddleware থেকে নিবেদিত নিরাপত্তা প্যাকেজ `erikwang2013/security-php` v1.1+-এ স্থানান্তরিত হয়েছে, যা **৩১টি ডিটেক্টর** সরবরাহ করে, ৫টি বড় আক্রমণ শ্রেণি কভার করে।

### 2.1 ডিটেক্টরের শ্রেণিবিভাগ

**ইনজেকশন আক্রমণ (১১ ধরনের):** XSS, SQL ইনজেকশন, কমান্ড ইনজেকশন, NoSQL ইনজেকশন, LDAP ইনজেকশন, XPath ইনজেকশন, JNDI/Log4Shell, SSI সার্ভার-সাইড ইনক্লুশন, GraphQL ইনজেকশন, SSTI টেমপ্লেট ইনজেকশন

**প্রোটোকল ও অনুরোধ আক্রমণ (৯ ধরনের):** SSRF, XXE, HTTP রেসপন্স হেডার ইনজেকশন, Host হেডার আক্রমণ, Request Smuggling, Open Redirect, CORS বাইপাস, WebSocket হাইজ্যাকিং, DNS Rebinding

**HTTP প্রোটোকল স্তর যাচাই (৬ ধরনের):** HTTP মেথড যাচাই (৪০৫), অনুরোধ বডির আকার সীমা (৪১৩), Content-Type যাচাই (৪১৫), CSRF Origin পরীক্ষা, IP আক্রমণ এসকেলেশন ব্ল্যাকলিস্ট, সংবেদনশীল ডেটা লিক শনাক্তকরণ

**ডেটা ও সিরিয়ালাইজেশন আক্রমণ (৫ ধরনের):** PHP ডি-সিরিয়ালাইজেশন, CSV ফর্মুলা ইনজেকশন, ইমেইল হেডার ইনজেকশন, JWT আক্রমণ (গাঠনিক বিশ্লেষণ), JS Prototype Pollution

**ফাইল ও পাথ আক্রমণ (২ ধরনের):** পাথ ট্রাভার্সাল, দূষিত ফাইল আপলোড

### 2.2 হ্যান্ডলিং মোড

প্রতিটি ডিটেক্টর স্বাধীনভাবে দুটি মোড সমর্থন করে:
- `block` — আক্রমণ শনাক্ত হলেই ব্লক করে, কনফিগার করা স্ট্যাটাস কোড ফেরত দেয়
- `log` — শুধু লগ রাখে, ব্লক করে না (`header_injection`, `ssti`, `nosql_injection` ডিফল্টভাবে log মোডে থাকে, মিথ্যা পজিটিভ রোধ করতে)

### 2.3 IP আক্রমণ এসকেলেশন ব্ল্যাকলিস্ট

একই IP ৬০ সেকেন্ডে ৫ বার আক্রমণ শনাক্তকরণ ট্রিগার করলে → স্বয়ংক্রিয়ভাবে ১৫ মিনিটের জন্য ব্যান। স্টোরেজ ব্যাকএন্ড ঐচ্ছিক: Redis (বিতরণকৃত), File (একক মেশিনের JSON) বা Cache (উচ্চ-সমবর্তী স্বাধীন ফাইল); বর্তমান কনফিগারেশন Redis স্টোরেজ ব্যবহার করে।

### 2.4 নিরাপত্তা লগ

ফাইলের অবস্থান: `runtime/logs/security.log` (স্বয়ংক্রিয় রোটেশন, 10MB/ফাইল)

## 4. নিরাপত্তা রেসপন্স হেডার

সমস্ত হেডার `Cors` মিডলওয়্যারে ইনজেক্ট হয়, `$response->withHeaders()` এর মাধ্যমে প্রতিটি রেসপন্সে যুক্ত হয়।

| হেডার | মান | কার্যকারিতা |
|----|-----|------|
| Access-Control-Allow-Origin | `*` | যেকোনো অরিজিনকে ক্রস-ডোমেইন অনুমতি (ইন্ট্রানেট অ্যাডমিন প্যানেল পরিস্থিতি) |
| Access-Control-Allow-Methods | `GET,POST,PUT,DELETE,OPTIONS` | অনুমোদিত মেথডের সেট |
| Access-Control-Allow-Headers | `Authorization,Content-Type,API-Version` | অনুমোদিত কাস্টম হেডার |
| Access-Control-Max-Age | `86400` | প্রিফ্লাইট অনুরোধ ২৪ ঘণ্টা ক্যাশ |
| X-Content-Type-Options | `nosniff` | ব্রাউজার MIME স্নিফিং নিষিদ্ধ |
| X-Frame-Options | `DENY` | সব iframe এমবেডিং নিষিদ্ধ, ক্লিকজ্যাকিং প্রতিরোধ |
| X-XSS-Protection | `1; mode=block` | ব্রাউজারের অন্তর্নির্মিত XSS ফিল্টার সক্রিয় করে এবং পেজ রেন্ডারিং ব্লক করে |
| Referrer-Policy | `strict-origin-when-cross-origin` | একই অরিজিনে সম্পূর্ণ URL, ক্রস-অরিজিনে শুধু ডোমেইন পাঠায় |
| Permissions-Policy | `camera=(), microphone=(), geolocation=()` | পুরো সাইটে ক্যামেরা/মাইক্রোফোন/জিওলোকেশন API নিষ্ক্রিয় |

OPTIONS প্রিফ্লাইট অনুরোধ সরাসরি ২০৪ খালি রেসপন্স ফেরত দেয়, পরবর্তী মিডলওয়্যার চেইনে প্রবেশ করে না।

### 4.2 Content-Security-Policy (CSP)

অন্যান্য নিরাপত্তা হেডারের সাথে Cors মিডলওয়্যারে ইনজেক্ট হয়, ডিফেন্স ইন ডেপথ প্রদান করে, ব্রাউজার লোড ও এক্সিকিউট করতে পারা রিসোর্সের উৎস সীমিত করে।

| হেডার | মান | কার্যকারিতা |
|----|-----|------|
| Content-Security-Policy | `default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'` | স্ক্রিপ্ট/স্টাইল/ইমেজ/কানেকশন/ফ্রেম/ফর্ম ইত্যাদি রিসোর্সের উৎস সীমিত করে |
| X-Permitted-Cross-Domain-Policies | `none` | Adobe Flash/PDF ইত্যাদি ক্রস-ডোমেইন পলিসি ফাইল লোডিং নিষিদ্ধ |

CSP নীতির মূল পয়েন্ট:
- `default-src 'self'`: ডিফল্টভাবে শুধু একই-অরিজিন রিসোর্স অনুমোদিত
- `script-src 'self' 'unsafe-inline' 'unsafe-eval'`: একই-অরিজিন স্ক্রিপ্ট + ইনলাইন স্ক্রিপ্ট (Flutter Web-এর জন্য প্রয়োজনীয়) + eval (Flutter Web ডিবাগিংয়ের জন্য প্রয়োজনীয়) অনুমোদিত
- `frame-ancestors 'none'`: যেকোনো পেজে iframe এমবেডিং নিষিদ্ধ, X-Frame-Options: DENY-এর সাথে দ্বৈত নিশ্চয়তা
- `base-uri 'self'`: `<base>` ট্যাগ শুধু একই-অরিজিনে নির্দেশ করতে সীমিত
- `form-action 'self'`: ফর্ম শুধু একই-অরিজিনে জমা দিতে সীমিত

## 5. রেট লিমিটিং নীতি

### অ্যালগরিদম

Redis Sorted Set স্লাইডিং উইন্ডো + Lua অ্যাটমিক স্ক্রিপ্ট, মূল অপারেশন:

```lua
-- 1. 清理窗口外的旧记录
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, windowStart)
-- 2. 检查当前窗口计数
local count = redis.call('ZCARD', KEYS[1])
-- 3. 超限则返回 {0, count}，未超限则 ZADD 并返回 {1, count+1}
if count >= limit then return {0, count} end
redis.call('ZADD', KEYS[1], now, now . '.' . random)  -- 随机后缀避免同毫秒覆盖
redis.call('EXPIRE', KEYS[1], window + 10)
```

Lua স্ক্রিপ্ট Redis সার্ভারে একক থ্রেডে কার্যকর হয়, **স্বাভাবিকভাবেই অ্যাটমিক**, TOCTOU (Time-of-check to Time-of-use) রেস কন্ডিশন দূর করে।

### রেট লিমিট কনফিগারেশন

| রুট | সীমা | উইন্ডো | পরিস্থিতি |
|------|------|------|------|
| ডিফল্ট (সব রুট) | ৬০ বার/মিনিট | ৬০ সে | সাধারণ API |
| `/api/auth/login` | ১০ বার/মিনিট | ৬০ সে | লগইন (ব্রুট-ফোর্স প্রতিরোধ) |
| `/api/auth/register` | ৫ বার/মিনিট | ৬০ সে | রেজিস্ট্রেশন (বাল্ক রেজিস্ট্রেশন প্রতিরোধ) |

### রেসপন্স হেডার

রেট লিমিট ট্রিগার হলে HTTP ৪২৯ এবং JSON বডি ফেরত দেয়:
```json
{"code": 429, "message": "请求过于频繁，请稍后再试", "data": []}
```

সব রেসপন্স (সাধারণ রেসপন্সসহ) নিম্নলিখিত হেডার বহন করে:

| হেডার | বিবরণ |
|----|------|
| X-RateLimit-Limit | বর্তমান উইন্ডোতে অনুমোদিত সর্বোচ্চ অনুরোধ সংখ্যা |
| X-RateLimit-Remaining | বর্তমান উইন্ডোতে অবশিষ্ট অনুরোধ সংখ্যা |
| X-RateLimit-Reset | উইন্ডো রিসেটের Unix টাইমস্ট্যাম্প |
| Retry-After | শুধু রেট লিমিটের সময় পাঠানো হয়, প্রতীক্ষার প্রস্তাবিত সেকেন্ড |

### ডিগ্রেডেশন নীতি

Redis অস্বাভাবিক (কানেকশন টাইমআউট, অনুপলব্ধ ইত্যাদি) হলে **fail-open**:

```php
try {
    $result = Redis::eval($lua, ...);
} catch (\Throwable $e) {
    return $handler($request); // Redis down, 放行所有请求
}
```

স্বল্প সময়ের জন্য রেট লিমিট সুরক্ষা হারানো ভালো, বরং সাধারণ ব্যবসায়িক অনুরোধ ব্লক করার চেয়ে।

### 5.4 অ্যাকাউন্ট লক প্রক্রিয়া

রেট লিমিটিংয়ের পাশাপাশি, লগইন ইন্টারফেস অতিরিক্ত **অ্যাকাউন্ট লক** প্রক্রিয়া যোগ করে, নির্দিষ্ট ব্যবহারকারীদের বিরুদ্ধে লক্ষ্যবস্তু ব্রুট-ফোর্স প্রতিরোধ করে।

**লক প্রক্রিয়া**:

```
登录失败 → Redis INCR account_lockout:{userId} TTL=900s
连续 5 次失败 → Redis SETEX account_locked:{userId} 900 1
            → 返回 429 "账号已被锁定，请15分钟后再试"
            → 清除计数器 DEL account_lockout:{userId}
```

**লক সময়ের আচরণ**:

লক সময়কালে সব লগইন অনুরোধ সরাসরি ৪২৯ ফেরত দেয়, পাসওয়ার্ড যাচাই হয় না, ব্রুট-ফোর্স চেষ্টা সম্পূর্ণভাবে বাধাগ্রস্ত হয়।

**কনফিগারেশন ধ্রুবক**:

| ধ্রুবক | মান | অর্থ |
|------|-----|------|
| MAX_LOGIN_ATTEMPTS | ৫ | সর্বোচ্চ ধারাবাহিক ব্যর্থতা সংখ্যা |
| LOCKOUT_DURATION | ৯০০ | লক স্থায়িত্বকাল (সেকেন্ড), অর্থাৎ ১৫ মিনিট |

দ্রষ্টব্য: অ্যাকাউন্ট লক `userId`-এর উপর ভিত্তি করে, IP-র উপর নয়, তাই IP পরিবর্তন করলে লক বাইপাস হয় না। IP রেট লিমিট (১০ বার/মিনিট) এর সাথে মিলে দ্বৈত সুরক্ষা তৈরি হয়:
- IP স্তর: ১০ বার/মিনিট রেট লিমিট বিতরণকৃত ব্রুট-ফোর্স প্রতিরোধ করে
- অ্যাকাউন্ট স্তর: ৫ ব্যর্থতায় লক লক্ষ্যবস্তু ব্রুট-ফোর্স প্রতিরোধ করে

## 6. প্রমাণীকরণ ও অনুমোদন

### 6.1 JWT প্রমাণীকরণ

AdminAuth মিডলওয়্যার দ্বারা বাস্তবায়িত, প্রমাণীকরণ প্রয়োজন এমন রুট গ্রুপে মাউন্ট করা হয়।

**প্যারামিটার কনফিগারেশন** (`config/plugin/erikwang2013/jwt/jwt`, `.env` থেকে ইনজেক্ট):

| প্যারামিটার | মান | বিবরণ |
|------|-----|------|
| অ্যালগরিদম | HS256 | HMAC-SHA256 সিমেট্রিক সিগনেচার |
| কী | `JWT_SECRET` | এনভায়রনমেন্ট ভেরিয়েবল থেকে ইনজেক্ট, প্রোডাকশনে পরিবর্তন প্রয়োজন |
| access_token TTL | ৭২০০ সে (২ ঘণ্টা) | `JWT_TTL` |
| refresh_token TTL | ১২০৯৬০০ সে (১৪ দিন) | `JWT_REFRESH_TTL` |
| ইস্যুয়ার | `open-admin` | `JWT_ISSUER` |
| অডিয়েন্স | `open-admin` | `JWT_AUDIENCE` |

**টোকেন নিষ্কাশন**: `Authorization: Bearer <token>` হেডার থেকে নিষ্কাশিত, মূল JWT পেতে `Bearer ` উপসর্গ সরানো হয়।

**প্রমাণীকরণ প্রক্রিয়া**:
১. খালি টোকেন → সরাসরি ৪০১ `{"code": 401, "message": "未登录"}`
২. Redis ব্ল্যাকলিস্ট `jwt_blacklist:{md5(token)}` পরীক্ষা → মিলল → ৪০১ `Token已失效，请重新登录`
৩. JWT ডিকোড → ব্যর্থ (মেয়াদোত্তীর্ণ/সিগনেচার মেলেনি) → ৪০১ `Token已过期或无效`
৪. সফল → `$request->adminId` এবং `$request->adminUsername` ইনজেক্ট

**ব্ল্যাকলিস্ট প্রক্রিয়া**: ব্যবহারকারী লগআউট করলে `md5(token)` Redis-এ লেখা হয়, TTL JWT-এর অবশিষ্ট বৈধতার সমান। Redis ব্যর্থ হলে ব্ল্যাকলিস্ট পরীক্ষা এড়িয়ে যায় (fail-open); তখন লগআউট করা টোকেন স্বল্প সময় ব্যবহার হতে পারে, তবে JWT-এর স্বল্প বৈধতা (২ ঘণ্টা) সুরক্ষা হিসেবে কাজ করে।

### 6.2 সমবর্তী সেশন সীমা

টোকেন লিক হওয়ার পর বহু ডিভাইসে অপব্যবহার রোধ করতে, সিস্টেম একই ব্যবহারকারীর একসাথে ধারণযোগ্য বৈধ টোকেনের সংখ্যা সীমিত করে।

**সীমা লজিক**:

```
登录成功 → 签发新 Token
         → 查询当前用户有效 Token 数量: Redis SCARD user_tokens:{userId}
         → 若数量 >= 3（MAX_CONCURRENT_SESSIONS）:
            → 按创建时间升序排列，移除最旧的 Token:
              Redis SREM user_tokens:{userId} <oldest_token_id>
              Redis SETEX jwt_blacklist:{md5(oldest_token)} TTL remaining
         → 将新 Token 加入集合: Redis SADD user_tokens:{userId} <new_token_id>
            Redis SET user_token:{token_id} {userId} EX {TTL}
```

**কনফিগারেশন ধ্রুবক**:

| ধ্রুবক | মান | অর্থ |
|------|-----|------|
| MAX_CONCURRENT_SESSIONS | ৩ | একই ব্যবহারকারীর সর্বোচ্চ সমবর্তী টোকেন সংখ্যা |

**বহিষ্কৃত হওয়ার পরিস্থিতি**: ব্যবহারকারী যখন ৪র্থ ডিভাইসে লগইন করে, ১ম ডিভাইসের টোকেন জোর করে ব্ল্যাকলিস্টে যায়, পরবর্তী অনুরোধ ৪০১ "Token已失效，请重新登录" ফেরত দেয়।

লগআউটে, বর্তমান টোকেন সেট থেকে সরানো হয়। টোকেন স্বাভাবিকভাবে মেয়াদোত্তীর্ণ হলে, Redis কী স্বয়ংক্রিয়ভাবে মেয়াদ শেষ হয়, সেটের সদস্য সংখ্যা কমে যায়।

### 6.3 RBAC অনুমতি মডেল

AdminPermission মিডলওয়্যার দ্বারা বাস্তবায়িত।

**ডেটা মডেল**: User -> Role -> Permission তিন-স্তর সম্পর্ক

- `erik_admin_user` (ব্যবহারকারী টেবিল)
- `erik_admin_user_role` (ব্যবহারকারী-রোল সম্পর্ক টেবিল)
- `erik_admin_role` (রোল টেবিল)
- `erik_admin_role_permission` (রোল-অনুমতি সম্পর্ক টেবিল)
- `erik_admin_permission` (অনুমতি টেবিল)

**অনুমতির ধরন**:
| type | অর্থ | উদাহরণ |
|------|------|------|
| ১ | মেনু অনুমতি | বাম নেভিগেশনের দৃশ্যমানতা নিয়ন্ত্রণ করে |
| ২ | বাটন অনুমতি | পেজের ভেতরের অপারেশন বাটন নিয়ন্ত্রণ করে (নতুন/সম্পাদনা/মুছুন) |
| ৩ | API অনুমতি | ব্যাকএন্ড ইন্টারফেস কল নিয়ন্ত্রণ করে |

API অনুমতি শনাক্তকারী ফরম্যাট: `{method}.{path}`

উদাহরণস্বরূপ:
- `post.admin/user` — ব্যবহারকারী তৈরি
- `put.admin/user` — ব্যবহারকারী সম্পাদনা
- `delete.admin/user` — ব্যবহারকারী মুছে ফেলা
- `get.admin/user` — ব্যবহারকারী তালিকা দেখা

**অনুমোদন প্রক্রিয়া**:
১. `$request->adminId` খালি → অনুমতি (রুটে প্রমাণীকরণ প্রি-কনফিগার করা নেই)
২. ব্যবহারকারী → রোল (স্থিতি `status=0` বিশিষ্ট নিষ্ক্রিয় রোল বাদ) → অনুমতি তালিকা প্রাপ্তি
৩. সুপার অ্যাডমিন (`slug = '*'`) → সরাসরি অনুমতি
৪. `strtolower(method) . '.' . trim(path, '/')` নির্মাণ → অনুমতি তালিকার সাথে তুলনা
৫. মিল না → ৪০৩ `{"code": 403, "message": "无权限访问"}`

**দ্বিতীয় নিশ্চিতকরণ**: BaseController `confirmPassword()` মেথড সরবরাহ করে; সংবেদনশীল অপারেশন (ব্যবহারকারী মুছা, ডেটা এক্সপোর্ট ইত্যাদি) Controller স্তরে বর্তমান পাসওয়ার্ড ইনপুটের অতিরিক্ত প্রয়োজন রাখে, সেশন হাইজ্যাকিংয়ের পর অননুমোদিত অপারেশন প্রতিরোধ করে।

## 8. ডেটা সুরক্ষা

সিস্টেম তিন-স্তরের ডেটা সুরক্ষা নীতি গ্রহণ করে, যা ডেটা প্রবাহের তিনটি পর্যায়ের সাথে সামঞ্জস্যপূর্ণ।

### 8.1 ট্রান্সমিশন স্তর — EncryptionService

`EncryptionService` `erikwang2013/encryption` প্যাকেজ ব্যবহার করে, API অনুরোধ/রেসপন্সের সংবেদনশীল ফিল্ড এনক্রিপ্ট/ডিক্রিপ্ট করে।

**প্রযুক্তিগত বিবরণ**:
- অ্যালগরিদম: `aes-256-cbc-hmac` (ট্যাম্পারিং প্রতিরোধে অন্তর্নির্মিত HMAC সিগনেচার)
- কী: `ENCRYPTION_KEY` এনভায়রনমেন্ট ভেরিয়েবল, স্বয়ংক্রিয়ভাবে ৩২ বাইটে সারিবদ্ধ
- ব্যবহার: ক্লায়েন্ট ও API-এর মধ্যে ফোন নম্বর, আইডি কার্ড নম্বর ইত্যাদি ফিল্ডের ট্রান্সমিশন

**মাস্কিং ইউটিলিটি মেথড**:
- `maskPhone('13812341234')` → `138****1234`
- `maskEmail('abc@example.com')` → `a***@example.com` (ব্যবহারকারীর নাম ২ অক্ষরের বেশি) বা `a**@example.com`

### 8.2 স্টোরেজ স্তর — Encryptable Cast

`AdminUser` মডেল `Erikwang2013\Encryptable\Encryptable` Eloquent cast ব্যবহার করে, সংশ্লিষ্ট ফিল্ড:

- `email` → Encryptable-এ cast, স্বয়ংক্রিয় এনক্রিপ্ট/ডিক্রিপ্ট
- `phone` → Encryptable-এ cast, স্বয়ংক্রিয় এনক্রিপ্ট/ডিক্রিপ্ট
- `id_card` → Encryptable-এ cast, স্বয়ংক্রিয় এনক্রিপ্ট/ডিক্রিপ্ট

ডেটাবেসে লেখার সময় স্বয়ংক্রিয়ভাবে সাইফারটেক্সটে এনক্রিপ্ট হয়, পড়ার সময় স্বয়ংক্রিয়ভাবে প্লেইনটেক্সটে ডিক্রিপ্ট হয়। ডেটাবেস স্টোরেজ কলামের ধরন `VARCHAR(500)`, সাইফারটেক্সট base64 আকারে সংরক্ষিত।

**কী সিস্টেম**: ট্রান্সমিশন স্তর এনক্রিপশন (`ENCRYPTION_KEY`) থেকে স্বাধীন `ENCRYPTABLE_KEY` ব্যবহার করে; একটি কী লিক হলে অন্য স্তর ব্যর্থ হয় না।

কী রোটেশন: `ENCRYPTION_PREVIOUS_KEYS` এনভায়রনমেন্ট ভেরিয়েবল ঐতিহাসিক কীগুলোর তালিকা (কমা-বিভক্ত) সমর্থন করে; পুরনো ডেটা পড়ার সময় ঐতিহাসিক কী দিয়ে ডিক্রিপ্টের চেষ্টা হয়, লেখার সময় বর্তমান কী দিয়ে পুনরায় এনক্রিপ্ট হয়।

### 8.3 প্রদর্শন স্তর — ID অস্পষ্টকরণ ও মাস্কিং

**Hashids ID অস্পষ্টকরণ**: `HashidsService` `erikwang2013/hashids` প্যাকেজ ব্যবহার করে।

- বাহ্যিক API ফেরত দেওয়া ডেটাবেস BIGINT ID hash স্ট্রিংয়ে এনকোড হয় (যেমন `xK3mN9qR2pL7wV8b`)
- ক্লায়েন্ট অনুরোধে hash স্ট্রিং পাঠায়, ব্যাকএন্ড স্বয়ংক্রিয়ভাবে মূল ID-তে ডিকোড করে
- সল্ট `HASHIDS_SALT` এনভায়রনমেন্ট ভেরিয়েবল থেকে ইনজেক্ট; সল্ট ভিন্ন হলে এনকোড/ডিকোড ফলাফল সম্পূর্ণ ভিন্ন
- hash-এর সর্বনিম্ন দৈর্ঘ্য ১৬ অক্ষর, ৬২-অক্ষরের আলফানিউমেরিক ক্যারেক্টারসেট ব্যবহার
- BaseController `encodeId()`, `decodeId()`, `encodeIds()` সুবিধাজনক মেথড সরবরাহ করে

**এক্সপোর্ট মাস্কিং**: Excel/PDF এক্সপোর্টে (ExportController), সংবেদনশীল ফিল্ড একীভূতভাবে মাস্ক হয়:
- ফোন নম্বর: `138****1234`
- ইমেইল: `a***@example.com`
- আইডি কার্ড: সম্পূর্ণভাবে `********` দিয়ে ঢাকা

## 10. security.txt (RFC 9116)

সিস্টেম `/.well-known/security.txt`-এ RFC 9116 মান অনুযায়ী নিরাপত্তা যোগাযোগ তথ্য এন্ডপয়েন্ট সরবরাহ করে, যাতে নিরাপত্তা গবেষকরা দুর্বলতা আবিষ্কার করলে দ্রুত রিপোর্ট চ্যানেল খুঁজে পান।

**অ্যাক্সেসের উপায়**:

```
GET /.well-known/security.txt
```

**রেসপন্স বিষয়বস্তু**:

```text
Contact: mailto:security@erik.xyz
Expires: 2027-05-20T00:00:00.000Z
Preferred-Languages: zh, en
Canonical: https://erik.xyz/.well-known/security.txt
Policy: https://erik.xyz/security-policy
```

**ফিল্ড ব্যাখ্যা**:

| ফিল্ড | বিবরণ |
|------|------|
| Contact | নিরাপত্তা দুর্বলতা রিপোর্টের যোগাযোগ |
| Expires | ফাইলের মেয়াদ শেষের সময়, নিয়মিত আপডেট প্রয়োজন |
| Preferred-Languages | পছন্দের যোগাযোগের ভাষা |
| Canonical | এই ফাইলের ক্যানোনিকাল URL |
| Policy | নিরাপত্তা নীতি/দুর্বলতা প্রকাশ নীতির লিংক |

এই এন্ডপয়েন্ট রেট লিমিটিং, প্রমাণীকরণ ইত্যাদি মিডলওয়্যারের অধীন নয়; যে কেউ সরাসরি অ্যাক্সেস করতে পারে।

## 11. Nginx নিরাপত্তা কনফিগারেশন

প্রজেক্ট প্রোডাকশন পরিবেশের Nginx রিভার্স প্রক্সির নিরাপত্তা শক্তিশালীকরণের জন্য রেফারেন্স কনফিগারেশন হিসেবে `docs/nginx-security.conf` সরবরাহ করে।

**অন্তর্ভুক্ত নিরাপত্তা ব্যবস্থা**:

| কনফিগারেশন আইটেম | কার্যকারিতা |
|--------|------|
| `server_tokens off` | Nginx সংস্করণ নম্বর লুকায় |
| `client_max_body_size 10m` | অনুরোধ বডির আকার সীমিত করে, SecurityMiddleware (erikwang2013/security-php) এর সাথে সমন্বয় |
| `limit_req_zone` | Nginx স্তরে অনুরোধ ফ্রিকোয়েন্সি সীমা |
| `limit_conn_zone` | সমবর্তী কানেকশন সংখ্যা সীমা |
| `add_header` নিরাপত্তা হেডার | Nginx স্তরে X-XSS-Protection ইত্যাদি নিরাপত্তা হেডার যুক্ত করে |
| `if ($request_method)` | Nginx স্তরে অ-মানক HTTP মেথড প্রত্যাখ্যান করে |
| SSL/TLS কনফিগারেশন | আধুনিক TLS 1.2/1.3 কনফিগারেশন, দুর্বল সাইফার সুইট নিষ্ক্রিয় |
| ব্যাকএন্ড হেডার লুকানো | `proxy_hide_header` webman সংস্করণের মতো সংবেদনশীল হেডার সরিয়ে দেয় |

**ব্যবহারের উপায়**: `docs/nginx-security.conf`-এর কনফিগারেশন আপনার Nginx server ব্লকে একীভূত করুন, প্রকৃত ডোমেইন ও সার্টিফিকেট পাথ অনুযায়ী সামঞ্জস্য করুন।
