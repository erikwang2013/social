## 1. गहराई में रक्षा (Defense in Depth) का समग्र दृश्य

सिस्टम 7-परत वाले गहराई में रक्षा मॉडल का उपयोग करता है, जो बाहर से अंदर तक परत दर परत दुर्भावनापूर्ण अनुरोधों को छानता है, यह सुनिश्चित करता है कि किसी भी एक परत के विफल होने पर भी आगे की रक्षा पंक्तियाँ बनी रहें।

पूरी मिडलवेयर श्रृंखला निम्न क्रम में निष्पादित होती है (`config/middleware.php` देखें):

```
请求 → Cors → Locale(Accept-Language) → SecurityMiddleware (erikwang2013/security-php, 31种检测器) → RateLimit → [路由组中间件: AdminAuth → AdminPermission → OperationLog] → Controller
```

| परत | मिडलवेयर/तंत्र | सुरक्षा लक्ष्य |
|----|--------|---------|
| 1 | SecurityMiddleware (erikwang2013/security-php) | 31 प्रकार की आक्रमण जाँच + HTTP विधि सत्यापन + अनुरोध बॉडी आकार सीमा + Content-Type सत्यापन + CSRF + IP आक्रमण एस्कलेशन ब्लैकलिस्ट |
| 2 | Cors | क्रॉस-ओरिजिन सुरक्षा + सुरक्षा हेडर इंजेक्शन |
| 3 | RateLimit | Redis स्लाइडिंग विंडो रेट लिमिटिंग, ब्रूट-फोर्स से बचाव |
| 4 | AdminAuth | JWT प्रमाणीकरण + ब्लैकलिस्ट लॉगआउट |
| 5 | AdminPermission | RBAC method.path ग्रैन्युलैरिटी प्रमाणीकरण |
| 6 | OperationLog | संचालन ऑडिट + स्रोत एंड ट्रैकिंग |
| 7 | डेटा एन्क्रिप्शन | Hashids ID अस्पष्टीकरण + Encryptable DB एन्क्रिप्शन + EncryptionService ट्रांसमिशन एन्क्रिप्शन |

फ्रंटएंड की तीन परतें (Flutter) अलग से अपना इनपुट सत्यापन करती हैं; बैकएंड किसी पर भरोसा नहीं करता, प्रत्येक परत स्वतंत्र रूप से रक्षा करती है।

## 2. आक्रमण जाँच इंजन

## 2. 攻击检测引擎 (erikwang2013/security-php)

आक्रमण जाँच को स्वयं के SecurityMiddleware से समर्पित सुरक्षा पैकेज `erikwang2013/security-php` v1.1+ में स्थानांतरित किया गया है, जो **31 डिटेक्टर** प्रदान करता है, जो 5 बड़ी आक्रमण श्रेणियों को कवर करते हैं।

### 2.1 डिटेक्टर वर्गीकरण

**इंजेक्शन आक्रमण (11 प्रकार):** XSS, SQL इंजेक्शन, कमांड इंजेक्शन, NoSQL इंजेक्शन, LDAP इंजेक्शन, XPath इंजेक्शन, JNDI/Log4Shell, SSI सर्वर-साइड इंक्लूज़न, GraphQL इंजेक्शन, SSTI टेम्पलेट इंजेक्शन

**प्रोटोकॉल और अनुरोध आक्रमण (9 प्रकार):** SSRF, XXE, HTTP रिस्पॉन्स हेडर इंजेक्शन, Host हेडर आक्रमण, Request Smuggling, Open Redirect, CORS बाइपास, WebSocket हाइजैकिंग, DNS Rebinding

**HTTP प्रोटोकॉल परत सत्यापन (6 प्रकार):** HTTP विधि सत्यापन (405), अनुरोध बॉडी आकार सीमा (413), Content-Type सत्यापन (415), CSRF Origin जाँच, IP आक्रमण एस्कलेशन ब्लैकलिस्ट, संवेदनशील डेटा लीक जाँच

**डेटा और सीरियलाइज़ेशन आक्रमण (5 प्रकार):** PHP डी-सीरियलाइज़ेशन, CSV फ़ॉर्मूला इंजेक्शन, ईमेल हेडर इंजेक्शन, JWT आक्रमण (संरचनात्मक विश्लेषण), JS Prototype Pollution

**फ़ाइल और पाथ आक्रमण (2 प्रकार):** पाथ ट्रैवर्सल, दुर्भावनापूर्ण फ़ाइल अपलोड

### 2.2 हैंडलिंग मोड

प्रत्येक डिटेक्टर स्वतंत्र रूप से दो मोड का समर्थन करता है:
- `block` — आक्रमण का पता चलते ही रोकता है, कॉन्फ़िगर किया गया स्टेटस कोड लौटाता है
- `log` — केवल लॉग करता है, रोकता नहीं (`header_injection`, `ssti`, `nosql_injection` डिफ़ॉल्ट रूप से log मोड में होते हैं, गलत सकारात्मक रोकने के लिए)

### 2.3 IP आक्रमण एस्कलेशन ब्लैकलिस्ट

एक ही IP द्वारा 60 सेकंड में 5 बार आक्रमण जाँच ट्रिगर होना → 15 मिनट के लिए स्वचालित बैन। स्टोरेज बैकएंड वैकल्पिक रूप से Redis (वितरित), File (सिंगल-मशीन JSON) या Cache (उच्च-समवर्ती स्वतंत्र फ़ाइल) हो सकता है; वर्तमान कॉन्फ़िगरेशन Redis स्टोरेज का उपयोग करता है।

### 2.4 सुरक्षा लॉग

फ़ाइल स्थान: `runtime/logs/security.log` (स्वचालित रोटेशन, 10MB/फ़ाइल)

## 4. सुरक्षा रिस्पॉन्स हेडर

सभी हेडर `Cors` मिडलवेयर में इंजेक्ट किए जाते हैं, `$response->withHeaders()` के माध्यम से हर रिस्पॉन्स में जोड़े जाते हैं।

| हेडर | मान | कार्य |
|----|-----|------|
| Access-Control-Allow-Origin | `*` | किसी भी ओरिजिन को क्रॉस-डोमेन की अनुमति (इंट्रानेट एडमिन पैनल परिदृश्य) |
| Access-Control-Allow-Methods | `GET,POST,PUT,DELETE,OPTIONS` | अनुमत विधियों का सेट |
| Access-Control-Allow-Headers | `Authorization,Content-Type,API-Version` | अनुमत कस्टम हेडर |
| Access-Control-Max-Age | `86400` | प्रीफ़्लाइट अनुरोध कैश 24 घंटे |
| X-Content-Type-Options | `nosniff` | ब्राउज़र MIME स्निफ़िंग पर प्रतिबंध |
| X-Frame-Options | `DENY` | सभी iframe एम्बेडिंग पर प्रतिबंध, क्लिकजैकिंग रोकता है |
| X-XSS-Protection | `1; mode=block` | ब्राउज़र का अंतर्निहित XSS फ़िल्टर सक्षम करता है और पेज रेंडरिंग रोकता है |
| Referrer-Policy | `strict-origin-when-cross-origin` | समान ओरिजिन पर पूर्ण URL, क्रॉस-ओरिजिन पर केवल डोमेन भेजता है |
| Permissions-Policy | `camera=(), microphone=(), geolocation=()` | पूरी साइट पर कैमरा/माइक्रोफ़ोन/जियोलोकेशन API अक्षम |

OPTIONS प्रीफ़्लाइट अनुरोध सीधे 204 खाली रिस्पॉन्स लौटाते हैं, आगे की मिडलवेयर श्रृंखला में प्रवेश नहीं करते।

### 4.2 Content-Security-Policy (CSP)

अन्य सुरक्षा हेडर के साथ Cors मिडलवेयर में इंजेक्ट किया जाता है, गहराई में रक्षा प्रदान करता है, ब्राउज़र द्वारा लोड और निष्पादित किए जा सकने वाले संसाधनों के स्रोतों को सीमित करता है।

| हेडर | मान | कार्य |
|----|-----|------|
| Content-Security-Policy | `default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'` | स्क्रिप्ट/स्टाइल/इमेज/कनेक्शन/फ्रेम/फ़ॉर्म आदि संसाधनों के स्रोत सीमित करता है |
| X-Permitted-Cross-Domain-Policies | `none` | Adobe Flash/PDF आदि क्रॉस-डोमेन पॉलिसी फ़ाइल लोडिंग पर प्रतिबंध |

CSP नीति के मुख्य बिंदु:
- `default-src 'self'`: डिफ़ॉल्ट रूप से केवल समान-ओरिजिन संसाधनों की अनुमति
- `script-src 'self' 'unsafe-inline' 'unsafe-eval'`: समान-ओरिजिन स्क्रिप्ट + इनलाइन स्क्रिप्ट (Flutter Web के लिए आवश्यक) + eval (Flutter Web डिबगिंग के लिए आवश्यक) की अनुमति
- `frame-ancestors 'none'`: किसी भी पेज द्वारा iframe एम्बेडिंग पर प्रतिबंध, X-Frame-Options: DENY के साथ दोहरी सुरक्षा
- `base-uri 'self'`: `<base>` टैग को केवल समान-ओरिजिन की ओर इंगित करने तक सीमित करता है
- `form-action 'self'`: फ़ॉर्म केवल समान-ओरिजिन पर सबमिट करने तक सीमित करता है

## 5. रेट लिमिटिंग नीति

### एल्गोरिदम

Redis Sorted Set स्लाइडिंग विंडो + Lua एटॉमिक स्क्रिप्ट, मुख्य संचालन:

```lua
-- 1. 清理窗口外的旧记录
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, windowStart)
-- 2. 检查当前窗口计数
local count = redis.call('ZCARD', KEYS[1])
-- 3. 超限则返回 {0, count}，未超限则 ZADD 并返回 {1, count+1}
if count >= limit then return {0, count} end
redis.call('ZADD', KEYS[1], now, now . '.' . random)  -- 随机后缀避免同毫秒覆盖
redis.call('EXPIRE', KEYS[1], window + 10)
```

Lua स्क्रिप्ट Redis सर्वर पर सिंगल-थ्रेड में निष्पादित होती है, **स्वाभाविक रूप से एटॉमिक**, TOCTOU (Time-of-check to Time-of-use) रेस कंडीशन समाप्त करती है।

### रेट लिमिट कॉन्फ़िगरेशन

| रूट | सीमा | विंडो | परिदृश्य |
|------|------|------|------|
| डिफ़ॉल्ट (सभी रूट) | 60 बार/मिनट | 60s | सामान्य API |
| `/api/auth/login` | 10 बार/मिनट | 60s | लॉगिन (ब्रूट-फोर्स रोकथाम) |
| `/api/auth/register` | 5 बार/मिनट | 60s | रजिस्ट्रेशन (बल्क रजिस्ट्रेशन रोकथाम) |

### रिस्पॉन्स हेडर

रेट लिमिट ट्रिगर होने पर HTTP 429 और JSON body लौटाता है:
```json
{"code": 429, "message": "请求过于频繁，请稍后再试", "data": []}
```

सभी रिस्पॉन्स (सामान्य रिस्पॉन्स सहित) निम्न हेडर ले जाते हैं:

| हेडर | विवरण |
|----|------|
| X-RateLimit-Limit | वर्तमान विंडो में अनुमत अधिकतम अनुरोध संख्या |
| X-RateLimit-Remaining | वर्तमान विंडो में शेष उपलब्ध अनुरोध संख्या |
| X-RateLimit-Reset | विंडो रीसेट का Unix टाइमस्टैम्प |
| Retry-After | केवल रेट लिमिट पर भेजा जाता है, प्रतीक्षा के सुझाए गए सेकंड |

### डिग्रेडेशन नीति

Redis असामान्य (कनेक्शन टाइमआउट, अनुपलब्ध आदि) होने पर **fail-open**:

```php
try {
    $result = Redis::eval($lua, ...);
} catch (\Throwable $e) {
    return $handler($request); // Redis down, 放行所有请求
}
```

थोड़े समय के लिए रेट लिमिट सुरक्षा खोना बेहतर है, बजाय सामान्य व्यावसायिक अनुरोधों को रोकने के।

### 5.4 खाता लॉक तंत्र

रेट लिमिटिंग के अलावा, लॉगिन इंटरफ़ेस में अतिरिक्त **खाता लॉक** तंत्र जोड़ा गया है, जो विशिष्ट उपयोगकर्ताओं के विरुद्ध लक्षित ब्रूट-फोर्स रोकता है।

**लॉक प्रक्रिया**:

```
登录失败 → Redis INCR account_lockout:{userId} TTL=900s
连续 5 次失败 → Redis SETEX account_locked:{userId} 900 1
            → 返回 429 "账号已被锁定，请15分钟后再试"
            → 清除计数器 DEL account_lockout:{userId}
```

**लॉक अवधि के दौरान व्यवहार**:

लॉक अवधि के दौरान सभी लॉगिन अनुरोध सीधे 429 लौटाते हैं, पासवर्ड सत्यापन नहीं होता, ब्रूट-फोर्स प्रयास पूरी तरह अवरुद्ध होते हैं।

**कॉन्फ़िगरेशन स्थिरांक**:

| स्थिरांक | मान | अर्थ |
|------|-----|------|
| MAX_LOGIN_ATTEMPTS | 5 | अधिकतम लगातार विफलताएँ |
| LOCKOUT_DURATION | 900 | लॉक अवधि (सेकंड), अर्थात 15 मिनट |

ध्यान दें: खाता लॉक `userId` पर आधारित है, IP पर नहीं, इसलिए IP बदलने से लॉक बाइपास नहीं होता। IP रेट लिमिट (10 बार/मिनट) के साथ मिलकर दोहरी सुरक्षा बनती है:
- IP स्तर: 10 बार/मिनट की रेट लिमिट वितरित ब्रूट-फोर्स रोकती है
- खाता स्तर: 5 विफलताओं पर लॉक लक्षित ब्रूट-फोर्स रोकता है

## 6. प्रमाणीकरण और प्राधिकरण

### 6.1 JWT प्रमाणीकरण

AdminAuth मिडलवेयर द्वारा कार्यान्वित, प्रमाणीकरण आवश्यक रूट समूहों पर माउंट किया जाता है।

**पैरामीटर कॉन्फ़िगरेशन** (`config/plugin/erikwang2013/jwt/jwt`, `.env` से इंजेक्ट):

| पैरामीटर | मान | विवरण |
|------|-----|------|
| एल्गोरिदम | HS256 | HMAC-SHA256 सममित हस्ताक्षर |
| कुंजी | `JWT_SECRET` | पर्यावरण चर से इंजेक्ट, उत्पादन में बदलना आवश्यक |
| access_token TTL | 7200s (2h) | `JWT_TTL` |
| refresh_token TTL | 1209600s (14d) | `JWT_REFRESH_TTL` |
| जारीकर्ता | `open-admin` | `JWT_ISSUER` |
| श्रोता | `open-admin` | `JWT_AUDIENCE` |

**Token निष्कर्षण**: `Authorization: Bearer <token>` हेडर से निकाला जाता है, मूल JWT पाने के लिए `Bearer ` उपसर्ग हटाया जाता है।

**प्रमाणीकरण प्रक्रिया**:
1. खाली token → सीधे 401 `{"code": 401, "message": "未登录"}`
2. Redis ब्लैकलिस्ट `jwt_blacklist:{md5(token)}` जाँच → मिला → 401 `Token已失效，请重新登录`
3. JWT decode → विफल (समाप्त/हस्ताक्षर मेल नहीं) → 401 `Token已过期或无效`
4. सफल → `$request->adminId` और `$request->adminUsername` इंजेक्ट करता है

**ब्लैकलिस्ट तंत्र**: उपयोगकर्ता लॉगआउट करते समय `md5(token)` Redis में लिखा जाता है, TTL JWT की शेष वैधता के बराबर। Redis विफल होने पर ब्लैकलिस्ट जाँच छोड़ दी जाती है (fail-open); इस स्थिति में लॉगआउट किए गए Token थोड़े समय के लिए उपयोग हो सकते हैं, लेकिन JWT की छोटी वैधता (2h) सुरक्षा के रूप में काम करती है।

### 6.2 समवर्ती सत्र सीमा

Token लीक होने के बाद कई डिवाइसों पर दुरुपयोग रोकने के लिए, सिस्टम एक ही उपयोगकर्ता के पास एक साथ रखे जा सकने वाले वैध Token की संख्या सीमित करता है।

**सीमा तर्क**:

```
登录成功 → 签发新 Token
         → 查询当前用户有效 Token 数量: Redis SCARD user_tokens:{userId}
         → 若数量 >= 3（MAX_CONCURRENT_SESSIONS）:
            → 按创建时间升序排列，移除最旧的 Token:
              Redis SREM user_tokens:{userId} <oldest_token_id>
              Redis SETEX jwt_blacklist:{md5(oldest_token)} TTL remaining
         → 将新 Token 加入集合: Redis SADD user_tokens:{userId} <new_token_id>
            Redis SET user_token:{token_id} {userId} EX {TTL}
```

**कॉन्फ़िगरेशन स्थिरांक**:

| स्थिरांक | मान | अर्थ |
|------|-----|------|
| MAX_CONCURRENT_SESSIONS | 3 | एक ही उपयोगकर्ता के लिए अधिकतम समवर्ती Token संख्या |

**बाहर निकाले जाने का परिदृश्य**: जब उपयोगकर्ता चौथे डिवाइस पर लॉगिन करता है, तो पहले डिवाइस का Token बलपूर्वक ब्लैकलिस्ट में जाता है, आगे के अनुरोध 401 "Token已失效，请重新登录" लौटाते हैं।

लॉगआउट पर, वर्तमान Token सेट से हटा दिया जाता है। Token स्वाभाविक रूप से समाप्त होने पर, Redis कुंजी स्वतः समाप्त होती है, सेट के सदस्य घटते हैं।

### 6.3 RBAC अनुमति मॉडल

AdminPermission मिडलवेयर द्वारा कार्यान्वित।

**डेटा मॉडल**: User -> Role -> Permission तीन-परत संबंध

- `erik_admin_user` (उपयोगकर्ता तालिका)
- `erik_admin_user_role` (उपयोगकर्ता-रोल संबंध तालिका)
- `erik_admin_role` (रोल तालिका)
- `erik_admin_role_permission` (रोल-अनुमति संबंध तालिका)
- `erik_admin_permission` (अनुमति तालिका)

**अनुमति प्रकार**:
| type | अर्थ | उदाहरण |
|------|------|------|
| 1 | मेनू अनुमति | बाएँ नेविगेशन की दृश्यता नियंत्रित करता है |
| 2 | बटन अनुमति | पेज के भीतर संचालन बटन नियंत्रित करता है (नया/संपादित/हटाएँ) |
| 3 | API अनुमति | बैकएंड इंटरफ़ेस कॉल नियंत्रित करता है |

API अनुमति पहचानकर्ता प्रारूप: `{method}.{path}`

उदाहरण के लिए:
- `post.admin/user` — उपयोगकर्ता बनाना
- `put.admin/user` — उपयोगकर्ता संपादित करना
- `delete.admin/user` — उपयोगकर्ता हटाना
- `get.admin/user` — उपयोगकर्ता सूची देखना

**प्रमाणीकरण प्रक्रिया**:
1. `$request->adminId` खाली → अनुमति दें (रूट पर प्रमाणीकरण प्री-कॉन्फ़िगर नहीं)
2. उपयोगकर्ता → रोल (स्थिति `status=0` वाले अक्षम रोल छोड़ें) → अनुमति सूची प्राप्त करें
3. सुपर एडमिन (`slug = '*'`) → सीधे अनुमति दें
4. `strtolower(method) . '.' . trim(path, '/')` बनाएँ → अनुमति सूची से तुलना करें
5. मेल नहीं → 403 `{"code": 403, "message": "无权限访问"}`

**द्वितीयक पुष्टि**: BaseController `confirmPassword()` विधि प्रदान करता है; संवेदनशील संचालन (उपयोगकर्ता हटाना, डेटा निर्यात आदि) Controller स्तर पर वर्तमान पासवर्ड दर्ज करने की अतिरिक्त आवश्यकता रखते हैं, सत्र हाइजैकिंग के बाद अनधिकृत संचालन रोकते हैं।

## 7. ऑडिट लॉग

### 7.1 संचालन लॉग

OperationLog मिडलवेयर POST / PUT / DELETE अनुरोधों के लिए स्वचालित रूप से संचालन लॉग रिकॉर्ड करता है। GET अनुरोध रिकॉर्ड नहीं होते।

**रिकॉर्ड किए गए फ़ील्ड**:

| फ़ील्ड | स्रोत | विवरण |
|------|------|------|
| id | SnowflakeService::generate() | वैश्विक रूप से अद्वितीय ID |
| user_id | `$request->adminId` | संचालक ID, लॉगिन न होने पर 0 |
| action | `$request->method()` | method के बराबर |
| method | `$request->method()` | POST / PUT / DELETE |
| path | `$request->path()` | अनुरोध पथ |
| ip | `$request->getRealIp()` | क्लाइंट का वास्तविक IP |
| source | detectSource() | क्लाइंट स्रोत प्लेटफ़ॉर्म |
| input | अनुरोध body (मास्क किया गया JSON) | संचालन द्वारा सबमिट किया गया डेटा |

**संवेदनशील फ़ील्ड फ़िल्टर**: अनुरोध बॉडी को पुनरावृत्त रूप से स्कैन करता है; निम्न फ़ील्ड के मान `***` से बदले जाते हैं:

`password`, `old_password`, `new_password`, `new_password_confirmation`, `token`, `secret`, `access_token`, `refresh_token`

**स्रोत एंड जाँच** (`detectSource()`): प्राथमिकता क्रम:

1. पहले `X-Client-Platform` कस्टम हेडर पढ़ता है (नेटिव क्लाइंट द्वारा स्पष्ट रूप से घोषित)
2. User-Agent स्ट्रिंग से अनुमान लगाने पर डिग्रेड (`detectSource()` विधि की जाँच क्रम):

| प्लेटफ़ॉर्म | UA कीवर्ड |
|------|----------|
| iPadOS | `iPad` |
| macOS | `Macintosh`, `Mac OS` |
| Windows | `Windows` |
| Linux | `Linux` |
| iOS | `iPhone`, `iOS`, `CFNetwork` |
| Android | `Android` |
| HarmonyOS | `HarmonyOS`, `OpenHarmony` |
| Web | फ़ॉलबैक डिफ़ॉल्ट मान |

**गलती सहनशीलता**: लॉग लिखने में त्रुटि व्यावसायिक अनुरोध को अवरुद्ध नहीं करती (`catch (\Throwable)` मौन रूप से निगल लेता है)।

### 7.2 सुरक्षा लॉग

**फ़ाइल स्थान**: `runtime/logs/security.log`

**रिकॉर्ड की गई सामग्री**:

## 8. डेटा सुरक्षा

सिस्टम तीन-परत डेटा सुरक्षा नीति अपनाता है, जो डेटा प्रवाह के तीन चरणों के अनुरूप है।

### 8.1 परिवहन परत — EncryptionService

`EncryptionService` `erikwang2013/encryption` पैकेज का उपयोग करता है, API अनुरोध/रिस्पॉन्स में संवेदनशील फ़ील्ड को एन्क्रिप्ट/डिक्रिप्ट करता है।

**तकनीकी विवरण**:
- एल्गोरिदम: `aes-256-cbc-hmac` (छेड़छाड़ रोकने के लिए अंतर्निहित HMAC हस्ताक्षर)
- कुंजी: `ENCRYPTION_KEY` पर्यावरण चर, स्वतः 32 बाइट्स पर संरेखित
- उपयोग: क्लाइंट और API के बीच फ़ोन नंबर, आईडी कार्ड नंबर जैसे फ़ील्ड का परिवहन

**मास्किंग उपयोगिता विधियाँ**:
- `maskPhone('13812341234')` → `138****1234`
- `maskEmail('abc@example.com')` → `a***@example.com` (उपयोगकर्ता नाम 2 वर्णों से अधिक) या `a**@example.com`

### 8.2 भंडारण परत — Encryptable Cast

`AdminUser` मॉडल `Erikwang2013\Encryptable\Encryptable` Eloquent cast का उपयोग करता है, संबंधित फ़ील्ड:

- `email` → Encryptable में cast, स्वचालित एन्क्रिप्ट/डिक्रिप्ट
- `phone` → Encryptable में cast, स्वचालित एन्क्रिप्ट/डिक्रिप्ट
- `id_card` → Encryptable में cast, स्वचालित एन्क्रिप्ट/डिक्रिप्ट

डेटाबेस में लिखते समय स्वचालित रूप से साइफरटेक्स्ट में एन्क्रिप्ट होता है, पढ़ते समय स्वचालित रूप से प्लेनटेक्स्ट में डिक्रिप्ट होता है। डेटाबेस स्टोरेज कॉलम प्रकार `VARCHAR(500)` है, साइफरटेक्स्ट base64 रूप में संग्रहीत होता है।

**कुंजी प्रणाली**: परिवहन परत एन्क्रिप्शन (`ENCRYPTION_KEY`) से स्वतंत्र `ENCRYPTABLE_KEY` का उपयोग करती है; एक कुंजी के लीक होने से दूसरी परत विफल नहीं होती।

कुंजी रोटेशन: `ENCRYPTION_PREVIOUS_KEYS` पर्यावरण चर ऐतिहासिक कुंजियों की सूची (कॉमा-पृथक) का समर्थन करता है; पुराना डेटा पढ़ते समय ऐतिहासिक कुंजियों से डिक्रिप्ट करने का प्रयास होता है, लिखते समय वर्तमान कुंजी से पुनः एन्क्रिप्ट होता है।

### 8.3 प्रदर्शन परत — ID अस्पष्टीकरण और मास्किंग

**Hashids ID अस्पष्टीकरण**: `HashidsService` `erikwang2013/hashids` पैकेज का उपयोग करता है।

- बाहरी API द्वारा लौटाए गए डेटाबेस BIGINT ID hash स्ट्रिंग में एन्कोड होते हैं (जैसे `xK3mN9qR2pL7wV8b`)
- क्लाइंट अनुरोध में hash स्ट्रिंग भेजता है, बैकएंड स्वचालित रूप से मूल ID में डिकोड करता है
- साल्ट `HASHIDS_SALT` पर्यावरण चर से इंजेक्ट होता है; साल्ट अलग होने पर एन्कोड/डिकोड परिणाम पूरी तरह भिन्न होते हैं
- hash की न्यूनतम लंबाई 16 वर्ण, 62-वर्ण अल्फ़ान्यूमेरिक वर्णसेट का उपयोग
- BaseController `encodeId()`, `decodeId()`, `encodeIds()` सुविधाजनक विधियाँ प्रदान करता है

**निर्यात मास्किंग**: Excel/PDF निर्यात में (ExportController), संवेदनशील फ़ील्ड समान रूप से मास्क होते हैं:
- फ़ोन नंबर: `138****1234`
- ईमेल: `a***@example.com`
- आईडी कार्ड: पूरी तरह से `********` से ढका जाता है

| ENCRYPTION_KEY | API परिवहन परत एन्क्रिप्शन कुंजी | erikwang2013/encryption | 32 बाइट्स यादृच्छिक स्ट्रिंग |
| ENCRYPTABLE_KEY | DB भंडारण परत एन्क्रिप्शन कुंजी | erikwang2013/encryptable | 32 बाइट्स यादृच्छिक स्ट्रिंग, परिवहन कुंजी से भिन्न |

**सुरक्षा आवश्यकताएँ**:
- `.env` फ़ाइल `.gitignore` में शामिल है, रिपॉज़िटरी में कमिट करना सख्त वर्जित है
- `.env.example` सार्वजनिक टेम्पलेट फ़ाइल है, इसमें वास्तविक कुंजियाँ नहीं होतीं
- उत्पादन में सभी डिफ़ॉल्ट कुंजियों को यादृच्छिक स्ट्रिंग में बदलना **अनिवार्य** है
- कुंजी उत्पन्न करने के लिए `openssl rand -base64 32` का उपयोग करने की सलाह

## 10. security.txt (RFC 9116)

सिस्टम `/.well-known/security.txt` पर RFC 9116 मानक के अनुरूप सुरक्षा संपर्क जानकारी एंडपॉइंट प्रदान करता है, ताकि सुरक्षा शोधकर्ता भेद्यता खोजने पर तुरंत रिपोर्ट चैनल पा सकें।

**पहुँच विधि**:

```
GET /.well-known/security.txt
```

**रिस्पॉन्स सामग्री**:

```text
Contact: mailto:security@erik.xyz
Expires: 2027-05-20T00:00:00.000Z
Preferred-Languages: zh, en
Canonical: https://erik.xyz/.well-known/security.txt
Policy: https://erik.xyz/security-policy
```

**फ़ील्ड विवरण**:

| फ़ील्ड | विवरण |
|------|------|
| Contact | सुरक्षा भेद्यता रिपोर्ट संपर्क |
| Expires | फ़ाइल की समाप्ति तिथि, नियमित अपडेट आवश्यक |
| Preferred-Languages | पसंदीदा संवाद भाषाएँ |
| Canonical | इस फ़ाइल का कैनोनिकल URL |
| Policy | सुरक्षा नीति/भेद्यता प्रकटीकरण नीति लिंक |

यह एंडपॉइंट रेट लिमिटिंग, प्रमाणीकरण जैसे मिडलवेयर से मुक्त है; कोई भी सीधे एक्सेस कर सकता है।

## 11. Nginx सुरक्षा कॉन्फ़िगरेशन

प्रोजेक्ट उत्पादन परिवेश के Nginx रिवर्स प्रॉक्सी के सुरक्षा सुदृढ़ीकरण हेतु संदर्भ कॉन्फ़िगरेशन के रूप में `docs/nginx-security.conf` प्रदान करता है।

**शामिल सुरक्षा उपाय**:

| कॉन्फ़िगरेशन आइटम | कार्य |
|--------|------|
| `server_tokens off` | Nginx संस्करण संख्या छिपाता है |
| `client_max_body_size 10m` | अनुरोध बॉडी आकार सीमित करता है, SecurityMiddleware (erikwang2013/security-php) के साथ समन्वय |
| `limit_req_zone` | Nginx स्तर पर अनुरोध आवृत्ति सीमा |
| `limit_conn_zone` | समवर्ती कनेक्शन संख्या सीमा |
| `add_header` सुरक्षा हेडर | Nginx स्तर पर X-XSS-Protection आदि सुरक्षा हेडर जोड़ता है |
| `if ($request_method)` | Nginx स्तर पर गैर-मानक HTTP विधियाँ अस्वीकार करता है |
| SSL/TLS कॉन्फ़िगरेशन | आधुनिक TLS 1.2/1.3 कॉन्फ़िगरेशन, कमज़ोर साइफर सूट अक्षम |
| बैकएंड हेडर छिपाना | `proxy_hide_header` webman संस्करण जैसे संवेदनशील हेडर हटाता है |

**उपयोग विधि**: `docs/nginx-security.conf` की कॉन्फ़िगरेशन को अपने Nginx server ब्लॉक में विलय करें, वास्तविक डोमेन और प्रमाणपत्र पथ के अनुसार समायोजित करें।

## 12. खतरा मॉडल

### 12.1 संरक्षित खतरे

| खतरा प्रकार | आक्रमण वेक्टर | रक्षा परतें |
|----------|---------|---------|
| HTTP विधि दुरुपयोग | TRACE/TRACK XST आक्रमण, CONNECT टनल प्रॉक्सी, WebDAV विधि जाँच | SecurityMiddleware http_method डिटेक्टर 405 विधि व्हाइटलिस्ट |
| लक्षित ब्रूट-फोर्स | विशिष्ट उपयोगकर्ता के विरुद्ध बार-बार पासवर्ड प्रयास | खाता लॉक (5 विफलताओं पर 15 मिनट लॉक) + RateLimit (लॉगिन 10/मिनट) + Captcha |
| ब्रूट-फोर्स | वितरित IP से बार-बार उपयोगकर्ता/पासवर्ड प्रयास | RateLimit (लॉगिन 10/मिनट) + Captcha |
| XSS क्रॉस-साइट स्क्रिप्टिंग | `<script>`, onerror, javascript: | SecurityMiddleware (erikwang2013/security-php) (5 मोड) + X-XSS-Protection रिस्पॉन्स हेडर + CSP |
| SQL इंजेक्शन | UNION SELECT, OR 1=1, टिप्पणी बाइपास | SecurityMiddleware (erikwang2013/security-php) (6 मोड) + Eloquent ORM पैरामीटराइज़्ड क्वेरी |
| CSRF क्रॉस-साइट अनुरोध जालसाजी | दुर्भावनापूर्ण वेबसाइट अनुरोध भेजती है | SecurityMiddleware (erikwang2013/security-php) Origin/Referer सत्यापन |
| पाथ ट्रैवर्सल | `../../etc/passwd` | SecurityMiddleware (erikwang2013/security-php) पाथ ट्रैवर्सल मोड + UploadController एक्सटेंशन व्हाइटलिस्ट |
| कमांड इंजेक्शन | `;ls`, `` `whoami` ``, `$(cat ...)` | SecurityMiddleware (erikwang2013/security-php) (4 मोड) |
| सत्र हाइजैकिंग | JWT Token चोरी | JWT छोटी वैधता (2h) + ब्लैकलिस्ट लॉगआउट + संवेदनशील संचालन पर द्वितीयक पासवर्ड पुष्टि |
| ID एन्यूमरेशन | संख्यात्मक ID से डेटा मात्रा का अनुमान | Hashids द्वारा यादृच्छिक स्ट्रिंग में अस्पष्टीकरण |
| डेटा लीक | DB चोरी / मैन-इन-द-मिडिल / लॉग लीक | तीन-परत एन्क्रिप्शन/मास्किंग + OperationLog संवेदनशील फ़ील्ड फ़िल्टर |
| DoS आक्रमण | विशाल अनुरोध बॉडी / उच्च आवृत्ति अनुरोध | अनुरोध बॉडी 10MB सीमा + RateLimit 60/मिनट + IP ब्लैकलिस्ट |
| विशेषाधिकार वृद्धि | कम-विशेषाधिकार वाले उपयोगकर्ता प्रशासन इंटरफ़ेस तक पहुँचते हैं | RBAC method.path ग्रैन्युलैरिटी प्रमाणीकरण |
| फ़ाइल अपलोड आक्रमण | shell.php.png डबल एक्सटेंशन | SecurityMiddleware (erikwang2013/security-php) दुर्भावनापूर्ण फ़ाइल जाँच |

### 12.2 ज्ञात सीमाएँ

| सीमा | प्रभाव क्षेत्र | शमन उपाय |
|------|---------|---------|
| CSRF सुरक्षा केवल ब्राउज़र के लिए प्रभावी | गैर-ब्राउज़र क्लाइंट (curl, Postman, मोबाइल App) Origin/Referer जाँच छोड़ सकते हैं | गैर-ब्राउज़र क्लाइंट स्वाभाविक रूप से CSRF से प्रभावित नहीं होते; Cookie के स्थान पर JWT प्रमाणीकरण पर निर्भरता |
| Redis अनुपलब्ध होने पर रेट लिमिट और ब्लैकलिस्ट fail-open में डिग्रेड | आक्रमणकारी रेट लिमिट और उच्च-आवृत्ति अवरोधन बाइपास कर सकते हैं | Redis उपलब्धता अलर्ट निगरानी; IP ब्लैकलिस्ट file/redis/cache तीन बैकएंड डिग्रेडेशन समर्थित |
| कोई स्वतंत्र WAF इंजन नहीं | रेगेक्स-आधारित जाँच, समर्पित WAF नियम इंजन नहीं | उत्पादन में Nginx ModSecurity या Cloudflare WAF लगाने की सलाह |
| JWT स्टेटलेस, सक्रिय रूप से अमान्य नहीं किया जा सकता | Token समाप्ति से पहले सर्वर से सक्रिय रूप से रद्द नहीं किया जा सकता (ब्लैकलिस्ट के अलावा) | ब्लैकलिस्ट + छोटा 2h TTL जोखिम विंडो कम करता है |
| एडमिन एंडपॉइंट पर विशेष रेट लिमिट नहीं | एडमिन इंटरफ़ेस सामान्य इंटरफ़ेस के साथ 60/मिनट डिफ़ॉल्ट साझा करता है | एडमिन संचालन आवृत्ति स्वाभाविक रूप से कम, फिलहाल भेद आवश्यक नहीं |
| PCRE बैकट्रैकिंग सीमा | पैकेज में 1,000,000 बैकट्रैकिंग सीमा + finally पुनर्प्राप्ति, अत्यंत जटिल इनपुट पर प्रदर्शन जोखिम | अनुरोध बॉडी आकार सीमा (10MB) फ़ॉलबैक |
