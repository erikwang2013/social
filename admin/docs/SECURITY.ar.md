## 1. النظرة العامة للدفاع المتعمق

يعتمد النظام نموذج الدفاع المتعمق من 7 طبقات، حيث يتم تصفية الطلبات الخبيثة طبقة بعد طبقة من الخارج إلى الداخل، بما يضمن أنه حتى عند تعطل أي طبقة واحدة، تبقى خطوط الدفاع اللاحقة جاهزة للتغطية.

يتم تنفيذ سلسلة الوسيط (Middleware) بأكملها بالترتيب التالي (انظر `config/middleware.php`):

```
请求 → Cors → Locale(Accept-Language) → SecurityMiddleware (erikwang2013/security-php, 31种检测器) → RateLimit → [路由组中间件: AdminAuth → AdminPermission → OperationLog] → Controller
```

| الطبقة | الوسيط/الآلية | هدف الحماية |
|----|--------|---------|
| 1 | SecurityMiddleware (erikwang2013/security-php) | 31 نوعًا من كشف الهجمات + التحقق من طرق HTTP + حد حجم جسم الطلب + التحقق من Content-Type + CSRF + القائمة السوداء لتصعيد هجمات IP |
| 2 | Cors | أمان عبر الأصول + حقن ترويسات الاستجابة الأمنية |
| 3 | RateLimit | تحديد المعدل بنافذة منزلقة Redis، ضد القوة الغاشمة |
| 4 | AdminAuth | مصادقة JWT + تسجيل خروج بالقائمة السوداء |
| 5 | AdminPermission | تفويض RBAC بدقة method.path |
| 6 | OperationLog | تدقيق العمليات + تتبع مصدر العميل |
| 7 | تشفير البيانات | إخفاء المعرفات بـ Hashids + تشفير قاعدة البيانات بـ Encryptable + تشفير النقل بـ EncryptionService |

طبقات الواجهة الأمامية الثلاث (Flutter) لديها تحقق إدخال مستقل خاص بها؛ لا يثق الخادم الخلفي بأي شيء، وكل طبقة تدافع بشكل مستقل.

## 2. 攻击检测引擎 (erikwang2013/security-php)

تم ترحيل كشف الهجمات من SecurityMiddleware الخاص إلى حزمة الأمان المخصصة `erikwang2013/security-php` الإصدار v1.1+، التي توفر **31 كاشفًا** تغطي 5 فئات كبيرة من الهجمات.

### 2.1 تصنيف الكواشف

**هجمات الحقن (11 نوعًا):** XSS، حقن SQL، حقن الأوامر، حقن NoSQL، حقن LDAP، حقن XPath، JNDI/Log4Shell، تضمين جانب الخادم SSI، حقن GraphQL، حقن القوالب SSTI

**هجمات البروتوكول والطلب (9 أنواع):** SSRF، XXE، حقن ترويسات استجابة HTTP، هجوم ترويسة Host، Request Smuggling، إعادة التوجيه المفتوحة Open Redirect، تجاوز CORS، اختطاف WebSocket، DNS Rebinding

**التحقق من طبقة بروتوكول HTTP (6 أنواع):** التحقق من طرق HTTP (405)، حد حجم جسم الطلب (413)، التحقق من Content-Type (415)، فحص أصل CSRF، القائمة السوداء لتصعيد هجمات IP، كشف تسرب البيانات الحساسة

**هجمات البيانات والتسلسل (5 أنواع):** إلغاء تسلسل PHP، حقن صيغ CSV، حقن ترويسات البريد الإلكتروني، هجمات JWT (تحليل بنيوي)، تلوث النموذج الأولي JS Prototype Pollution

**هجمات الملفات والمسارات (نوعان):** اجتياز المسار، رفع ملفات خبيثة

### 2.2 أوضاع المعالجة

يدعم كل كاشف وضعين بشكل مستقل:
- `block` — يمنع الطلب فور اكتشاف الهجوم، ويعيد رمز الحالة المكوّن
- `log` — يسجل فقط دون منع (`header_injection`، `ssti`، `nosql_injection` تعمل بوضع السجل افتراضيًا لمنع النتائج الإيجابية الكاذبة)

### 2.3 القائمة السوداء لتصعيد هجمات IP

نفس عنوان IP الذي يطلق 5 عمليات كشف هجوم خلال 60 ثانية → يُحظر تلقائيًا لمدة 15 دقيقة. الخلفية التخزينية اختيارية: Redis (موزع)، File (JSON لجهاز واحد) أو Cache (ملف مستقل عالي التزامن)، والتكوين الحالي يستخدم تخزين Redis.

### 2.4 سجلات الأمان

موقع الملف: `runtime/logs/security.log` (تدوير تلقائي، 10 ميجابايت/ملف)

## 4. ترويسات استجابة الأمان

يتم حقن جميع الترويسات في وسيط `Cors`، وتُضاف إلى كل استجابة عبر `$response->withHeaders()`.

| الترويسة | القيمة | الوظيفة |
|----|-----|------|
| Access-Control-Allow-Origin | `*` | السماح بأي أصل عبر النطاقات (سيناريو لوحة إدارة داخل الشبكة) |
| Access-Control-Allow-Methods | `GET,POST,PUT,DELETE,OPTIONS` | مجموعة الطرق المسموحة |
| Access-Control-Allow-Headers | `Authorization,Content-Type,API-Version` | الترويسات المخصصة المسموحة |
| Access-Control-Max-Age | `86400` | تخزين طلبات الفحص المسبق لمدة 24 ساعة |
| X-Content-Type-Options | `nosniff` | منع المتصفح من تخمين نوع MIME |
| X-Frame-Options | `DENY` | منع كل التضمين عبر iframe، ضد اختطاف النقرات |
| X-XSS-Protection | `1; mode=block` | تفعيل فلتر XSS المدمج في المتصفح ومنع عرض الصفحة |
| Referrer-Policy | `strict-origin-when-cross-origin` | نفس الأصل يرسل URL كاملًا، عبر الأصول يرسل النطاق فقط |
| Permissions-Policy | `camera=(), microphone=(), geolocation=()` | تعطيل واجهات الكاميرا/الميكروفون/تحديد الموقع في الموقع كله |

تستجيب طلبات الفحص المسبق OPTIONS مباشرة باستجابة فارغة 204، دون الدخول إلى سلسلة الوسيط التالية.

### 4.2 سياسة أمان المحتوى (CSP)

يُحقن في وسيط Cors مع ترويسات الأمان الأخرى، ويوفر دفاعًا متعمقًا يحد من مصادر الموارد التي يمكن للمتصفح تحميلها وتنفيذها.

| الترويسة | القيمة | الوظيفة |
|----|-----|------|
| Content-Security-Policy | `default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'` | تقييد مصادر النصوص/الأنماط/الصور/الاتصالات/الأطر/النماذج إلخ |
| X-Permitted-Cross-Domain-Policies | `none` | منع تحميل ملفات سياسات عبر النطاقات مثل Adobe Flash/PDF |

النقاط الرئيسية لسياسة CSP:
- `default-src 'self'`: افتراضيًا يُسمح بموارد نفس الأصل فقط
- `script-src 'self' 'unsafe-inline' 'unsafe-eval'`: السماح بنصوص نفس الأصل + النصوص المضمّنة (ضروري لـ Flutter Web) + eval (ضروري لتصحيح أخطاء Flutter Web)
- `frame-ancestors 'none'`: منع التضمين في iframe من أي صفحة، ضمانة مزدوجة مع X-Frame-Options: DENY
- `base-uri 'self'`: تقييد وسم `<base>` ليشير إلى نفس الأصل فقط
- `form-action 'self'`: تقييد النماذج للإرسال إلى نفس الأصل فقط

## 5. سياسة تحديد المعدل

### الخوارزمية

نافذة منزلقة Redis Sorted Set + نص Lua ذري، العمليات الأساسية:

```lua
-- 1. 清理窗口外的旧记录
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, windowStart)
-- 2. 检查当前窗口计数
local count = redis.call('ZCARD', KEYS[1])
-- 3. 超限则返回 {0, count}，未超限则 ZADD 并返回 {1, count+1}
if count >= limit then return {0, count} end
redis.call('ZADD', KEYS[1], now, now . '.' . random)  -- 随机后缀避免同毫秒覆盖
redis.call('EXPIRE', KEYS[1], window + 10)
```

يُنفذ نص Lua على خيط واحد في خادم Redis، وهو **ذري بطبيعته**، مما يلغي حالة السباق TOCTOU (Time-of-check to Time-of-use).

### إعداد تحديد المعدل

| المسار | الحد | النافذة | السيناريو |
|------|------|------|------|
| الافتراضي (كل المسارات) | 60 مرة/دقيقة | 60 ثانية | واجهات API العامة |
| `/api/auth/login` | 10 مرات/دقيقة | 60 ثانية | تسجيل الدخول (ضد القوة الغاشمة) |
| `/api/auth/register` | 5 مرات/دقيقة | 60 ثانية | التسجيل (ضد التسجيل الجماعي) |

### ترويسات الاستجابة

عند تجاوز الحد، يُعاد HTTP 429 مع نص JSON:
```json
{"code": 429, "message": "请求过于频繁，请稍后再试", "data": []}
```

تحمل جميع الاستجابات (بما فيها العادية) الترويسات التالية:

| الترويسة | الوصف |
|----|------|
| X-RateLimit-Limit | الحد الأقصى للطلبات المسموحة في النافذة الحالية |
| X-RateLimit-Remaining | الطلبات المتبقية المتاحة في النافذة الحالية |
| X-RateLimit-Reset | الطابع الزمني Unix لإعادة تعيين النافذة |
| Retry-After | تُرسل فقط عند تحديد المعدل، الثواني المقترحة للانتظار |

### سياسة التدهور

عند تعطل Redis (انتهاء مهلة الاتصال، عدم التوفر إلخ) يُطبق **fail-open**:

```php
try {
    $result = Redis::eval($lua, ...);
} catch (\Throwable $e) {
    return $handler($request); // Redis down, 放行所有请求
}
```

من الأفضل فقدان حماية تحديد المعدل لفترة قصيرة بدلًا من حجب طلبات الأعمال العادية.

### 5.4 آلية قفل الحساب

بالإضافة إلى تحديد المعدل، تضيف واجهة تسجيل الدخول آلية **قفل الحساب** لمنع القوة الغاشمة الموجّهة ضد مستخدمين محددين.

**عملية القفل**:

```
登录失败 → Redis INCR account_lockout:{userId} TTL=900s
连续 5 次失败 → Redis SETEX account_locked:{userId} 900 1
            → 返回 429 "账号已被锁定，请15分钟后再试"
            → 清除计数器 DEL account_lockout:{userId}
```

**السلوك أثناء فترة القفل**:

خلال فترة القفل، تُعيد جميع طلبات تسجيل الدخول 429 مباشرة دون التحقق من كلمة المرور، مما يمنع محاولات القوة الغاشمة تمامًا.

**ثوابت الإعداد**:

| الثابت | القيمة | المعنى |
|------|-----|------|
| MAX_LOGIN_ATTEMPTS | 5 | أقصى عدد من الإخفاقات المتتالية |
| LOCKOUT_DURATION | 900 | مدة القفل (بالثواني)، أي 15 دقيقة |

ملاحظة: يعتمد قفل الحساب على `userId` وليس IP، لذا فإن تغيير IP لا يتجاوز القفل. وبالتضافر مع تحديد معدل IP (10 مرات/دقيقة) يتشكل حماية مزدوجة:
- مستوى IP: تحديد 10 مرات/دقيقة يمنع القوة الغاشمة الموزعة
- مستوى الحساب: القفل بعد 5 إخفاقات يمنع القوة الغاشمة الموجّهة

## 6. المصادقة والتفويض

### 6.1 مصادقة JWT

يُنفَّذ عبر وسيط AdminAuth، ويُركَّب على مجموعات المسارات التي تتطلب المصادقة.

**إعداد المعاملات** (`config/plugin/erikwang2013/jwt/jwt`، تُحقن من `.env`):

| المعامل | القيمة | الوصف |
|------|-----|------|
| الخوارزمية | HS256 | توقيع متماثل HMAC-SHA256 |
| المفتاح | `JWT_SECRET` | يُحقن من متغير بيئة، يجب تغييره في الإنتاج |
| صلاحية access_token | 7200 ثانية (ساعتان) | `JWT_TTL` |
| صلاحية refresh_token | 1209600 ثانية (14 يومًا) | `JWT_REFRESH_TTL` |
| المُصدِر | `open-admin` | `JWT_ISSUER` |
| الجمهور | `open-admin` | `JWT_AUDIENCE` |

**استخراج التوكن**: يُستخرج من ترويسة `Authorization: Bearer <token>`، مع إزالة البادئة `Bearer ` للحصول على JWT الأصلي.

**عملية المصادقة**:
1. توكن فارغ → 401 مباشرة `{"code": 401, "message": "未登录"}`
2. فحص القائمة السوداء في Redis `jwt_blacklist:{md5(token)}` → إصابة → 401 `Token已失效，请重新登录`
3. فك JWT → فشل (منتهي/توقيع غير مطابق) → 401 `Token已过期或无效`
4. نجاح → حقن `$request->adminId` و `$request->adminUsername`

**آلية القائمة السوداء**: عند تسجيل خروج المستخدم، يُكتب `md5(token)` في Redis، وتُضبط TTL على الصلاحية المتبقية لـ JWT. عند تعطل Redis تُتخطى فحوصات القائمة السوداء (fail-open)، ويمكن استخدام التوكن المسجل خروجه لفترة قصيرة، لكن صلاحية JWT القصيرة (ساعتان) تعمل كحماية احتياطية.

### 6.2 حد الجلسات المتزامنة

لمنع إساءة استخدام التوكن المسربة عبر أجهزة متعددة، يحد النظام عدد التوكنات الصالحة التي يحملها نفس المستخدم في وقت واحد.

**منطق الحد**:

```
登录成功 → 签发新 Token
         → 查询当前用户有效 Token 数量: Redis SCARD user_tokens:{userId}
         → 若数量 >= 3（MAX_CONCURRENT_SESSIONS）:
            → 按创建时间升序排列，移除最旧的 Token:
              Redis SREM user_tokens:{userId} <oldest_token_id>
              Redis SETEX jwt_blacklist:{md5(oldest_token)} TTL remaining
         → 将新 Token 加入集合: Redis SADD user_tokens:{userId} <new_token_id>
            Redis SET user_token:{token_id} {userId} EX {TTL}
```

**ثوابت الإعداد**:

| الثابت | القيمة | المعنى |
|------|-----|------|
| MAX_CONCURRENT_SESSIONS | 3 | أقصى عدد توكنات متزامنة لنفس المستخدم |

**سيناريو الطرد**: عندما يسجل المستخدم الدخول من الجهاز الرابع، يُدفع توكن الجهاز الأول قسريًا إلى القائمة السوداء، وتعيد الطلبات اللاحقة 401 "Token已失效，请重新登录".

عند تسجيل الخروج، يُزال التوكن الحالي من المجموعة. وعند انتهاء صلاحية التوكن طبيعيًا، تنتهي صلاحية مفتاح Redis تلقائيًا ويقل عدد أعضاء المجموعة.

### 6.3 نموذج أذونات RBAC

يُنفَّذ عبر وسيط AdminPermission.

**نموذج البيانات**: ارتباط ثلاثي الطبقات User -> Role -> Permission

- `erik_admin_user` (جدول المستخدمين)
- `erik_admin_user_role` (جدول ارتباط المستخدم-الدور)
- `erik_admin_role` (جدول الأدوار)
- `erik_admin_role_permission` (جدول ارتباط الدور-الإذن)
- `erik_admin_permission` (جدول الأذونات)

**أنواع الأذونات**:
| type | المعنى | مثال |
|------|------|------|
| 1 | إذن قائمة | يتحكم في ظهور التنقل الأيسر |
| 2 | إذن زر | يتحكم في أزرار العمليات داخل الصفحة (إضافة/تعديل/حذف) |
| 3 | إذن واجهة API | يتحكم في استدعاءات الواجهات الخلفية |

صيغة معرف إذن API: `{method}.{path}`

مثلًا:
- `post.admin/user` — إنشاء مستخدم
- `put.admin/user` — تعديل مستخدم
- `delete.admin/user` — حذف مستخدم
- `get.admin/user` — عرض قائمة المستخدمين

**عملية التفويض**:
1. `$request->adminId` فارغ → السماح (المسار غير مكوّن بمصادقة مسبقة)
2. الحصول على المستخدم → الأدوار (تخطي الأدوار المعطلة ذات `status=0`) → قائمة الأذونات
3. مدير فائق (`slug = '*'`) → السماح مباشرة
4. بناء `strtolower(method) . '.' . trim(path, '/')` → المقارنة مع قائمة الأذونات
5. عدم التطابق → 403 `{"code": 403, "message": "无权限访问"}`

**التأكيد الثانوي**: يوفر BaseController طريقة `confirmPassword()`؛ تتطلب العمليات الحساسة (حذف المستخدمين، تصدير البيانات إلخ) إدخال كلمة المرور الحالية على مستوى الـ Controller، لمنع العمليات غير المصرح بها بعد اختطاف الجلسة.

## 7. سجلات التدقيق

### 7.1 سجلات العمليات

يسجل وسيط OperationLog تلقائيًا سجلات العمليات لطلبات POST / PUT / DELETE. لا تُسجل طلبات GET.

**الحقول المسجلة**:

| الحقل | المصدر | الوصف |
|------|------|------|
| id | SnowflakeService::generate() | معرف فريد عالميًا |
| user_id | `$request->adminId` | معرف المنفذ، 0 عند عدم تسجيل الدخول |
| action | `$request->method()` | يكافئ method |
| method | `$request->method()` | POST / PUT / DELETE |
| path | `$request->path()` | مسار الطلب |
| ip | `$request->getRealIp()` | عنوان IP الحقيقي للعميل |
| source | detectSource() | منصة مصدر العميل |
| input | نص الطلب (JSON بعد الإخفاء) | بيانات العملية المقدمة |
| created_at | `date('Y-m-d H:i:s')` | وقت العملية |

**فلتر الحقول الحساسة**: يمسح نص الطلب بشكل تكراري، وتُستبدل قيم الحقول التالية بـ `***`:

`password`, `old_password`, `new_password`, `new_password_confirmation`, `token`, `secret`, `access_token`, `refresh_token`

**كشف مصدر العميل** (`detectSource()`): حسب الأولوية:

1. يقرأ أولًا الترويسة المخصصة `X-Client-Platform` (تُعلن صراحةً من العملاء الأصليين)
2. يتراجع إلى الاستدلال من سلسلة User-Agent (ترتيب فحص طريقة `detectSource()`):

| المنصة | كلمات User-Agent المفتاحية |
|------|----------|
| iPadOS | `iPad` |
| macOS | `Macintosh`, `Mac OS` |
| Windows | `Windows` |
| Linux | `Linux` |
| iOS | `iPhone`, `iOS`, `CFNetwork` |
| Android | `Android` |
| HarmonyOS | `HarmonyOS`, `OpenHarmony` |
| Web | القيمة الافتراضية الاحتياطية |

**تحمل الأخطاء**: فشل كتابة السجل لا يحجب طلبات الأعمال (`catch (\Throwable)` يبتلع الخطأ بصمت).

### 7.2 سجلات الأمان

**موقع الملف**: `runtime/logs/security.log`

**المحتوى المسجل**:
- سجلات اعتراض الهجمات: فئة الهجوم، IP، المسار، الحقل، المصدر، مقطع الحمولة (أول 200 حرف)
- إشعارات حظر IP: الـ IP المحظور، عدد مرات الإطلاق

أذونات السجل هي `FILE_APPEND | LOCK_EX`، مما يضمن كتابة آمنة تحت التزامن.

## 8. حماية البيانات

يعتمد النظام سياسة حماية بيانات من ثلاث طبقات، تقابل المراحل الثلاث لتدفق البيانات.

### 8.1 طبقة النقل — EncryptionService

تستخدم `EncryptionService` حزمة `erikwang2013/encryption` لتشفير/فك تشفير الحقول الحساسة في طلبات/استجابات API.

**التفاصيل التقنية**:
- الخوارزمية: `aes-256-cbc-hmac` (بتوقيع HMAC مدمج ضد التلاعب)
- المفتاح: متغير البيئة `ENCRYPTION_KEY`، يُحاذى تلقائيًا إلى 32 بايت
- الاستخدام: نقل حقول مثل رقم الهاتف ورقم الهوية بين العميل وAPI

**طرق أدوات الإخفاء**:
- `maskPhone('13812341234')` → `138****1234`
- `maskEmail('abc@example.com')` → `a***@example.com` (اسم المستخدم أطول من حرفين) أو `a**@example.com`

### 8.2 طبقة التخزين — Encryptable Cast

يستخدم نموذج `AdminUser` تحويل Eloquent `Erikwang2013\Encryptable\Encryptable`، والحقول المقابلة:

- `email` → تحويل إلى Encryptable، تشفير/فك تلقائي
- `phone` → تحويل إلى Encryptable، تشفير/فك تلقائي
- `id_card` → تحويل إلى Encryptable، تشفير/فك تلقائي

عند الكتابة إلى قاعدة البيانات يُشفر تلقائيًا إلى نص مشفر، وعند القراءة يُفك تلقائيًا إلى نص واضح. نوع عمود التخزين هو `VARCHAR(500)`، ويُخزن النص المشفر بصيغة base64.

**نظام المفاتيح**: يستخدم `ENCRYPTABLE_KEY` مستقلة عن تشفير طبقة النقل (`ENCRYPTION_KEY`)؛ تسريب مفتاح واحد لا يعطل الطبقة الأخرى.

تدوير المفاتيح: يدعم متغير البيئة `ENCRYPTION_PREVIOUS_KEYS` قائمة المفاتيح التاريخية (مفصولة بفواصل)؛ عند قراءة البيانات القديمة تُحاول فك التشفير بالمفاتيح التاريخية، وعند الكتابة يُعاد التشفير بالمفتاح الحالي.

### 8.3 طبقة العرض — إخفاء المعرفات والإخفاء

**إخفاء المعرفات بـ Hashids**: تستخدم `HashidsService` حزمة `erikwang2013/hashids`.

- تُشفر معرفات BIGINT لقاعدة البيانات التي تعيدها واجهات API الخارجية إلى سلاسل hash (مثل `xK3mN9qR2pL7wV8b`)
- يرسل العميل سلسلة hash في الطلب، ويفكها الخادم الخلفي تلقائيًا إلى المعرف الأصلي
- يُحقن الملح `HASHIDS_SALT` من متغير بيئة؛ اختلاف الملح يعطي نتائج تشفير/فك مختلفة تمامًا
- الحد الأدنى لطول hash هو 16 خانة، باستخدام مجموعة مكونة من 62 حرفًا أبجديًا رقميًا
- يوفر BaseController الطرق المساعدة `encodeId()` و `decodeId()` و `encodeIds()`

**الإخفاء عند التصدير**: عند تصدير Excel/PDF (ExportController)، تُخفى الحقول الحساسة بشكل موحد:
- رقم الهاتف: `138****1234`
- البريد الإلكتروني: `a***@example.com`
- رقم الهوية: يغطى بالكامل إلى `********`

## 9. إدارة المفاتيح

تُحقن جميع المفاتيح من متغيرات بيئة `.env`؛ تقرأ ملفات الإعداد عبر `getenv()` مع قيم افتراضية احتياطية مدمجة (آمنة في بيئة التطوير فقط).

| متغير البيئة | الاستخدام | الحزمة | متطلب الإنتاج |
|----------|------|-----|---------|
| JWT_SECRET | مفتاح توقيع JWT | erikwang2013/jwt-webman | سلسلة عشوائية من 64+ حرفًا |
| JWT_ALGORITHM | خوارزمية توقيع JWT | نفسها | الإبقاء على HS256 |
| HASHIDS_SALT | ملح ترميز المعرفات | erikwang2013/hashids | سلسلة عشوائية |
| SNOWFLAKE_DATACENTER_ID | معرف مركز البيانات (0-31) | erikwang2013/snowflake-php | الإبقاء على الافتراضي في مركز بيانات واحد |
| ENCRYPTION_KEY | مفتاح تشفير طبقة نقل API | erikwang2013/encryption | سلسلة عشوائية من 32 بايت |
| ENCRYPTABLE_KEY | مفتاح تشفير طبقة تخزين قاعدة البيانات | erikwang2013/encryptable | سلسلة عشوائية من 32 بايت، مختلفة عن مفتاح النقل |

**متطلبات الأمان**:
- ملف `.env` مدرج في `.gitignore`، ويُمنع منعًا باتًا إيداعه في المستودع
- `.env.example` ملف قالب عام لا يحتوي مفاتيح حقيقية
- في الإنتاج **يجب** استبدال جميع المفاتيح الافتراضية بسلاسل عشوائية
- يُنصح بتوليد المفاتيح عبر `openssl rand -base64 32`

### عزل تخزين المفاتيح

| الطبقة | مفتاح الإعداد | متغير بيئة المفتاح |
|----|--------|-------------|
| تشفير النقل | `config/encryption.php` → `key` | `ENCRYPTION_KEY` |
| تشفير التخزين | `config/encryptable.php` → `key` | `ENCRYPTABLE_KEY` |

## 10. security.txt (RFC 9116)

يوفر النظام نقطة نهاية لمعلومات الاتصال الأمنية في `/.well-known/security.txt` متوافقة مع معيار RFC 9116، ليسهل على باحثي الأمان إيجاد قناة الإبلاغ سريعًا عند اكتشاف الثغرات.

**طريقة الوصول**:

```
GET /.well-known/security.txt
```

**محتوى الاستجابة**:

```text
Contact: mailto:security@erik.xyz
Expires: 2027-05-20T00:00:00.000Z
Preferred-Languages: zh, en
Canonical: https://erik.xyz/.well-known/security.txt
Policy: https://erik.xyz/security-policy
```

**شرح الحقول**:

| الحقل | الوصف |
|------|------|
| Contact | وسيلة الإبلاغ عن ثغرات الأمان |
| Expires | تاريخ انتهاء صلاحية الملف، يتطلب تحديثًا دوريًا |
| Preferred-Languages | لغات التواصل المفضلة |
| Canonical | الرابط الرسمي (الكنسي) لهذا الملف |
| Policy | رابط سياسة الأمان/سياسة الإفصاح عن الثغرات |

هذه النقطة النهائية لا تخضع لوسائط تحديد المعدل أو المصادقة؛ يمكن لأي شخص الوصول إليها مباشرة.

## 11. إعداد أمان Nginx

يوفر المشروع `docs/nginx-security.conf` كإعداد مرجعي لتقوية الوكيل العكسي Nginx في بيئة الإنتاج.

**إجراءات الأمان المتضمنة**:

| عنصر الإعداد | الوظيفة |
|--------|------|
| `server_tokens off` | إخفاء رقم إصدار Nginx |
| `client_max_body_size 10m` | تحديد حجم جسم الطلب، بالتعاون مع SecurityMiddleware (erikwang2013/security-php) |
| `limit_req_zone` | تحديد معدل الطلبات على مستوى Nginx |
| `limit_conn_zone` | تحديد عدد الاتصالات المتزامنة |
| `add_header` ترويسات الأمان | إضافة X-XSS-Protection وغيرها من ترويسات الأمان على مستوى Nginx |
| `if ($request_method)` | رفض طرق HTTP غير القياسية على مستوى Nginx |
| إعداد SSL/TLS | إعداد TLS 1.2/1.3 حديث، تعطيل حزم التشفير الضعيفة |
| إخفاء ترويسات الخادم الخلفي | `proxy_hide_header` يزيل الترويسات الحساسة مثل إصدار webman |

**طريقة الاستخدام**: ادمج الإعدادات من `docs/nginx-security.conf` في كتلة server في Nginx لديك، مع الضبط وفق النطاق الفعلي ومسار الشهادات.
