## 1. Обзор многоуровневой защиты

Система использует 7-уровневую модель многоуровневой защиты: вредоносные запросы фильтруются слой за слоем снаружи внутрь, чтобы даже при отказе любого отдельного уровня последующие рубежи обороны продолжали работать.

Вся цепочка промежуточного ПО выполняется в следующем порядке (см. `config/middleware.php`):

```
请求 → Cors → Locale(Accept-Language) → SecurityMiddleware (erikwang2013/security-php, 31种检测器) → RateLimit → [路由组中间件: AdminAuth → AdminPermission → OperationLog] → Controller
```

| Уровень | Промежуточное ПО / механизм | Цель защиты |
|----|--------|---------|
| 1 | SecurityMiddleware (erikwang2013/security-php) | 31 детектор атак + проверка HTTP-методов + ограничение размера тела запроса + проверка Content-Type + CSRF + чёрный список эскалации атак по IP |
| 2 | Cors | Безопасность междоменных запросов + внедрение защитных заголовков ответа |
| 3 | RateLimit | Ограничение частоты скользящим окном Redis, защита от перебора |
| 4 | AdminAuth | Аутентификация JWT + выход через чёрный список |
| 5 | AdminPermission | Авторизация RBAC с гранулярностью method.path |
| 6 | OperationLog | Аудит операций + отслеживание источника клиента |
| 7 | Шифрование данных | Обефускация ID Hashids + шифрование БД Encryptable + шифрование передачи EncryptionService |

Фронтенд-слои (Flutter) имеют собственную независимую проверку ввода; бэкенд не доверяет ничему, и каждый слой защищается самостоятельно.

## 2. Движок обнаружения атак

## 2. 攻击检测引擎 (erikwang2013/security-php)

Обнаружение атак перенесено с собственного SecurityMiddleware на выделенный пакет безопасности `erikwang2013/security-php` v1.1+, предоставляющий **31 детектор**, охватывающий 5 основных категорий атак.

### 2.1 Классификация детекторов

**Инъекционные атаки (11):** XSS, SQL-инъекция, инъекция команд, NoSQL-инъекция, LDAP-инъекция, XPath-инъекция, JNDI/Log4Shell, SSI (включения на стороне сервера), GraphQL-инъекция, SSTI-инъекция шаблонов

**Протокольные и запросные атаки (9):** SSRF, XXE, инъекция заголовков HTTP-ответа, атака на заголовок Host, Request Smuggling, Open Redirect, обход CORS, перехват WebSocket, DNS Rebinding

**Проверка HTTP-протокольного слоя (6):** проверка HTTP-метода (405), ограничение размера тела запроса (413), проверка Content-Type (415), проверка Origin для CSRF, чёрный список эскалации атак по IP, обнаружение утечки чувствительных данных

**Атаки на данные и сериализацию (5):** десериализация PHP, инъекция формул CSV, инъекция заголовков электронной почты, атаки на JWT (структурный анализ), JS Prototype Pollution

**Файловые и путевые атаки (2):** обход пути, загрузка вредоносных файлов

### 2.2 Режимы обработки

Каждый детектор независимо поддерживает два режима:
- `block` — блокировать при обнаружении атаки, возвращать настроенный код состояния
- `log` — только записывать в лог без блокировки (`header_injection`, `ssti`, `nosql_injection` по умолчанию в режиме log для предотвращения ложных срабатываний)

### 2.3 Чёрный список эскалации атак по IP

Если один IP за 60 секунд срабатывает 5 раз на детекторах атак, он автоматически блокируется на 15 минут. Бэкенд хранения может быть Redis (распределённый), File (одиночный JSON-узел) или Cache (отдельные файлы для высокого параллелизма); текущая конфигурация использует Redis.

### 2.4 Журналы безопасности

Расположение файла: `runtime/logs/security.log` (авторотация, 10 МБ на файл)

## 4. Защитные заголовки ответа

Все заголовки внедряются в промежуточном ПО `Cors` и добавляются к каждому ответу через `$response->withHeaders()`.

| Заголовок | Значение | Назначение |
|----|-----|------|
| Access-Control-Allow-Origin | `*` | Разрешить междоменные запросы из любого источника (сценарий интранет-админки) |
| Access-Control-Allow-Methods | `GET,POST,PUT,DELETE,OPTIONS` | Набор разрешённых методов |
| Access-Control-Allow-Headers | `Authorization,Content-Type,API-Version` | Разрешённые пользовательские заголовки |
| Access-Control-Max-Age | `86400` | Кэширование предварительного запроса на 24 часа |
| X-Content-Type-Options | `nosniff` | Запрет MIME-сниффинга браузером |
| X-Frame-Options | `DENY` | Запрет всех iframe-встраиваний, защита от кликджекинга |
| X-XSS-Protection | `1; mode=block` | Включить встроенный XSS-фильтр браузера и блокировать рендеринг страницы |
| Referrer-Policy | `strict-origin-when-cross-origin` | Для того же источника — полный URL, для кросс-домена — только домен |
| Permissions-Policy | `camera=(), microphone=(), geolocation=()` | Отключить API камеры/микрофона/геолокации на всём сайте |

OPTIONS-запросы предварительной проверки сразу возвращают пустой ответ 204 и не входят в последующую цепочку промежуточного ПО.

### 4.2 Content-Security-Policy (CSP)

Внедряется вместе с другими защитными заголовками в промежуточном ПО Cors, обеспечивая многоуровневую защиту за счёт ограничения источников ресурсов, которые браузер может загружать и выполнять.

| Заголовок | Значение | Назначение |
|----|-----|------|
| Content-Security-Policy | `default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'` | Ограничение источников скриптов/стилей/изображений/подключений/фреймов/форм и других ресурсов |
| X-Permitted-Cross-Domain-Policies | `none` | Запрет загрузки файлов междоменных политик, таких как Adobe Flash/PDF |

Ключевые моменты политики CSP:
- `default-src 'self'`: по умолчанию разрешены только ресурсы того же источника
- `script-src 'self' 'unsafe-inline' 'unsafe-eval'`: разрешены скрипты того же источника + встроенные скрипты (обязательно для Flutter Web) + eval (обязательно для отладки Flutter Web)
- `frame-ancestors 'none'`: запрет встраивания в iframe любой страницы, двойная защита вместе с X-Frame-Options: DENY
- `base-uri 'self'`: ограничить тег `<base>` только тем же источником
- `form-action 'self'`: ограничить отправку форм только на тот же источник

## 5. Стратегия ограничения частоты

### Алгоритм

Скользящее окно Redis Sorted Set + атомарный Lua-скрипт, критические операции:

```lua
-- 1. 清理窗口外的旧记录
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, windowStart)
-- 2. 检查当前窗口计数
local count = redis.call('ZCARD', KEYS[1])
-- 3. 超限则返回 {0, count}，未超限则 ZADD 并返回 {1, count+1}
if count >= limit then return {0, count} end
redis.call('ZADD', KEYS[1], now, now . '.' . random)  -- 随机后缀避免同毫秒覆盖
redis.call('EXPIRE', KEYS[1], window + 10)
```

Lua-скрипт выполняется на сервере Redis в одном потоке, что **естественно атомарно** и устраняет состояние гонки TOCTOU (Time-of-check to Time-of-use).

### Конфигурация ограничения частоты

| Маршрут | Ограничение | Окно | Сценарий |
|------|------|------|------|
| По умолчанию (все маршруты) | 60 раз/мин | 60s | Общее API |
| `/api/auth/login` | 10 раз/мин | 60s | Вход (защита от перебора) |
| `/api/auth/register` | 5 раз/мин | 60s | Регистрация (защита от массовой регистрации) |

### Заголовки ответа

При срабатывании ограничения возвращается HTTP 429 с телом JSON:
```json
{"code": 429, "message": "请求过于频繁，请稍后再试", "data": []}
```

Все ответы (включая обычные) несут следующие заголовки:

| Заголовок | Описание |
|----|------|
| X-RateLimit-Limit | Максимальное число запросов, разрешённых в текущем окне |
| X-RateLimit-Remaining | Оставшееся число доступных запросов в текущем окне |
| X-RateLimit-Reset | Unix-метка времени сброса окна |
| Retry-After | Присутствует только при ограничении; рекомендуемое время ожидания в секундах |

### Стратегия деградации

При сбое Redis (таймаут соединения, недоступность и т. д.) — **fail-open**:

```php
try {
    $result = Redis::eval($lua, ...);
} catch (\Throwable $e) {
    return $handler($request); // Redis down, 放行所有请求
}
```

Лучше временно потерять защиту от перегрузки, чем блокировать обычные бизнес-запросы.

### 5.4 Механизм блокировки учётной записи

Помимо ограничения частоты, интерфейс входа добавляет **механизм блокировки учётной записи** для защиты от целевого перебора конкретных пользователей.

**Процесс блокировки**:

```
登录失败 → Redis INCR account_lockout:{userId} TTL=900s
连续 5 次失败 → Redis SETEX account_locked:{userId} 900 1
            → 返回 429 "账号已被锁定，请15分钟后再试"
            → 清除计数器 DEL account_lockout:{userId}
```

**Поведение во время блокировки**:

Во время блокировки все запросы входа сразу возвращают 429 без проверки пароля, полностью блокируя попытки перебора.

**Константы конфигурации**:

| Константа | Значение | Смысл |
|------|-----|------|
| MAX_LOGIN_ATTEMPTS | 5 | Максимальное число последовательных неудач |
| LOCKOUT_DURATION | 900 | Длительность блокировки в секундах, т. е. 15 минут |

Примечание: блокировка учётной записи основана на `userId`, а не на IP, поэтому смена IP не позволяет атакующему обойти её. В сочетании с IP-ограничением частоты (10 раз/мин) образуется двойная защита:
- Уровень IP: лимит 10 раз/мин блокирует распределённый перебор
- Уровень учётной записи: блокировка после 5 неудач блокирует целевой перебор

## 6. Аутентификация и авторизация

### 6.1 Аутентификация JWT

Реализована промежуточным ПО AdminAuth, подключённым к группам маршрутов, требующим аутентификации.

**Конфигурация параметров** (`config/plugin/erikwang2013/jwt/jwt`, внедряется через `.env`):

| Параметр | Значение | Описание |
|------|-----|------|
| Алгоритм | HS256 | Симметричная подпись HMAC-SHA256 |
| Секрет | `JWT_SECRET` | Внедряется через переменную окружения; в проде обязательна замена |
| TTL access_token | 7200s (2ч) | `JWT_TTL` |
| TTL refresh_token | 1209600s (14д) | `JWT_REFRESH_TTL` |
| Эмитент | `open-admin` | `JWT_ISSUER` |
| Аудитория | `open-admin` | `JWT_AUDIENCE` |

**Извлечение токена**: из заголовка `Authorization: Bearer <token>`; удалите префикс `Bearer `, чтобы получить исходный JWT.

**Процесс аутентификации**:
1. Пустой token → сразу 401 `{"code": 401, "message": "未登录"}`
2. Проверка чёрного списка Redis `jwt_blacklist:{md5(token)}` → совпадение → 401 `Token已失效，请重新登录`
3. Декодирование JWT → ошибка (истёк/не совпадает подпись) → 401 `Token已过期或无效`
4. Успех → внедрение `$request->adminId` и `$request->adminUsername`

**Механизм чёрного списка**: при выходе пользователя `md5(token)` записывается в Redis с TTL, равным оставшемуся сроку действия JWT. При сбое Redis проверка чёрного списка пропускается (fail-open); в этом случае вышедший токен ещё можно использовать короткое время, но короткий срок действия самого JWT (2ч) служит запасной защитой.

### 6.2 Ограничение одновременных сессий

Чтобы предотвратить использование утёкшего токена на нескольких устройствах, система ограничивает число действительных токенов, которые один пользователь может держать одновременно.

**Логика ограничения**:

```
登录成功 → 签发新 Token
         → 查询当前用户有效 Token 数量: Redis SCARD user_tokens:{userId}
         → 若数量 >= 3（MAX_CONCURRENT_SESSIONS）:
            → 按创建时间升序排列，移除最旧的 Token:
              Redis SREM user_tokens:{userId} <oldest_token_id>
              Redis SETEX jwt_blacklist:{md5(oldest_token)} TTL remaining
         → 将新 Token 加入集合: Redis SADD user_tokens:{userId} <new_token_id>
            Redis SET user_token:{token_id} {userId} EX {TTL}
```

**Константа конфигурации**:

| Константа | Значение | Смысл |
|------|-----|------|
| MAX_CONCURRENT_SESSIONS | 3 | Максимальное число одновременных токенов на пользователя |

**Сценарий принудительного выхода**: когда пользователь входит на 4-м устройстве, токен 1-го устройства принудительно добавляется в чёрный список, и последующие запросы возвращают 401 "Token已失效，请重新登录".

При выходе текущий токен удаляется из набора. При естественном истечении токена ключ Redis истекает автоматически, и состав набора соответственно уменьшается.

### 6.3 Модель прав RBAC

Реализована промежуточным ПО AdminPermission.

**Модель данных**: трёхуровневая связь User -> Role -> Permission

- `erik_admin_user` (таблица пользователей)
- `erik_admin_user_role` (таблица связи пользователь-роль)
- `erik_admin_role` (таблица ролей)
- `erik_admin_role_permission` (таблица связи роль-право)
- `erik_admin_permission` (таблица прав)

**Типы прав**:
| type | Смысл | Пример |
|------|------|------|
| 1 | Право на меню | Управление видимостью левой навигации |
| 2 | Право на кнопку | Управление кнопками действий на странице (добавить/изменить/удалить) |
| 3 | Право на API | Управление вызовами бэкенд-интерфейсов |

Формат идентификатора права API: `{method}.{path}`

Например:
- `post.admin/user` — создать пользователя
- `put.admin/user` — изменить пользователя
- `delete.admin/user` — удалить пользователя
- `get.admin/user` — просмотреть список пользователей

**Процесс авторизации**:
1. `$request->adminId` пуст → пропустить (у маршрута не настроена предварительная аутентификация)
2. Получить пользователя → роли (пропуская отключённые роли с `status=0`) → список прав
3. Суперадминистратор (`slug = '*'`) → пропустить напрямую
4. Сформировать `strtolower(method) . '.' . trim(path, '/')` → сравнить со списком прав
5. Нет совпадения → 403 `{"code": 403, "message": "无权限访问"}`

**Второе подтверждение**: BaseController предоставляет метод `confirmPassword()`; чувствительные операции (удаление пользователя, экспорт данных и т. д.) дополнительно требуют ввода текущего пароля на уровне Controller, что предотвращает несанкционированные операции после перехвата сессии.

## 7. Журналы аудита

### 7.1 Журналы операций

Промежуточное ПО OperationLog автоматически записывает журналы операций для запросов POST / PUT / DELETE. GET-запросы не записываются.

**Записываемые поля**:

| Поле | Источник | Описание |
|------|------|------|
| id | SnowflakeService::generate() | Глобально уникальный ID |
| user_id | `$request->adminId` | ID оператора, 0 если не авторизован |
| action | `$request->method()` | То же, что method |
| method | `$request->method()` | POST / PUT / DELETE |
| path | `$request->path()` | Путь запроса |
| ip | `$request->getRealIp()` | Реальный IP клиента |
| source | detectSource() | Платформа-источник клиента |
| input | Тело запроса (маскированный JSON) | Переданные данные операции |
| created_at | `date('Y-m-d H:i:s')` | Время операции |

**Фильтрация чувствительных полей**: рекурсивный обход тела запроса; значения следующих полей заменяются на `***`:

`password`, `old_password`, `new_password`, `new_password_confirmation`, `token`, `secret`, `access_token`, `refresh_token`

**Определение источника** (`detectSource()`): по приоритету:

1. Сначала читается пользовательский заголовок `X-Client-Platform` (явно объявляется нативными клиентами)
2. Запасной вариант — вывод из строки User-Agent (порядок проверки в методе `detectSource()`):

| Платформа | Ключевые слова UA |
|------|----------|
| iPadOS | `iPad` |
| macOS | `Macintosh`, `Mac OS` |
| Windows | `Windows` |
| Linux | `Linux` |
| iOS | `iPhone`, `iOS`, `CFNetwork` |
| Android | `Android` |
| HarmonyOS | `HarmonyOS`, `OpenHarmony` |
| Web | Значение по умолчанию |

**Отказоустойчивость**: исключения при записи журнала не блокируют бизнес-запросы (`catch (\Throwable)` молча игнорируется).

### 7.2 Журналы безопасности

**Расположение файла**: `runtime/logs/security.log`

**Записываемое содержимое**:
- Журналы перехвата атак: категория атаки, IP, путь, поле, источник, фрагмент payload (первые 200 символов)
- Уведомления о блокировке IP: заблокированный IP, число срабатываний

Права журнала — `FILE_APPEND | LOCK_EX`, что обеспечивает безопасную запись при параллелизме.

## 8. Защита данных

Система применяет трёхуровневую стратегию защиты данных, соответствующую трём стадиям движения данных.

### 8.1 Транспортный уровень — EncryptionService

`EncryptionService` использует пакет `erikwang2013/encryption` для шифрования/дешифрования чувствительных полей в API-запросах/ответах.

**Технические детали**:
- Алгоритм: `aes-256-cbc-hmac` (встроенная подпись HMAC предотвращает подделку)
- Ключ: переменная окружения `ENCRYPTION_KEY`, автоматически выравнивается до 32 байт
- Применение: передача между клиентом и API таких полей, как номера телефонов и номера удостоверений личности

**Методы маскирования**:
- `maskPhone('13812341234')` → `138****1234`
- `maskEmail('abc@example.com')` → `a***@example.com` (имя пользователя длиннее 2 символов) или `a**@example.com`

### 8.2 Уровень хранения — Encryptable Cast

Модель `AdminUser` использует Eloquent-cast `Erikwang2013\Encryptable\Encryptable`, соответствующие поля:

- `email` → cast как Encryptable, автоматическое шифрование/дешифрование
- `phone` → cast как Encryptable, автоматическое шифрование/дешифрование
- `id_card` → cast как Encryptable, автоматическое шифрование/дешифрование

При записи в базу данных автоматически шифруется в шифротекст, при чтении автоматически расшифровывается в открытый текст. Тип столбца хранения — `VARCHAR(500)`, шифротекст хранится в формате base64.

**Система ключей**: независимо от транспортного шифрования (`ENCRYPTION_KEY`) используется `ENCRYPTABLE_KEY`; утечка одного ключа не выводит из строя другой уровень.

Ротация ключей: переменная окружения `ENCRYPTION_PREVIOUS_KEYS` поддерживает список исторических ключей (через запятую). При чтении старых данных дешифрование пробуется историческими ключами, при обратной записи повторное шифрование выполняется текущим ключом.

### 8.3 Уровень представления — обефускация ID и маскирование

**Обефускация ID Hashids**: `HashidsService` использует пакет `erikwang2013/hashids`.

- Возвращаемые внешним API BIGINT ID из БД кодируются в хеш-строки (например, `xK3mN9qR2pL7wV8b`)
- Клиент передаёт хеш-строку в запросе, бэкенд автоматически декодирует её обратно в исходный ID
- Соль внедряется через переменную окружения `HASHIDS_SALT`; при разной соли результаты кодирования/декодирования полностью различаются
- Минимальная длина хеша — 16 символов, используется 62-символьный буквенно-цифровой набор
- BaseController предоставляет удобные методы `encodeId()`, `decodeId()`, `encodeIds()`

**Маскирование при экспорте**: при экспорте Excel/PDF (ExportController) чувствительные поля единообразно маскируются:
- Телефон: `138****1234`
- Email: `a***@example.com`
- Удостоверение личности: полностью скрыто как `********`

## 9. Управление ключами

Все ключи внедряются через переменные окружения `.env`; конфигурационные файлы читают их через `getenv()` и содержат встроенные запасные значения по умолчанию (безопасно только для среды разработки).

| Переменная окружения | Назначение | Пакет | Требование для прода |
|----------|------|-----|---------|
| JWT_SECRET | Ключ подписи JWT | erikwang2013/jwt-webman | Случайная строка из 64+ символов |
| JWT_ALGORITHM | Алгоритм подписи JWT | тот же | Оставить HS256 |
| HASHIDS_SALT | Соль кодирования ID | erikwang2013/hashids | Случайная строка |
| SNOWFLAKE_DATACENTER_ID | ID дата-центра (0-31) | erikwang2013/snowflake-php | Для одного ЦОД оставить по умолчанию |
| ENCRYPTION_KEY | Ключ шифрования транспортного уровня API | erikwang2013/encryption | Случайная строка из 32 байт |
| ENCRYPTABLE_KEY | Ключ шифрования уровня хранения БД | erikwang2013/encryptable | Случайная строка из 32 байт, отличается от транспортного ключа |

**Требования безопасности**:
- Файл `.env` добавлен в `.gitignore`, строго запрещено коммитить его в репозиторий
- `.env.example` — публичный файл-шаблон, не содержащий реальных ключей
- В продакшене **обязательно** заменить все ключи по умолчанию на случайные строки
- Рекомендуется генерировать ключи командой `openssl rand -base64 32`

### Изоляция хранения ключей

| Уровень | Ключ конфигурации | Переменная окружения ключа |
|----|--------|-------------|
| Транспортное шифрование | `config/encryption.php` → `key` | `ENCRYPTION_KEY` |
| Шифрование хранения | `config/encryptable.php` → `key` | `ENCRYPTABLE_KEY` |
| Обефускация ID | `config/hashids.php` → `connections.main.salt` | `HASHIDS_SALT` |
| Подпись JWT | `config/plugin/erikwang2013/jwt/jwt` | `JWT_SECRET` |

## 10. security.txt (RFC 9116)

Система предоставляет по адресу `/.well-known/security.txt` конечную точку контактной информации для безопасности, соответствующую стандарту RFC 9116, чтобы исследователи безопасности могли быстро найти канал для сообщения об уязвимостях.

**Способ доступа**:

```
GET /.well-known/security.txt
```

**Содержимое ответа**:

```text
Contact: mailto:security@erik.xyz
Expires: 2027-05-20T00:00:00.000Z
Preferred-Languages: zh, en
Canonical: https://erik.xyz/.well-known/security.txt
Policy: https://erik.xyz/security-policy
```

**Описание полей**:

| Поле | Описание |
|------|------|
| Contact | Контакт для сообщения об уязвимостях безопасности |
| Expires | Время истечения файла, требует периодического обновления |
| Preferred-Languages | Предпочитаемые языки общения |
| Canonical | Канонический URL этого файла |
| Policy | Ссылка на политику безопасности / политику раскрытия уязвимостей |

Эта конечная точка не ограничена ни лимитом частоты, ни аутентификацией и другим промежуточным ПО; любой может обратиться к ней напрямую.

## 11. Конфигурация безопасности Nginx

Проект предоставляет `docs/nginx-security.conf` как справочную конфигурацию усиления безопасности обратного прокси Nginx в продакшене.

**Включённые меры безопасности**:

| Пункт конфигурации | Назначение |
|--------|------|
| `server_tokens off` | Скрыть номер версии Nginx |
| `client_max_body_size 10m` | Ограничение размера тела запроса, совместно с SecurityMiddleware (erikwang2013/security-php) |
| `limit_req_zone` | Ограничение частоты запросов на уровне Nginx |
| `limit_conn_zone` | Ограничение числа одновременных соединений |
| Заголовки безопасности `add_header` | Добавление защитных заголовков, таких как X-XSS-Protection, на уровне Nginx |
| `if ($request_method)` | Отказ от нестандартных HTTP-методов на уровне Nginx |
| Конфигурация SSL/TLS | Современная конфигурация TLS 1.2/1.3, слабые шифронаборы отключены |
| Скрытие заголовков бэкенда | `proxy_hide_header` удаляет чувствительные заголовки, такие как версия webman |

**Способ использования**: объедините конфигурацию из `docs/nginx-security.conf` в свой блок server Nginx, скорректировав под реальный домен и пути сертификатов.

## 12. Модель угроз

### 12.1 Защищённые угрозы

| Тип угрозы | Вектор атаки | Уровень защиты |
|----------|---------|---------|
| Злоупотребление HTTP-методами | TRACE/TRACK XST-атаки, CONNECT-туннельный прокси, зондирование методов WebDAV | Детектор http_method SecurityMiddleware, белый список методов 405 |
| Целевой перебор | Повторные попытки пароля против конкретного пользователя | Блокировка учётной записи (15 мин после 5 неудач) + RateLimit (вход 10/мин) + Captcha |
| Перебор | Повторные попытки подбора имени/пароля с распределённых IP | RateLimit (вход 10/мин) + Captcha |
| XSS (межсайтовый скриптинг) | `<script>`, onerror, javascript: | SecurityMiddleware (erikwang2013/security-php) (5 шаблонов) + заголовок ответа X-XSS-Protection + CSP |
| SQL-инъекция | UNION SELECT, OR 1=1, обход через комментарии | SecurityMiddleware (erikwang2013/security-php) (6 шаблонов) + параметризованные запросы Eloquent ORM |
| CSRF (межсайтовая подделка запроса) | Подделка запросов вредоносными сайтами | Проверка Origin/Referer в SecurityMiddleware (erikwang2013/security-php) |
| Обход пути | `../../etc/passwd` | Шаблон обхода пути в SecurityMiddleware (erikwang2013/security-php) + белый список расширений UploadController |
| Инъекция команд | `;ls`, `` `whoami` ``, `$(cat ...)` | SecurityMiddleware (erikwang2013/security-php) (4 шаблона) |
| Перехват сессии | Кража JWT-токенов | Короткий срок действия JWT (2ч) + выход через чёрный список + второе подтверждение пароля для чувствительных операций |
| Перечисление ID | Угадывание объёма данных перебором числовых ID | Обефускация Hashids в случайные строки |
| Утечка данных | Слив БД / посредник / утечка журналов | Трёхуровневое шифрование/маскирование + фильтрация чувствительных полей OperationLog |
| DoS-атаки | Чрезмерно большие тела запросов / высокочастотные запросы | Лимит тела запроса 10 МБ + RateLimit 60/мин + чёрный список IP |
| Повышение привилегий | Доступ пользователей с низкими правами к административным интерфейсам | Авторизация RBAC с гранулярностью method.path |
| Атаки через загрузку файлов | Двойное расширение shell.php.png | Обнаружение вредоносных файлов в SecurityMiddleware (erikwang2013/security-php) |

### 12.2 Известные ограничения

| Ограничение | Область влияния | Меры смягчения |
|------|---------|---------|
| Защита CSRF работает только для браузеров | Небраузерные клиенты (curl, Postman, мобильные приложения) могут пропустить проверки Origin/Referer | Небраузерные клиенты естественно невосприимчивы к CSRF; полагаемся на аутентификацию JWT вместо Cookie |
| При недоступности Redis лимит частоты и чёрный список деградируют до fail-open | Атакующие могут обойти лимит частоты и блокировку высокочастотных запросов | Мониторинг доступности Redis с алертами; чёрный список IP поддерживает три бэкенда: file/redis/cache |
| Нет отдельного движка WAF | Обнаружение на основе регулярных выражений, а не специализированный движок правил WAF | В проде рекомендуется Nginx ModSecurity или Cloudflare WAF перед приложением |
| JWT без состояния нельзя активно аннулировать | До истечения токен нельзя отозвать на сервере (кроме чёрного списка) | Чёрный список + короткий TTL 2ч сокращают окно риска |
| Нет особого лимита для административных конечных точек | Админские API разделяют общий лимит 60/мин с обычными API | Частота админских операций естественно низка, разделение пока не требуется |
| Ограничение возврата PCRE | В пакете встроен предел 1 000 000 возвратов + восстановление через finally; крайне сложные входные данные всё ещё несут риск для производительности | Запасной вариант — ограничение размера тела запроса (10 МБ) |
