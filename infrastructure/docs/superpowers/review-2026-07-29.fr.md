## Problèmes corrigés

### BUG-001 : bee_logs — `WorkerGuard` abandonné immédiatement, perte des journaux asynchrones

**Gravité :** élevée  
**Fichier :** `crates/bee_logs/src/lib.rs:54,62`

Le `WorkerGuard` retourné par `tracing_appender::non_blocking()` est abandonné (dropped) à la fin de la branche `match`,
ce qui arrête immédiatement le thread d'écriture non bloquant et fait perdre tous les messages de journaux asynchrones.

**Correction :** ajout d'une structure `LogHandle` contenant `Option<WorkerGuard>` ; `Logger::init()` retourne désormais
`Result<LogHandle, ...>`. Les appelants doivent garder `LogHandle` vivant pour garantir l'écriture continue.

### BUG-002 : bee_cache — fuite mémoire des entrées expirées par TTL

**Gravité :** moyenne  
**Fichier :** `crates/bee_cache/src/lib.rs:60-71`

`MemoryCache::get()` ne retourne que `None` lorsqu'elle détecte l'expiration du TTL, sans supprimer l'entrée de la HashMap.
Dans les applications de longue durée, les entrées expirées s'accumulent et provoquent une fuite mémoire.

**Correction :** `get()` libère le verrou de lecture, acquiert le verrou d'écriture et supprime l'entrée expirée après détection.

### BUG-003 : examples/hello — avertissement d'import inutilisé

**Gravité :** faible  
**Fichier :** `examples/hello/src/main.rs:1`

`use bee_rust::prelude::*` n'est pas utilisé et génère un avertissement de compilation.

**Correction :** import supprimé ; la valeur retournée par `init()` est liée à `_log_handle` pour éviter un abandon prématuré du LogHandle.

## Observations d'architecture

### Points forts

1. **Découpage clair en crates** — 15 crates aux responsabilités nettes et à la direction des dépendances sensée (fondations → stockage → Web → agrégation)
2. **Abstractions de trait complètes** — les quatre traits de stockage `KvStore`, `SearchEngine`, `GraphDB`, `TimeSeriesDB` sont conçus de manière cohérente
3. **Stratégie de test correcte** — chaque crate teste son trait avec des implémentations stub/mock, sans dépendre de services externes
4. **Types d'erreur normalisés** — derive `thiserror::Error` uniforme, formatage cohérent des messages d'erreur
5. **Zéro unsafe** — aucun bloc unsafe dans tout le code
6. **Usage judicieux des proc macros** — les deux macros derive `Config` et `Model` ont une responsabilité unique

### Suggestions d'amélioration

1. **Le trait `KvStore` devrait utiliser `&self`** — à l'image de `SearchEngine`/`GraphDB`/`TimeSeriesDB`, qui utilisent tous `&self`. La mutabilité interne est gérée par les implémentations (ex. la MultiplexedConnection de RedisStore).

2. **`bee_config_macro` devrait parser l'attribut section** — actuellement seule la section `"default"` est traitée ; il faut parcourir toutes les sections et mapper les champs imbriqués via `#[config(section = "xxx")]`.

3. **`bee_orm_macro` devrait parser l'attribut `#[bee(...)]`** — le nom de table est déduit du nom de la structure + "s", en ignorant l'attribut `#[bee(table = "...")]`.

4. **`bee_cache::Cache::get` devrait retourner `Result<Option<Vec<u8>>>`** — pour rester cohérent avec `CacheError`. La signature actuelle `async fn get(&self, key: &str) -> Option<Vec<u8>>` avale les erreurs réseau/sérialisation.

5. **Ajouter des tests d'intégration** — tous les tests actuels sont unitaires. Recommandation : des tests d'intégration entre `bee_router` + `bee_session` + `bee_cache` pour vérifier la collaboration middleware Session + contrôleurs.

## Conclusion

La qualité globale du code est bonne, le design d'architecture et le découpage en crates sont raisonnables. **Les problèmes clés sont tous des états stub/inachevés**, avec peu de bugs dans la logique métier réelle (seulement deux problèmes concrets : le cycle de vie du guard dans bee_logs et la fuite TTL dans bee_cache).

Le projet se trouve au **début de la Phase 6** — la structure de base est complète, mais l'implémentation des fonctions clés (intégration Router/axum, backends de base de données ORM, rechargement à chaud Config, pilotes concrets des moteurs de stockage) attend encore des tâches ultérieures.
