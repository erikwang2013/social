## 修正済みの問題

### BUG-001: bee_logs — `WorkerGuard` が即時 drop され非同期ログが失われる

**深刻度:** 高  
**ファイル:** `crates/bee_logs/src/lib.rs:54,62`

`tracing_appender::non_blocking()` が返す `WorkerGuard` は `match` 分岐の終了時に drop され、
非ブロッキング書き込みワーカースレッドが即座に停止し、すべての非同期ログメッセージが失われます。

**修正:** `Option<WorkerGuard>` を保持する `LogHandle` 構造体を追加し、`Logger::init()` が
`Result<LogHandle, ...>` を返すように変更。呼び出し側は書き込み継続のため `LogHandle` を生存させ続ける必要があります。

### BUG-002: bee_cache — TTL 期限切れエントリのメモリリーク

**深刻度:** 中  
**ファイル:** `crates/bee_cache/src/lib.rs:60-71`

`MemoryCache::get()` は TTL 期限切れを検知しても `None` を返すだけで、HashMap からエントリを削除しません。
長時間稼働するアプリケーションでは期限切れエントリが蓄積し続け、メモリリークを引き起こします。

**修正:** `get()` は期限切れ検知後、読み取りロックを解放し、書き込みロックを取得して期限切れエントリを削除します。

### BUG-003: examples/hello — 未使用 import の警告

**深刻度:** 低  
**ファイル:** `examples/hello/src/main.rs:1`

`use bee_rust::prelude::*` が未使用で、コンパイル警告が発生します。

**修正:** 該当 import を削除し、`init()` の戻り値を `_log_handle` にバインドして LogHandle が早期に drop されないようにしました。

## アーキテクチャ所見

### 優れた点

1. **Crate 分割が明確** — 15 個の crate の責務が明確で、依存の方向が合理的（基盤 → ストレージ → Web → 集約）
2. **Trait 抽象が完全** — `KvStore`、`SearchEngine`、`GraphDB`、`TimeSeriesDB` の 4 つのストレージ trait の設計が一貫
3. **テスト戦略が正しい** — 各 crate は stub/mock 実装で trait をテストし、外部サービスに依存しない
4. **エラー型が規格化** — `thiserror::Error` derive を統一使用し、エラーメッセージの書式が一貫
5. **ゼロ unsafe** — 全コードに unsafe ブロックなし
6. **proc macro の使い方が適切** — `Config` と `Model` の 2 つの derive macro の責務が単一

### 改善提案

1. **`KvStore` trait は `&self` に変更すべき** — `SearchEngine`/`GraphDB`/`TimeSeriesDB` に倣い、すべて `&self` を使用。内部可変性は実装側で処理（例: RedisStore の MultiplexedConnection）。

2. **`bee_config_macro` は section 属性を解析すべき** — 現状 `"default"` セクションのみ処理。全セクションを走査し、`#[config(section = "xxx")]` でネストフィールドを対応セクションにマッピングする必要がある。

3. **`bee_orm_macro` は `#[bee(...)]` 属性を解析すべき** — 現状テーブル名は構造体名 + "s" から推測しており、`#[bee(table = "...")]` 属性を無視している。

4. **`bee_cache::Cache::get` は `Result<Option<Vec<u8>>>` を返すべき** — `CacheError` との整合性のため。現在のシグネチャ `async fn get(&self, key: &str) -> Option<Vec<u8>>` はネットワーク/シリアライズエラーを握りつぶしている。

5. **統合テストの追加** — 現在のテストはすべてユニットテスト。`bee_router` + `bee_session` + `bee_cache` 間に Session ミドルウェア + コントローラの連携フローを検証する統合テストの追加を推奨。

## 結論

コードの全体的な品質は良好で、アーキテクチャ設計と crate 分割は合理的です。**主要な問題はすべて stub/未完成状態**で、コアビジネスロジックのバグは少数（bee_logs の guard ライフサイクルと bee_cache の TTL リークの 2 件のみが実問題）。

プロジェクトは現在 **Phase 6 初期** — 基盤構造は完成していますが、主要機能の実装（Router の axum 統合、ORM データベースバックエンド、Config のホットリロード、ストレージエンジン具体ドライバ）は今後のタスクを待っています。
