## Problemas encontrados y corregidos en la tercera ronda (3 elementos)

### 1. [Crítico] bee_kv/redis_store — el cambio de API de redis-rs 0.27.6 rompe la compilación con `--all-features`

**Archivo:** `crates/bee_kv/src/redis_store.rs` (9 lugares)
**Gravedad:** Crítica — falla la compilación con `--all-features`

En redis-rs 0.27.6, la firma de `redis::Cmd::query_async()` cambió de `&self` a `&mut self`. Los 9 métodos de `RedisStore` usaban `&self.conn.clone()` y deben cambiarse a `&mut self.conn.clone()`.

**Métodos afectados:** `get`, `set`, `del`, `exists`, `incr` (2), `expire`, `mget`, `mset`

**Corrección:**
```rust
// Antes
.query_async(&self.conn.clone())
// Después
.query_async(&mut self.conn.clone())
```

### 2. [Medio] bee_router/filter — implementación vacía de SessionFilter sin documentación

**Archivo:** `crates/bee_router/src/filter.rs:17-19`
**Gravedad:** Media — el usuario podría suponer erróneamente que la sesión está cargada

`SessionFilter` implementa el trait `Filter` pero usa la implementación vacía por defecto (`before`/`after` devuelven directamente `Ok(())`). Tras llamar a este filtro, el usuario podría pensar que la sesión se ha cargado desde la petición, cuando en realidad no ha ocurrido nada.

**Corrección:** Actualizar el comentario de documentación para aclarar que actualmente es una implementación provisional y que la sesión la crea `Context::new()` por petición.

### 3. [Bajo] bee_template — `_to_json_value` se traga silenciosamente los errores de serialización

**Archivo:** `crates/bee_template/src/lib.rs:92`
**Gravedad:** Baja — solo se usa dentro de la macro `context!`

```rust
// Antes: devuelve Null silenciosamente cuando la serialización falla
serde_json::to_value(val).unwrap_or(serde_json::Value::Null)

// Después: panic con un mensaje de error claro (principio «los errores de programador deben causar panic»)
serde_json::to_value(val).expect("context! macro values must be serializable")
```

## Auditoría de calidad del código (observaciones sin cambios de código)

### Limitaciones conocidas (se recomienda mejorar en versiones posteriores)

| # | Ubicación | Descripción | Prioridad |
|---|------|------|--------|
| 1 | `bee_router/router.rs` | `Handler<T, ()>` usa el parámetro de tipo `()`, por lo que los handlers no pueden usar extractores de axum (State/Query/Path, etc.) | P2 |
| 2 | `bee_config_macro` | `reload()` y `watch()` generan implementaciones vacías, en contradicción con la descripción de «recargar» y «vigilar cambios» de la documentación del trait | P2 |
| 3 | `bee_rust/prelude` | Exportar `bee_config::Config` es una macro derive, no el trait `ConfigSource`; el nombre puede confundir a los usuarios | P3 |
| 4 | `bee_orm/QuerySet` | El genérico `T` no tiene trait bound; `PhantomData<T>` solo se usa como marcador de tipo | P3 |

### Evaluación positiva

- **Gestión de errores:** Todos los crates usan la derivación `thiserror::Error`, con tipos de error claramente definidos
- **Feature gate:** `bee_kv/redis_store` usa correctamente `#[cfg(feature = "redis")]`
- **Cobertura de pruebas:** Cada trait tiene una implementación stub y pruebas correspondientes
- **Documentación:** Todos los tipos públicos y métodos de trait tienen comentarios `///`
- **Seguridad asíncrona:** `tokio::sync::RwLock` se usa correctamente, sin llamadas bloqueantes mezcladas en contextos asíncronos
- **Cero unsafe:** Ningún unsafe en todo el proyecto
- **Cero unwrap:** En el código de biblioteca solo existe `expect()` con comentarios SAFETY

## Resumen

La tercera ronda encontró principalmente el fallo de compilación con `--all-features` causado por el cambio de API de redis-rs 0.27.6 (afecta a los 9 métodos de operaciones KV) y la falta de documentación de la implementación vacía de SessionFilter. Todos los problemas están corregidos, los 63 tests pasan y clippy no reporta avisos.

En el mismo periodo se completó la integración de la biblioteca de detección de ataques security-rust (v1.0.4): `SecurityFilter` implementa el trait `Filter` y escanea la query string de la URI y las cabeceras clave antes de que la petición entre en el Controller, cubriendo 27 tipos de ataque como XSS, inyección SQL, inyección de comandos, SSRF y traversal de rutas. Se añadieron 6 nuevas pruebas de detección de seguridad, controladas por el feature gate `security`.

La calidad general del proyecto es buena: cero código unsafe, gestión completa de errores, convenciones de nombres uniformes, todas las API públicas documentadas y cada trait probado. Las 4 limitaciones conocidas (nivel P2/P3) no afectan a la funcionalidad actual y se recomienda mejorarlas en versiones posteriores.
