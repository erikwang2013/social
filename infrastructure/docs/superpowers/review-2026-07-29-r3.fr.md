## Problèmes trouvés et corrigés à la troisième passe (3 éléments)

### 1. [Critique] bee_kv/redis_store — le changement d'API de redis-rs 0.27.6 casse la compilation `--all-features`

**Fichier :** `crates/bee_kv/src/redis_store.rs` (9 endroits)
**Gravité :** Critique — échec de compilation avec `--all-features`

Dans redis-rs 0.27.6, la signature de `redis::Cmd::query_async()` est passée de `&self` à `&mut self`. Les 9 méthodes de `RedisStore` utilisaient toutes `&self.conn.clone()` et doivent être changées en `&mut self.conn.clone()`.

**Méthodes concernées :** `get`, `set`, `del`, `exists`, `incr` (2), `expire`, `mget`, `mset`

**Correctif :**
```rust
// Avant
.query_async(&self.conn.clone())
// Après
.query_async(&mut self.conn.clone())
```

### 2. [Moyen] bee_router/filter — implémentation vide de SessionFilter sans documentation

**Fichier :** `crates/bee_router/src/filter.rs:17-19`
**Gravité :** Moyen — l'utilisateur pourrait croire à tort que la session est chargée

`SessionFilter` implémente le trait `Filter` mais utilise l'implémentation vide par défaut (`before`/`after` renvoient directement `Ok(())`). Après avoir appelé ce filtre, l'utilisateur peut penser que la session a été chargée depuis la requête, alors qu'en réalité rien ne s'est produit.

**Correctif :** Mettre à jour le commentaire de documentation pour préciser qu'il s'agit actuellement d'une implémentation provisoire et que la session est créée par requête via `Context::new()`.

### 3. [Faible] bee_template — `_to_json_value` avale silencieusement les erreurs de sérialisation

**Fichier :** `crates/bee_template/src/lib.rs:92`
**Gravité :** Faible — utilisé uniquement à l'intérieur de la macro `context!`

```rust
// Avant : renvoie silencieusement Null en cas d'échec de sérialisation
serde_json::to_value(val).unwrap_or(serde_json::Value::Null)

// Après : panic avec un message d'erreur clair (principe « les erreurs de programmeur doivent provoquer un panic »)
serde_json::to_value(val).expect("context! macro values must be serializable")
```

## Audit de la qualité du code (observations sans modification de code)

### Limites connues (amélioration recommandée dans les versions ultérieures)

| # | Emplacement | Description | Priorité |
|---|------|------|--------|
| 1 | `bee_router/router.rs` | `Handler<T, ()>` utilise le paramètre de type `()`, les handlers ne peuvent donc pas utiliser les extracteurs axum (State/Query/Path, etc.) | P2 |
| 2 | `bee_config_macro` | `reload()` et `watch()` génèrent des implémentations vides, en contradiction avec la description « recharger » et « surveiller les changements » de la documentation du trait | P2 |
| 3 | `bee_rust/prelude` | Exporter `bee_config::Config` est une macro derive, pas le trait `ConfigSource` ; le nom peut prêter à confusion | P3 |

### Évaluation positive

- **Gestion des erreurs :** Tous les crates utilisent la dérivation `thiserror::Error`, les types d'erreur sont clairement définis
- **Feature gate :** `bee_kv/redis_store` utilise correctement `#[cfg(feature = "redis")]`
- **Couverture de test :** Chaque trait dispose d'une implémentation stub et de tests correspondants
- **Documentation :** Tous les types publics et méthodes de trait ont des commentaires `///`
- **Sécurité asynchrone :** `tokio::sync::RwLock` est utilisé correctement, aucun appel bloquant dans un contexte asynchrone
- **Zéro unsafe :** Aucun unsafe dans tout le projet
- **Zéro unwrap :** Le code de bibliothèque ne contient que des `expect()` avec commentaires SAFETY

## Synthèse

La troisième passe a principalement révélé l'échec de compilation `--all-features` causé par le changement d'API de redis-rs 0.27.6 (affectant les 9 méthodes d'opérations KV), ainsi que l'absence de documentation de l'implémentation vide de SessionFilter. Tous les problèmes ont été corrigés, les 63 tests réussissent et clippy ne signale aucun avertissement.

Dans la même période, l'intégration de la bibliothèque de détection d'attaques security-rust (v1.0.4) a été réalisée : `SecurityFilter` implémente le trait `Filter` et analyse la query string de l'URI et les en-têtes clés avant que la requête n'entre dans le Controller, couvrant 27 types d'attaques dont XSS, injection SQL, injection de commandes, SSRF et traversée de chemin. 6 nouveaux tests de détection de sécurité ont été ajoutés, contrôlés par le feature gate `security`.

La qualité globale du projet est bonne : zéro code unsafe, gestion complète des erreurs, conventions de nommage uniformes, toutes les API publiques documentées, chaque trait testé. Les 4 limitations connues (niveau P2/P3) n'affectent pas la fonctionnalité actuelle ; leur amélioration est recommandée dans les versions ultérieures.
