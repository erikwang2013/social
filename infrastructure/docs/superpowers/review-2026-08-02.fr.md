## Liste des problèmes

### 1. 🔴 Élément de configuration invalide dans le Cargo.toml racine

**Fichier** : `Cargo.toml:24`  
**Problème** : `name = "bee-rust"` dans `[workspace.package]` est une clé invalide qui produit un avertissement à chaque compilation :

```
warning: /home/wwwroot/bee-rust/Cargo.toml: unused manifest key: workspace.package.name
```

**Correctif** : supprimer la ligne `name = "bee-rust"`. Un package au niveau du workspace n'a pas besoin de nom ; seul le `[package]` de chaque sous-crate en a besoin.

---

### 2. 🔴 Fichier LICENSE manquant

**Problème** : le `Cargo.toml` racine déclare `license = "Apache-2.0"`, mais il n'y a aucun fichier `LICENSE` à la racine du dépôt. Les conditions de la licence Apache-2.0 exigent d'inclure une copie de la licence dans les distributions.

**Correctif** : créer à la racine un fichier `LICENSE` contenant le texte intégral de la licence Apache-2.0.

---

### 3. 🔴 Métadonnées de licence incohérentes entre crates

Les crates suivants n'ont pas de champ `license` déclaré (ils apparaîtront « sans licence » lors de la publication sur crates.io) :

### 4. 🟡 Métadonnées de publication crates.io manquantes

Tous les crates manquent des champs suivants, ce qui nuit à la découvrabilité sur crates.io :

- `description` — brève description
- `repository` — lien vers le dépôt
- `keywords` — mots-clés de recherche
- `categories` — catégories (p. ex. `["web-programming", "database"]`)

Il est recommandé d'ajouter des champs communs dans `[workspace.package]` :

```toml
[workspace.package]
repository = "https://github.com/erikwang2013/bee-rust"
keywords = ["web", "framework", "beego", "mvc"]
categories = ["web-programming"]
```

### 6. 🟡 Les features de moteurs de stockage sont des placeholders vides

Les features suivantes sont déclarées mais n'ont aucune implémentation réelle, servant uniquement de placeholders vides :

- `bee_search` : `elasticsearch`, `opensearch`, `clickhouse` sont tous `[]`
- `bee_graph` : `neo4j`, `nebulagraph`, `arangodb` sont tous `[]`
- `bee_tsdb` : `influxdb`, `iotdb`, `questdb` sont tous `[]`

Cela signifie que les exemples de code du README pour les moteurs de recherche, bases de données graphes et bases de données temporelles ne peuvent pas réellement s'exécuter (leurs tests utilisent aussi des stubs).

**Suggestion** : marquer ces fonctions comme « planned / prévu » dans le README, ou ajouter de vraies dépendances de drivers et des implémentations.

---

### 7. 🟡 StubKvStore::expire() est une opération vide

**Fichier** : `crates/bee_kv/src/lib.rs:111`  
**Problème** : la méthode `expire()` du stub de test `StubKvStore` n'implémente pas la logique d'expiration TTL, alors que le trait définit cette interface. Les tests ne peuvent donc pas couvrir le comportement lié au TTL.

---

### 8. 🟢 Annotation cfg redondante sur RedisStore

**Fichier** : `crates/bee_kv/src/redis_store.rs`  
**Problème** : le module entier est déjà compilé conditionnellement via `#[cfg(feature = "redis")]` dans `lib.rs` ; l'annotation `#[cfg(feature = "redis")]` à l'intérieur de `redis_store.rs` est donc redondante (fonctionnellement correct, mais pas concis).

---

### 9. 🟢 Doc-tests manquants

En dehors de `bee_template` qui a 1 doc-test, aucun des autres crates n'a de tests de documentation. Il est recommandé d'ajouter des exemples de doc-tests pour les traits principaux (`Cache`, `KvStore`, `Controller`, etc.).

---

### 10. 🟢 bee_graph/src/lib.rs est un peu volumineux

406 lignes, proche de la limite de 500 lignes. Un découpage ultérieur est recommandé (par exemple des model.rs, query.rs séparés).

## Synthèse

La qualité globale du code du projet est bonne : compilation réussie, tests entièrement verts, Clippy sans avertissement, zéro code unsafe. L'architecture est claire et les abstractions de traits sont raisonnables. Les principaux problèmes se concentrent sur **l'exhaustivité de la configuration écosystème** — fichier de licence manquant, métadonnées Cargo.toml incomplètes, absence de CI/CD et de configuration de formatage. Ces problèmes n'affectent pas la fonctionnalité, mais ils nuisent au professionnalisme du projet open source et à l'expérience de publication sur crates.io. Il est recommandé de corriger en priorité les éléments P0 et P1.
